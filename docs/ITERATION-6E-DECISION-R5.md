# Requirement

YAHO 개인정보 정책 결정 Round 5 — R1–R4 전체 27항목 충돌 통합 검토.

기준: `f37398655fce1edf5bd6399f56c9aedc6f743b17` · `feature/phase21-ai-service` · PR #54 Draft(사용자 제공; 원격 재조회 없음). 작성일: 2026-10-24 UTC. **DOCS ONLY / 권고·보류 조건 정리 / 최종 정책 승인 아님.**

입력: [6E SPEC](ITERATION-6E-SPEC.md), [조건부 PLAN](ITERATION-6E-PLAN.md), [R1](ITERATION-6E-DECISION-R1.md), [R2](ITERATION-6E-DECISION-R2.md), [R3](ITERATION-6E-DECISION-R3.md), [R4](ITERATION-6E-DECISION-R4.md). 여섯 파일 모두 보호할 기존 작업물로 읽기만 했다. 시작 Git 상태에서 R1–R4는 미추적이었고 SPEC/PLAN은 HEAD 대비 차이가 없었다. 그 차이를 승인 여부로 해석하지 않는다. SPEC/PLAN의 조사 HEAD `12bfdf6`과 구별하여 코드·schema 인용은 이번 기준 HEAD에서 정적으로 확인했다. Memory는 보조 문맥으로만 읽었으며, `agent-memory-repo` 스킬은 설치·프로젝트·Memory 경로에서 찾지 못했다.

**집계:** 27/27항목 교차 검토, 8/8축에 검토 경계·실패·권고·보류 조건 기재. **실행 가능한 충돌 해소 완료 0축 / 충돌 결정 보류 7축(X01–X07) + CONFIRMED 경계·후속 검증 1축(X08)**. X08의 기존 보존 방향·잠금 순서·불변식·scope 유지 경계는 확인되었으며 미해결 정책 충돌로 집계하지 않는다. 기존 경계의 정합성 확인이나 권고문 작성은 정책 충돌 해소·승인으로 세지 않는다. 권고 방향 유지 19항목 / 보완 권고문 필요 8항목이며, 두 집합 모두 미승인 상태다. 아래 C01–C08은 Round 6의 C category 입력이며 Round 6 자체를 작성하거나 승인한 것이 아니다.

## Problem

R1의 거래 필드 종료, R2의 직원·공용 데이터 분리, R3의 연결·capability·재시도, R4의 비CONFIRMED 목적별 파기는 개별적으로 조건부다. 이를 한 사람의 파기 작업으로 합치면 종료 시점·제거 단위·보존 예외가 어긋날 수 있다. 같은 사람의 다른 목적, 같은 행의 다른 사람, 원문 삭제 후 금융 요청, 복구된 사본을 함께 검토해야 한다. 실제 충돌 사례나 개인정보의 존재·건수는 조사하지 않았다.

## Current Process

- **C5/A1:** CONFIRMED `ReservationApplication.childId` 이력이 있는 Child만 기존 고객 5년 정책 대상이다. 미확정 신청 사본은 수업일(KST)+1년·만료일 다음 날·REJECTED/CANCELLED·ADMIN 수동 실행 조건을 따른다. SUBMITTED는 먼저 수동 종결해야 한다([REQUIREMENTS:1879](../REQUIREMENTS.md#L1879), [범위:1923](../REQUIREMENTS.md#L1923), [계산·상태:42](../lib/reservation-applications/retention.ts#L42), [C5 CTE:62](../lib/reservation-applications/last-reserved-class.ts#L62)). G1–G4에 이 기간을 상속하지 않는다.
- **S:** 모든 자녀 신청이 이미 파기된 Submission에 한해 보호자 필드·F07을 NULL 처리하고 parent 파기 표시를 남긴 뒤, 연결 F04/F05도 NULL 처리한다. 별도 필드 목적 종료·미반환 잔액·분쟁·법정기간 검사는 이 함수에 없다([retention:223](../server/reservation-applications/retention.ts#L223)). 일반 Child 파기는 F01–F03을 보존하며, Child 제자리 변환·해당 부속행 삭제·예약 자유입력 NULL·요청 연결 tombstone을 처리한다([retention:264](../server/reservation-applications/retention.ts#L264), [실제 범위:342](../server/reservation-applications/retention.ts#L342)).
- **재시도:** formData 없는 ADMIN receipt 조회와 원문 equality를 검사하는 조회/쓰기 action이 공존한다. F04/F05가 NULL이면 과거 필수 문자열과 일치하지 않는다. 현재 폼은 결과 조회에도 formData를 보낸다([actions:201](../app/%28admin%29/reservation-applications/actions.ts#L201), [입금:234](../app/%28admin%29/reservation-applications/actions.ts#L234), [반환:261](../app/%28admin%29/reservation-applications/actions.ts#L261), [폼:74](../app/%28admin%29/reservation-applications/submissions/%5Bid%5D/deposit-form.tsx#L74)).
- **공유·신원:** F50–F54/F57은 개인별 구조가 없는 단일 문자열이다. F36/F37과 F55는 필수 문자열, F37은 unique이며 F34/F35는 required User FK다. 이름만 지워도 K01의 고객·금융·직원 연결은 남을 수 있다([schema User:164](../prisma/schema.prisma#L164), [Teacher/공용 필드:315](../prisma/schema.prisma#L315), [입금/반환:683](../prisma/schema.prisma#L683)).
- **현재 금융 잠금:** 6D 수정이 반영된 환불은 Payment를 먼저 잠근 뒤 PaymentItem을 잠그고 관계·상한을 재검증한다. 6D SPEC 앞부분의 과거 item→parent 설명을 현재 상태로 인용하지 않는다([6D 실행 기록:163](ITERATION-6D-PLAN.md#L163), [현재 core:110](../lib/payments/core.ts#L110)).

## User Story

운영자는 거래·책임·살아 있는 업무를 보존하면서 불필요한 개인정보만 종료하고 싶다. 서로 다른 라운드의 방향을 동시에 적용해도 안전한 조건과, 운영자·전문가 답이 없어 아직 적용할 수 없는 경계를 구별하고 싶다.

## Scope

F01–F05/F07 6건, F33–F37 5건, F50–F57 8건, K01–K04 4건, G1–G4 4건의 **총 27건**을 8축으로 교차 검토한다. 개별 권고의 유지/보완, 실패 사례, 추천 통합 방향과 독립 결정 의존을 이 파일에만 기록한다.

## Out of Scope

이 파일 외 모든 수정, R1–R4/SPEC/PLAN 덮어쓰기, REQUIREMENTS/ADR 반영, 최종 정책·기간·법률 판단·설계 승인, 구현·테스트·lint·build·CI 실행, stage/commit/push, 모든 DB 접근·실제 개인정보/백업 조회·삭제, migration·scheduler. 기존 금액·환불·보존식·잠금 순서·purge 범위 변경도 이번 정책 검토로 승인하지 않는다.

## Business Rules

- **A층/B층은 보관 목적의 구분이다.** A층의 원장 행·금액·시각·상태·FK·actor·배정·누계 보존은 유지한다. A층에도 식별 가능한 ID·FK·사유 enum이 남을 수 있으므로 비개인정보 층이라는 뜻은 아니다. B층 원문은 필드별 필요성과 실제 증빙 예외를 따로 판단한다. A층 자체의 최종 폐기와 `L`의 실제 분류·기간·기산점은 계속 미결정이다.
- **종료 사건 후보 ≠ 실행 가능한 만료일.** `updatedAt`·거래일·등록일·퇴사일로 없는 목적 종료·신고기한·장부 폐쇄일을 추정하지 않는다. 기존 C5/A1/S도 새로운 필드 기간의 법적 근거로 전용하지 않는다. 모든 새 적용 판단·예외·기간은 **ESTIMATE / 전문가 확인 전 미결정**이다.
- **법률 보조 확인:** 공식 [개인정보 보호법 제15조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1033214947)는 동의에 근거한 항목·목적·기간 등의 변경 고지·동의 규정을, [제21조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334901)는 불필요 정보의 파기와 다른 법령상 보존·분리 관리를, [제23조](https://www.law.go.kr/lsLinkCommonInfo.do?ancYnChk=&chrClsCd=010202&lsJoLnkSeq=1020398539)는 건강 등 민감정보의 별도 근거를 검토할 때 참조했다. 이 조문 확인은 YAHO의 개별 적법성·예외·보관기간 또는 백업 잔존 허용을 확정하지 않는다. E01–E08은 [SPEC Open Questions](ITERATION-6E-SPEC.md#open-questions)의 전문가 검토 ID를 그대로 사용한다.
- **통합 단위:** 사람 전체·Child 전체·Submission 전체·필드 전체·개별 내용·capability grant는 서로 다른 단위다. 한 단위의 만료/hold/파기 표시를 다른 단위로 자동 전파하지 않는다. 단위가 불명확하면 해당 범위의 실행을 보류하고 담당자·접근 제한·재검토 조건을 정할 방향만 제시한다. 불명확함은 무기한 보관 근거가 아니다.
- **보존 예외와 hold:** 실제 근거·필수 필드·사본 범위·접근자·종료/해제 사건·재검토일·책임자를 갖춰야 한다. 한 목적의 hold로 모든 개인정보를 가장 긴 기간까지 연장하거나, 다른 목적이 종료했다는 이유로 hold 대상 필드를 지우지 않는다. 새 전역 hold를 기존 C5/A1/S에 삽입하는 승인은 없다.
- **승인 상태:** 아래 RECOMMENDED RESOLUTION은 선택을 위한 제안이다. DEFERRAL CONDITION의 운영자·전문가 답, 해당 범위의 정책 기록과 별도 설계 승인 전에는 기존 규칙을 바꾸지 않는다. 새로운 원문 사본·이름/사유 hash·역매핑·개인정보 수집항목을 해결책으로 선택하지 않는다.

### X03 보충 — 현행 방어와 승인할 계약의 차이

- Deposit/Return의 키는 **각 테이블에서 unique인 nullable 필드**다. 종류 간 전역 고유성이나 과거 모든 행의 키 존재를 가정하지 않는다([schema:691](../prisma/schema.prisma#L691), [schema:738](../prisma/schema.prisma#L738)). NULL인 원문의 삭제 경위도 값만으로 증명되지 않는다. 기간·과거 행 처리 근거 없이 키를 지우거나 backfill하지 않는다.
- 현행 formData 없는 lookup은 원장 무결성·최신 잔액을 검증하지 않는다. 쓰기 action은 Submission 잠금·원장 검증·전체 payload 비교를 수행하므로, core가 prior key/target을 보고 기존 결과를 돌려준다는 사실을 비교 생략의 승인으로 사용할 수 없다([lookup:201](../app/%28admin%29/reservation-applications/actions.ts#L201), [쓰기:231](../app/%28admin%29/reservation-applications/actions.ts#L231), [core:196](../server/reservation-applications/finance.ts#L196)).
- 파기 후 read-only 계약은 현재 폼의 원문 포함 결과 조회·not-found 후 재쓰기 경로와 구별해야 한다. **원문이 없어 동일성을 검증할 수 없는 요청을 성공 replay로 바꾸지 않고 기존 기록 확인으로만 다룰지** 먼저 결정해야 한다. 원문 재입력 유도·새 키 재처리·원문/이름/사유 hash 보존은 해결안으로 채택하지 않는다.

### X06/X07 보충 — 보장 범위·고지 근거의 실제 간극

- **보장 가능 범위:** 향후 실제 승인·처리·검증이 있다면 그 정책 version·대상 범위·처리 시점에 대해 “지정 필드/부속행 처리, 원장·책임 연결 잔존”이라고 보고할 방향이다. 이 문서 작성은 처리 실적이 아니다. replica·CSV·로그·백업 세대별 반영/최종 종료가 입증되기 전 “전 사본 즉시 영구 파기” 또는 “법률상 익명정보”라고 보고할 수 없다. 백업 일부를 기술적으로 즉시 수정하기 어렵다는 사정도 무기한 잔존·법적 면책을 승인하지 않는다.
- **세대와 복구 증거:** 사본 종류별 보관 세대·원문을 포함하는 마지막 세대·최종 잔존 시점·접근권·폐기 확인 담당자가 필요하다. 복구 대상 snapshot보다 뒤의 파기/철회 사실은 그 snapshot만으로 회복할 수 없으므로 대조 근거가 독립적으로 확보돼야 한다. 증거 후보는 최소 대상 ID/범위·정책 version·시각·actor·결과·복구 후 재검증/복귀 승인이고, 이 연결 자체의 식별 위험·보관기간도 E05/E06 결정 대상이다. 새 저장소·table·실행 절차를 이번에 설계하거나 승인하지 않는다.
- **고지의 확인된 간극:** r3 수집 목록은 F07 선언명/F04 실제 입금자명을 직접 열거하지 않는다. 그런데 Phase 20 제출은 선언명을 필수로 검증하고 저장한다([동의:67](../lib/reservation-applications/consent-content.ts#L67), [검증:83](../lib/reservation-applications/phase20-validation.ts#L83), [저장:305](../server/reservation-applications/groups.ts#L305)). “거래기록 별도 법령 보존” 문구([동의:72](../lib/reservation-applications/consent-content.ts#L72))만으로 그 원문 항목·모든 보존 목적/기간이 고지·동의됐다고 결론내릴 수 없다. F07을 실제 입금자명 사본으로 보거나 새 이름 hash로 바꾸는 해결도 없다.
- **아동·건강·과거자료:** 기존 요건은 요청사항에 건강정보를 적지 않도록 안내하고 안전정보는 별도 ChildSafetyInfo·민감정보 동의·제한 접근으로 다룬다([REQUIREMENTS:1861](../REQUIREMENTS.md#L1861), [20-1.2–1.4:840](../REQUIREMENTS.md#L840), [schema:254](../prisma/schema.prisma#L254), ADR-006/008/054/055). 자유입력에 실제 혼입됐다는 확인은 없으나, 있다면 일반 신청 동의나 재무 권한으로 별도 근거를 대체하지 않는다. 새 고지/동의의 대상·문구·시행 시점·미응답 처리와 과거자료 정리는 E01/E04 판단이 먼저다. 직원·강사 계약/노무 근거도 고객 신청 동의와 별개다.

### 일관성 선언 — 유지 19항목 / 보완 8항목

**수정 없이 살아남는 조건부 권고:** R1 **F01/F03**, R2 **F33–F37/F50–F57 전부 13항목**, R3 **K01/K02**, R4 **G1/G2**, 총 19항목이다. 각각의 법적 근거·기간·사건 증거·접근·사본·예외가 미결정이라는 상태도 그대로 유지한다.

- F01은 대사 후 이름 NULL, F03은 환불/실제 분쟁 후 상세 NULL 방향과 enum·신규 NO_SHOW/ABSENT 검증 유지가 양립한다. 실제 잔존 목적이 있으면 기존 R1 예외 확인을 먼저 한다.
- R2의 직원 FK 보존·이메일 비투영·계정/강사 목적 독립, 공용 개인 부분 제거/모든 목적 종료 시만 전체 NULL/비개인 내용 유지 후보를 유지한다. **R2 권고 유지가 SPEC F50–F53/F57의 단위 미정합 해소나 redaction 최종 채택을 뜻하지 않는다.** F52 민감정보·F55 실명 판단도 독립 보류다.
- K01은 잔존 연결의 익명성 한계를 계속 명시하고 원장/FK를 끊지 않는다. K02는 TTL/철회와 저장 종료, 개별 grant와 전체 기기를 구별하며 금융 멱등키를 같이 지우지 않는다.
- G1은 출처 미상·독립 근거/기간, G2는 실제 이용·취소·NO_SHOW별 사건을 유지한다. 신청/예약 부재로 관리자 등록을 단정하거나 C5를 상속하지 않는다. G4는 별도 인원 집단이 아닌 overlay다.

**보완이 필요한 8항목:** R1 **F02/F04/F05/F07**, R3 **K03/K04**, R4 **G3/G4**다. 아래는 원문을 바꾸지 않고 제시하는 **향후 통합 권고문 대체안의 인용**이다. 방향을 철회하거나 결정을 완료한 문구가 아니며, C질문 해소와 행별 채택 기록이 필요하다.

**M01 — F02 / D16-MEMO, X01/X02/X04/X05.** R1의 “목적 종료 후 전체 memo NULL”은 공유 Payment와 혼합 내용의 전체 목적 종료 조건을 보완해야 한다. SPEC BR4도 전체 NULL을 최소 제안으로 두므로, R2의 내용별 제거 후보를 Payment.memo에 적용하는 것은 자동 정합화가 아닌 **새 단위 선택 제안**이며 C02의 명시 결정을 요구한다. 단순 이름 마스킹을 파기 완료로 취급하지 않는다.

> 대사·해당 문의의 종료를 Payment.memo의 목적 종료 후보로 유지한다. 공유 Payment의 다른 사람·유효 업무·필수 증빙에 필요한 내용이 없는지 본문 단위로 확인한 뒤 전체 NULL을 추천한다. 일부만 만료한 혼합 본문은 R2의 고객별 내용 제거/전체 목적 종료 때만 전체 NULL 후보를 함께 검토하며, 단위·정확성·예외가 불명확하면 해당 처리 범위를 보류한다. 한 Child의 만료만으로 메모 전체를 지우거나 금융 L로 전체를 연장하지 않는다.

**M02 — F04/F05/F07 / D16-DEPOSIT/RETURN/DECLARED, X01/X02/X03/X05/X07.** 대사·반환/분쟁 목적 종료 사건은 유지하되 **S의 우선순위가 정해지지 않았다는 조건을 각 권고에 명시**해야 한다.

> F04는 실제 입금자 대사, F05는 반환 이행·관련 실제 분쟁, F07은 선언명 대사를 종료 후보로 유지한다. 각 필드가 S보다 먼저 또는 뒤에 종료되는 경우의 적용 조건과 최소 보존 예외를 운영자·전문가가 행별로 결정하기 전에는 S를 앞당기거나 늦추거나 자동 우선하지 않는다. 승인 후 필드별 종료를 별도 판단하는 방향을 추천하되 그 차이는 새 정책 기록과 후속 설계에 명시한다. F04/F05는 K04 파기 후 계약·새 금융행위/사유 입력 근거, F07은 고지 간극과 완료 송금 안내에서의 실제 필요를 먼저 확인한다. 보호자 연락·실제 입금자·선언명·반환 사유를 하나의 공유 개인정보 묶음으로 취급하지 않는다.

**M03 — K03 / D16-COMPLETION, X02/X06/X07.** R3의 “완료 접근 만료 또는 그 capability 대상 PII 파기 중 먼저”는 **부분 파기를 무엇으로 볼지** 정해지기 전 실행 조건이 될 수 없다.

> 완료 만료 또는 승인된 대상 PII 파기 중 먼저 발생한 사건에서 불필요 hash를 끝내는 방향을 유지한다. 그 전에 일부 자녀·선언명·다른 필드의 파기가 전체 capability 종료인지, 유효 형제의 최소 안내만 허용할지 독립 결정한다. 단위 미결정은 S까지 보관 연장한다는 뜻이 아니다. 만료/파기 접근을 복원하지 않고 Submission/원장과 K04 ADMIN receipt는 보존하며, expiry metadata·사본·복구 후 재차단도 별도 종료 조건을 확인한다.

**M04 — K04 / D16-REPLAY, X01/X02/X03/X06.** R3의 읽기 전용 receipt/write-replay 종료 권고는 유지하되 **현재 UI 동작·성공 의미·키 필요기간과의 차이**를 통합 권고에 포함해야 한다.

> F04/F05가 적법하게 남는 동안 전체 원문 비교를 유지하고, 원문 파기 후 기존 성공 거래의 원문 기반 write-replay 종료와 명시적 읽기 전용 receipt 확인을 추천한다. receipt 성공은 ADMIN의 종류·대상·키에 해당하는 기존 저장 기록의 존재만 뜻하며 payload 동일성·은행 이체 성공·최신 잔액을 증명하지 않는다. 불일치·미발견·결과 불명은 자동 쓰기/새 키로 넘기지 않는다. 키 보존기간·조회 창·NULL 출처 불명/키 없는 과거 행·실제 새 금융행위의 처리 계약을 F04/F05·S 결정과 함께 먼저 승인받는다. 현재 폼과 formData 조회가 이미 이 계약을 구현했다고 간주하지 않으며, 비교 완화·원문/hash 추가 저장으로 우회하지 않는다.

**M05 — G3 / D17-UNCONFIRMED, X02/X03/X05/X07.** “사본 A1·SUBMITTED 보호 유지, 독립 Child와 반환 연락 별도 판단”은 **A1/S와 반환 연락의 충돌 처리**를 더 명시해야 한다.

> REJECTED/CANCELLED 사본의 기존 A1, SUBMITTED 수동 종결 선행, 독립 Child의 별도 근거·기간을 유지한다. A1 사본/S에 의해 지워질 이름·연락 등이 미반환·분쟁·필수 증빙에 실제 필요하면 최소 필드·사본·대상/해제 사건과 기존 조건의 선후를 독립 결정하기 전 해당 새 정책 적용을 보류한다. 사본/parent 전체 연장·원문 복제·전화번호 병합으로 해결하지 않는다. 신청만인 사람에게 Child를 만들지 않고, 실제 반환 완료와 K04 조회·새 금융행위 계약은 별도로 확인한다.

**M06 — G4 / D17-MIXED, X01/X02/X04/X05/X06/X07/X08.** 목적별 최소 처리 방향에는 **필드 hold·개인 전체 차단·부분 marker·공유 보호**의 서로 다른 단위를 명시해야 한다.

> 예약 이행·거래 증빙·동의 입증·현장 안전 각각의 만료/예외를 필드·행·사본별로 독립 판단한다. 유효 예약·미반환·실제 분쟁·법정 증빙에 필요한 필드를 포함한 전체 파기는 막고, 다른 목적의 만료 필드는 분리 가능성과 승인 조건이 확인된 별도 범위에서만 정리할 수 있다. 같은 필드의 중첩 필요·공유 본문·유효 형제·직원/강사 신원은 최소 범위와 접근·해제 책임을 따로 결정한다. 부분 종료를 Child/Submission 전체 purge marker로 표시하지 않고, 비CONFIRMED Consent/Safety의 새 삭제 예외·기존 C5 변경·전역 hold 삽입을 이 방향 승인으로 허용하지 않는다.

**공통 일관성:** 원장 보존, 새 원문/hash/역매핑 미추가, C5/A1/S 자동 변경 금지, 법적 적용 ESTIMATE, 최소 조회, 사본/복구 별도 확인, 최종 승인 아님이라는 R1–R4 공통 전제는 그대로 살아남는다. 위 보완안 채택도 전문가의 미결정을 대신하지 않는다.
