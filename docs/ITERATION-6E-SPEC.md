## Problem

6C는 A16(거래 개인정보의 기간·종료 처리)과 A17(CONFIRMED 신청 이력 없는 고객)을 MAJOR/P1 별도 승인 대상으로 남겼다(`docs/ITERATION-6C-REPORT.md:158`, `:159`). REQUIREMENTS는 거래의 `payerName/memo/reasonDetail`과 기존 고객 정책을 명시적으로 미결정으로 둔다(`REQUIREMENTS.md:2380`, `:2381`). 실제 데이터의 존재·건수·적법성은 이 조사로 판정하지 않는다.

## Current Process

### 확정된 경계

## User Story

운영자는 거래 사실을 훼손하지 않으면서 각 개인정보 사본의 목적·근거·기산점·종료 방식을 승인하고, CONFIRMED 이력 없는 고객을 별도 근거로 분류하여 무기한 보존과 무단 파기를 모두 피하고 싶다.

## Scope

A16의 필드별 두 보관 층, A17의 네 분류, 운영 결정표, 법률 전문가 검토 질문 및 승인 후 조건부 PLAN만 작성한다.

## Out of Scope

실제 자료/DB/백업 조회, 개인정보 검색·삭제·반출, 통계 건수, 코드·테스트·workflow·config 변경, migration 실행, scheduler 구현·활성화, commit/stage/push, 기존 5년 고객 정책·금액/환불/Revenue 정책 변경. 본 문서의 숫자 후보는 자동 승인값이 아니다.

## Business Rules

### BR1. 금융행위와 개인정보 필드는 다른 보관 층이다

- **A층(금융행위)**: Payment/PaymentItem/Refund, Deposit/Allocation/Obligation/Return/Mapping의 행·금액·일시·상태·연결, 환불 누계 및 `D=A+P+R+T`를 보존한다(`docs/DECISIONS.md:549`, `:550`, `:551`; `server/reservation-applications/retention.ts:272`). 서비스에 적용되는 법정 증빙 분류/기간은 아직 확정되지 않았다. A층 보존이 모든 B층 필드의 보존 의무를 뜻하지 않는다.
- **B층(개인정보 필드)**: 필요한 이름·연락처·사유만 목적/동의·계약·개별 법정 증빙 필요성에 따라 보관한다. 자유입력 전체를 세무증빙이라고 단정하지 않는다. 필드 필요성 종료 후 NULL/내용 삭제가 기본 제안이고, Child.name은 기존 공통 표식 `(파기됨)`을 쓴다. 이름 hash·유일한 대체 이름·별도 역매핑은 만들지 않는 운영 권장안이다.
- FK/금액/시간의 조합이나 외부 장부로 재식별될 수 있으므로 위 처리는 **필드 제거/기존 정책상 비식별화**다. 잔존 레코드가 법률상 익명정보라는 판단은 **ESTIMATE**, E05 전문가 검토 대상이다. 불변 ledger FK를 끊거나 합계를 바꾸는 방식으로 익명화를 주장하지 않는다.

### BR2. 근거 표기와 법률 검토

**법률 해석 honesty rule:** 저장소의 승인 문서가 직접 말하지 않은 모든 적용 판단·기간 후보·아동 관련 시사점은 **ESTIMATE(추정)**이며 E01–E08 전문가 검토 대상이다. 아래 공식 법령 링크는 조문 문서의 근거일 뿐 **YAHO에 그 기간이 확정 적용된다는 결론이 아니다**. 서비스의 사업자/세무 지위, 온라인 신청과 계약 성립, 증빙 분류, 실제 고지·동의·분쟁 자료를 검사하지 않았다. 전자금융거래법상 금융회사/전자금융업자의 기간을 이 프로그램 사업자에게 자동 적용하지 않는다.

### BR3. 표의 기간·처리·운영 코드

이 코드들은 아래 **각 행의 두 보관 층과 기산점·종료 처리에 포함**된다. 운영 권장안은 법령상 의무 열과 별도다.

- **C5**: CONFIRMED 이력 Child만 마지막 유효 예약 수업일/fallback+5년, KST 만료 다음 날 파기. 기존 승인 정책. A17 집단에는 사용 금지.
- **A1**: 신청 사본은 수업일+1년, REJECTED/CANCELLED만 수동 파기. SUBMITTED 자동 전이 금지. CONFIRMED 사본은 C5. 기존 승인 정책.
- **S**: Submission의 모든 자녀 신청이 각 A1/C5에 따라 파기된 뒤 parent/Deposit/Return PII 제거. 기존 코드의 처리 시점. 거래 필드의 별도 적법 기간이 승인된 것은 아니다.
- **L**: A층 법정 증빙 기간은 E/T/C 중 **실제 적용되는** 분류·기산점만 사용. B층은 해당 필드가 증빙에 필요한 기간만(필요 없으면 목적 종료 시 제거)이라는 **ESTIMATE 권장안**. 기간 숫자·기산사건·연장/분쟁 종료 조건은 미결정이다. `paidAt/depositedAt/refundedAt/returnedAt`은 사건 후보이지 세무/장부 기산 확정값이 아니다. 장부 폐쇄/신고기한 데이터가 없으면 실행 금지.
- **N**: nullable 필드 NULL, 자유입력 내용 삭제. 금액/일시/status/부모·자식 원장 FK/환불 누계/사유 enum은 유지. 고유 토큰이나 이름 hash로 대체하지 않는다.
- **C**: 기존 Child 변환(name 공통 표식, birth/guardian/memo NULL, gender UNSPECIFIED, inactive/파기 표시); **D**: 해당 부속 행 삭제. 어느 것도 금융·예약 행 삭제를 뜻하지 않는다.
- **B1**(모든 PII 행): 논리적 DB 필드 제거가 snapshot/PITR/복제본/CSV/로그의 제거 증명은 아니다. 운영자는 복제 전파·백업 보관주기/최종 잔존 시점·법정분리 보관/접근자·복구 후 재파기 절차를 승인해야 한다. 실제 설정 미확인. 원문을 삭제 로그/재시도 데이터/복구 목록에 다시 저장하지 않는다. 전문가 검토 E06.
- **B2**: B1+건강/아동 내용은 일반 목록·재무 화면에서 제외. ChildSafetyInfo 목록 include 금지라는 기존 경계 유지(`prisma/schema.prisma:254` 주석 및 `docs/DECISIONS.md:69` 참고). 재무 ADMIN 권한이 건강정보 장기보관 근거는 아니다(**ESTIMATE**, E04).
- **B3**: B1+처리자 User 참조는 직원/계정 담당자 권한으로 한정; 고객 파기에서 계정/인증정보를 연쇄 삭제하지 않는다. **B4**: B1+capability/hash도 연결 가능성 평가; 기존 만료/철회·파기 고객 접근 차단 유지.

각 A17 집단의 권장 기간은 **확정 숫자가 없는 목적 종료 기반 제안**이다. 운영자가 숫자/기산점/예외/과거자료 처리 근거를 승인할 때까지 실행 가능한 만료일이 아니다. 거래 보존 의무가 있어도 모든 고객/건강 데이터를 함께 보존한다는 결론은 없다(**ESTIMATE**, E01/E04).

### BR4. 종료 처리 후 정확히 남는 것

F01–F05의 N을 승인하면 이름/자유입력 원문은 NULL이고, Payment/Item/Refund 및 Deposit/Allocation/Obligation/Return/Mapping의 id·FK·금액·일시·상태·사유 enum·환불/반환 누계·필요 actor 증빙이 남는다. 식별이 불필요한 화면 표시는 공통 “파기됨” 표시만 사용한다. 이름 hash/전화번호 hash/역매핑 파일을 새로 만들지 않는다. 자유입력을 부분 마스킹해 원문 내용을 남기는 대안보다 전체 NULL이 최소 제안이다. 구조를 남기는 결정은 ledger 무결성 제약이며, 법률상 익명정보 판단과 금융 장부 자체의 최종 폐기는 별도 검토다.

현재 schema상 핵심 F01–F05는 nullable이므로 값 제거 자체에 migration이 필요하지 않다(`prisma/schema.prisma:803`, `:808`, `:843`, `:687`, `:737`). 직원 FK(required), 새로운 목적종료/hold/파기 증빙 저장 요구를 선택하면 별도 schema 설계가 필요할 수 있다. 그 선택은 PLAN에서 조건부로만 다룬다.
