# YAHO 개인정보 정책 결정 Round 2 — 처리자·공용 데이터 13항목 운영자 결정표

근거: [6E SPEC BR1–4·F33–F37·F50–F57·E01–E07](ITERATION-6E-SPEC.md#business-rules), [6E PLAN Gate 0·Data Model·P11](ITERATION-6E-PLAN.md#task), [Round 1](ITERATION-6E-DECISION-R1.md). Round 1은 미커밋 원문을 읽기만 했다. SPEC/PLAN의 조사 HEAD는 `12bfdf6`이며, 아래 코드·스키마·migration 인용은 이번 기준 HEAD에서 정적으로 확인했다. DB·실제 개인정보·운영 설정은 조회하지 않았고, 자유입력에 실제 개인 내용이 저장되어 있다고 단정하지 않는다. `agent-memory-repo` 스킬은 로컬 설치·프로젝트·Memory 경로에서 찾지 못했으며, 기존 Memory는 보조 문맥으로만 읽었다.

- **A층**은 금융 행·금액·일시·상태·처리자 FK·배정·누계를 보존하는 층, **B층**은 이름·이메일·전화·자유입력의 개별 목적을 판단하는 층이다. 공용 클래스·프로그램·강사 구조도 유지하되 공용 본문 자체를 금융 증빙으로 간주하지 않는다. `L`은 SPEC의 실제 적용 증빙 분류·기간·기산점이며 **미결정**이다. 고객 C5·신청 A1·Submission 전체 자녀 파기 조건 S를 이 13항목의 보관기간으로 전용하지 않는다.
- ④의 **P**(개인정보 보호법 제15·21·23조), **H**(아동·건강 관련 근거), **E/T/C**(전자상거래·세무·상업장부 관련 증빙 후보)는 [SPEC BR2](ITERATION-6E-SPEC.md#br2-근거-표기와-법률-검토)의 검토 코드다. 모든 필드별 법적 적용·예외는 **ESTIMATE / 미결정**이다. 공식 [제15조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1033214947), [제21조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334901), [제23조](https://www.law.go.kr/lsLinkCommonInfo.do?ancYnChk=&chrClsCd=010202&lsJoLnkSeq=1020398539) 공개 문서를 보조 확인했으나 YAHO의 개별 적법 근거·법정기간을 확정한 것은 아니다. 신규 숫자 기간은 제안하지 않는다.
- ③은 **기간이 아닌 목적 종료 사건 후보**, ⑦은 그 사건과 법적 기산점·기간의 검증 상태다. 목적이 끝났다는 추천만으로 실행 가능한 만료일이 생기지 않는다. 예외는 실제 필요한 최소 필드·근거·해제 사건·담당자를 따로 확인하며, 막연한 감사 가능성을 무기한 보존 근거로 삼지 않는다.
- **고객 파기를 이유로 User 행 또는 ADMIN 계정을 연쇄 삭제(cascading deletion)하는 것은 금지한다.** 직원·강사의 신원 정리도 고객 파기에 연결하지 않는다. 필드 제거·공통 표시만으로 잔존 FK가 법률상 익명정보가 되었다고 판단하지 않는다. SPEC B1–B3에 따라 사본·백업·복구 후 재노출·접근 통제는 별도 검토한다.
- 행 끝의 **approvable-direction**은 운영자가 방향만 승인할 수 있는 미승인 후보, **deferred-pending-expert**는 식별 범위·민감정보·책임증빙 등 핵심 판단을 전문가 확인 전 보류하는 상태다. 어느 상태도 정책 확정·구현·파기 승인이 아니다.

## A 보충 — 직원 FK 무결성과 두 종료일

- **퇴사일/계정 비활성화일은 업무·접근 종료 사건이고, 거래 책임증빙 보존 종료일은 해당 거래의 필요한 책임 확인·적용 증빙의 종료 사건이다.** 퇴사 뒤 실제 감사·분쟁이 남거나, 이메일 연락 필요는 이미 끝났어도 처리자 식별만 필요할 수 있다. 반대로 계정이 활성이라고 과거 모든 거래 실명의 보존 필요가 입증되는 것도 아니다. F33–F35의 FK·행위·시각과 F36/F37의 원문·조회권을 분리하여 판단한다. 이 날짜들을 같게 두거나 가장 늦은 날짜 하나로 이름·이메일을 일괄 연장하지 않는다. 퇴사·비활성화 날짜를 `updatedAt`으로 추정하지 않는다.
- **필수 제약은 정적 확인 사실:** [초기 migration:19·33](../prisma/migrations/20260820050000_init/migration.sql#L19)의 User.name/email NOT NULL·email unique, [입금:162·169](../prisma/migrations/20261006090000_phase20_reservation_application_enhancements/migration.sql#L162)·[반환:192·200](../prisma/migrations/20261006090000_phase20_reservation_application_enhancements/migration.sql#L192)의 required FK·DELETE RESTRICT가 있다. F34/F35 NULL은 현 제약에 위배된다. F33은 nullable이고 [기존 FK는 DELETE SET NULL](../prisma/migrations/20260820050000_init/migration.sql#L49)이지만, 이것은 User 삭제나 처리자 연결 제거의 정책 허가가 아니다. **고객 purge로 User 행·ADMIN 계정을 연쇄 삭제하는 제안은 금지**다. 전체 공통 이메일 대입은 unique 위반이며, 임의 고유 대체 이메일/이름 hash/역매핑을 새 보존 수단으로 선택하지 않는다.
- 퇴사자 접근 차단과 감사 조회 허용은 별개다. 현행 [principal:89](../lib/auth/principal.ts#L89)은 비활성 계정·authVersion 불일치를 거절한다. 거래 조회는 현재 User.name을 조인하므로 이름 변경·제거가 **다른 모든 관련 거래의 표시에도 영향**을 준다. 이름 snapshot을 새로 복제해 해결하는 결정은 없다. 현 ADMIN 거래 조회 가능 범위를 퇴사 후 승인 책임 담당자의 필요한 실명 조회로 좁힐지는 미결정이며, 별도 새 역할을 발명하지 않는다. 계정 담당 ADMIN의 인증·이메일 관리와도 구별한다. [UserAccountChange.previousEmail/nextEmail 및 감사 FK](../prisma/schema.prisma#L198)는 계정 소유자의 별도 검토 범위이며, 현재 이메일 제거만으로 모든 사본이 사라진다고 판단하지 않는다. FK 유지가 원문 신원의 무기한 보존을 승인하는 것은 아니다.

## B 보충 — 혼합 공용 필드의 정확한 제거 단위

- **고객별 내용 제거(redaction):** F50–F54/F57에 그 고객의 만료한 개인 내용이 확인되고 다른 사람·공용 목적이 살아 있으면 우선 검토할 단위다. 단순 이름 마스킹만으로는 알레르기·가족관계·사건 문맥으로 식별될 수 있어 해당 개인 내용과 간접 식별 단서까지 평가해야 한다. 같은 이름의 다른 사람 오삭제, 문맥 손실, 자유입력 검색 누락 위험이 있어 고객 ID 기반 구조가 없는 본문을 이름 매칭만으로 자동 판정하지 않는다. 실제 내용 검토는 이번 작업에서 수행하지 않았다.
- **전체 필드 NULL:** 본문 전체의 목적·보존 예외가 모두 종료했거나 모든 내용이 해당 고객의 제거 대상임이 확인될 때의 후보다. 분리가 어렵다는 이유만으로 다른 고객의 살아 있는 안전정보·취소 설명·운영 지식을 함께 지우지 않는다. **무조치:** 개인정보가 없는 공용 운영 내용이거나 해당 내용의 정당한 목적·예외가 아직 유효할 때 가능하다. 범위를 알 수 없어 검토 보류하는 것은 무기한 무조치 승인이 아니며, 담당자·접근 제한·재검토 조건을 정해야 한다. 어느 경우에도 공용 행·배정·예약·금융 FK를 지우지 않는다.
- **safetyMemo와 ChildSafetyInfo:** [REQUIREMENTS 20-1.2–1.5](../REQUIREMENTS.md#20-1-아동-안전-정보-및-동의)·[ADR-006](DECISIONS.md#adr-006-아동-안전-정보를-별도-테이블로-분리하고-수집-범위를-제한한다)은 장소의 공용 안전 주의사항과 아동별 알레르기·현장 긴급정보를 구별한다. 후자는 ChildSafetyInfo에 분리하며 진단명·병력·복용약 이력은 저장하지 않는 기존 경계다. [클래스 상세 projection](../lib/classes/queries.ts#L63)은 safetyMemo를 조회하므로, 만일 건강내용이 혼입되면 별도 안전정보의 목록 제외·상세 접근·조회 감사 보호를 그대로 받는다고 가정할 수 없다. 필요한 현장 대응은 별도 안전정보 구조와 기존 권한 안에서 검토하며, 혼입 내용을 자동 복사·이관하거나 동의·기간을 새로 인정하지 않는다. C5의 ChildSafetyInfo 삭제가 공용 메모 사본까지 제거하지 않는다는 **구조적 가능성**만 확인했으며 실제 사본 존재를 확인한 것은 아니다.

## C 보충 — Teacher와 인증 User의 독립 정책

Teacher는 배정·업무 연락·과거 수업 책임의 대상이고, User는 인증·역할·계정 변경 감사와 금융 처리자 연결의 대상이다. Teacher는 [선택적인 User 역관계](../prisma/schema.prisma#L315)를 가지며, User의 [teacherId는 unique·선택적](../prisma/schema.prisma#L171)이다. TEACHER 역할에는 연결을 요구하지만 ADMIN/MANAGER는 연결 없이 존재한다([ADR-050](DECISIONS.md#adr-050-phase-16은-adminmanagerteacher-3단계-역할과-manager의-재무계정-경계를-사용한다), [role/teacher CHECK:55](../prisma/migrations/20260913170000_phase16_account_access_management/migration.sql#L55)). 따라서 강사 모두가 인증 계정을 가진다거나 직원 모두가 Teacher라는 전제는 없다.

**Teacher 전화의 업무 연락 종료(F56), Teacher 실명의 과거 수업 책임 종료(F55), 메모 내용별 목적 종료(F57), User 인증/연락 종료(F36/F37), 금융 처리자 책임 목적(F33–F35)은 독립 정책이다.** TEACHER의 접근에는 User와 Teacher 양쪽 활성 상태가 영향을 주지만([principal:115](../lib/auth/principal.ts#L115)), 그 접근 차단 규칙이 두 저장소의 보관기간을 합치지는 않는다. Teacher 이름을 공통 표시로 바꾸더라도 연결 User에서 식별될 수 있고, User 이메일을 없애더라도 Teacher 전화가 남을 수 있다. 각각의 최소 범위·기산·예외·권한을 확인해야 하며 연결/계정의 추가 정책을 이번에 확정하지 않는다.

### (a) BATCH로 승인할 수 있는 방향

- **13행 공통 경계:** 고객 C5와 직원/강사/공용 목적을 분리, 고객 purge의 User/ADMIN 계정 연쇄 삭제 금지, 금융 처리자 FK·원장/공용 구조 유지, 실명/연락의 별도 최소화, 기간·법적 적용 ESTIMATE 유지, 잔존 FK의 익명정보 단정 금지. 공통 원칙 승인과 개별 처리 승인 기록을 구별한다.
- **F33/F34/F35 공통 조회 방향:** 기존 FK 유지·거래 이메일 비투영, 퇴사 후 권한 차단과 책임증빙 조회를 분리한다. 필요한 실명 범위·기간·기산점은 이 묶음으로 확정하지 않는다.
- **F50/F51/F53/F54/F57 공통 내용 단위 방향:** 비개인 공용 내용 유지, 확인된 만료 개인 부분만 제거, 전체 필드의 모든 목적·예외 종료가 확인된 경우에만 전체 NULL 후보. F52의 민감정보 판단은 독립 보류. 같은 회의에서 승인하더라도 **다섯 행별 선택·범위**를 기록하며 운영자 답변 전에는 채택된 정책이 아니다.

### (b) INDEPENDENTLY 승인해야 할 판단

- **F33·F34·F35 각각:** 환불/입금 확인/반환의 퇴사 후 식별 최소 범위, 실명 연결 필요성·기간·기산점·감사 접근자·예외 해제 사건. 같은 금융기간을 일괄 적용하지 않는다. F33 nullable과 F34/F35 required의 차이도 유지한다.
- **F36와 F37 각각:** 이름 표시/책임 실명과 이메일 인증/연락의 독립 목적·종료·접근권, 필수 name/email·unique와 양립할 최종 처리 및 계정 사본의 담당자. 고객 파기 승인이나 FK 보존 승인으로 계정 생애주기를 결정하지 않는다.
- **F50·F51·F53·F54·F57 각각:** 해당 본문에 대한 개인/공용 단위, 실제 필요한 예외, 사건 입증·기산점·기간·제거 범위·검토 책임자. 공통 redaction 방향의 배치 승인이 특정 본문의 일괄 NULL 허가는 아니다. SPEC 인용의 단위 미정합도 최종 정책에서 명시적으로 해소해야 한다.
- **F52:** 건강·아동 내용 근거/분리·접근, 유효 현장 안전정보 보전, 사고·분쟁 최소 증빙과 종료·사본 처리. 일반 메모와 일괄 승인 불가.
- **F55·F56 각각 및 F57의 강사 책임 내용:** 강사 실명에 의한 과거 책임·전화 연락·메모 목적의 차이, Teacher/User 간 별도 기간·권한·예외. F55 공통 표시와 F56 phone NULL을 서로 종속시키지 않는다. F56 방향은 approvable-direction이지만 기산·기간·연락 예외 확정은 독립이다.
- **모든 행의 실행 조건:** 실제 적용 근거, 필드 최소범위, 숫자 기간 또는 적법한 종료 규칙, 기산사건·만료경계, hold 해제/재검토 조건, 과거자료 근거, 사본·백업 최종 잔존과 복구 후 재파기 책임은 미결정이다. 필요한 답이 없는 행은 실행 승인으로 넘어가지 않는다.

### (c) 전문가 확인 — 도메인별

- **법률(E01/E02/E03/E07):** 거래·사고/분쟁·강사 계약/책임 기록별 실제 적용 법령·증빙 분류와 필수 신원 범위는 무엇인가? 금융 행·ID 보존과 실명/연락처 보존을 어디까지 분리할 수 있는가? E/T/C가 실제 적용되는 자료의 기간·정확한 기산점·예외 해제는 무엇인가(세무·장부 사항은 세무 전문가 포함)? 원장에 직원을 연결할 필요가 이메일이나 전체 공용 본문의 보존까지 요구하는가? 현재는 모두 **ESTIMATE / 미결정**이다.
- **노무(E07):** 직원과 위탁 강사 등 실제 종사자 지위·고용/계약 목적은 무엇인가? 퇴사/계약 종료, 인수인계, 계정 비활성화, 책임 확인 종료를 어떤 증거로 구별할 것인가? 각 이름·이메일·전화가 근무/계약상 필요한 범위·접근자·종료 조건은 무엇인가? 노무 관련 문서 보존 의무의 적용 자체와 기간도 **미결정**이며 새로운 연수나 근거 없는 퇴사일 기준을 만들지 않는다.
- **개인정보(E01/E04/E05/E06/E07):** 공용 필드 혼입이 확인될 때 아동·건강·제3자 정보의 적법 근거·최소 범위·내용별 제거 단위는 무엇인가? 직원 신원·강사 연락·건강정보에 누가 어떤 목적·종료 조건으로 접근해야 하는가? ChildSafetyInfo와 safetyMemo의 보호 경계, 자유입력의 간접식별·오삭제/누락, 잔존 FK·Teacher/User 상호 연결의 식별 가능성을 어떻게 평가할 것인가? 계정 이메일 사본·내보내기·백업·복구 후 재파기까지 확인할 책임·기한·증거는 무엇인가? 실제 값/설정 검토는 별도 허용 범위에서 수행해야 하며 이번에는 실행하지 않았다.
