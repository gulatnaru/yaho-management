# Requirement — 모바일 우선 화면 레이아웃 보완 SPEC

- 작성일: 2026-10-20
- 상태: 검토용 SPEC 보완. 화면 배치·문구·상태·전환을 설명하며 PLAN·구현 승인을 뜻하지 않는다.
- 기준: [통합 UX SPEC](UX-REDESIGN-INTEGRATED-SPEC.md)의 Business Rules 1~4·7~9 및 INT-01~30. 정책 근거는 [REQUIREMENTS.md](../REQUIREMENTS.md) 10.6·17·20·20-1·21-1·Phase 20과 [DECISIONS.md](DECISIONS.md) ADR-052~060이다.
- 표기: `[문구]`는 버튼, `〈문구〉`는 상태 배지, `□`는 미선택 입력, `{값}`은 실제 데이터 자리다. 예시 이름·금액·주소를 운영값으로 지정하지 않는다. 와이어프레임의 위→아래 순서가 모바일 정보 순서다.

## Problem

통합 SPEC의 세 여정을 작은 화면에서 검토할 수 있도록 카드 순서, 행동 문구와 상태별 차이를 구체화한다.

## Current Process

기존 링크 관리·보호자 폼·아이별 신청 목록의 분석은 통합 SPEC의 Current Process를 따른다. 이 문서는 목표 화면만 보완한다.

## User Story

ADMIN은 클래스 상세에서 링크를 준비·전달하고 가족 상세 한 화면에서 신청·실제 입금·확정을 처리한다. 보호자는 휴대폰에서 클래스를 확인하고 여러 자녀를 입력한 뒤 동의·최종 확인을 거쳐 제출한다.

## Scope

Screen A의 링크 영역, Screen B의 가족 목록·상세, Screen C의 세 입력 단계와 제출 결과 연결을 다룬다.

## Out of Scope

코드·DB·API·컴포넌트 설계·테스트 실행·배포 및 기존 확정 정책 변경. 입력 중 가격·잔여석 공개는 아래 사용자 결정 항목으로 분리하며, 기본 레이아웃은 기존 비공개 정책을 유지한다.

## Business Rules

### 공통 모바일 배치

- 360px·390px에서 한 열 카드와 세로 스크롤을 기본으로 한다. 768px 이상에서도 정보 순서·상태 의미는 같다. 가로 스크롤 표를 사용하지 않는다.
- 제목 → 현재 상태·안내 → 핵심 카드 → 주 행동 → 보조 행동 순서다. 카드 안의 여러 버튼도 모바일에서는 전체 폭으로 세로 배치한다. 누를 영역은 최소 44px을 목표로 한다.
- 긴 주소·프로그램명·오류는 카드 안에서 줄바꿈한다. 날짜 입력과 키보드가 화면을 밀거나 버튼·동의 본문을 가리지 않아야 한다.
- 상태는 색과 함께 이름·수치·시각을 표시한다. 펼침·진행 단계·필드 오류·처리 결과는 키보드와 보조기기로도 이해할 수 있어야 한다.
- 각 화면은 로딩·빈 상태·조회 실패·저장 중·저장 실패·완료를 구별한다. 실패를 `미발급`·`0건`·`완료`로 바꾸지 않는다.
- A·B는 ADMIN 전용이며 다른 역할에 카드·금액·건수·주소를 제공하지 않는다. C는 유효한 신청 링크 범위만 보여준다.

### Screen A: Admin Class Detail — 신청 링크 영역

#### 제목·정보 순서·기본 레이아웃

페이지 제목은 **클래스 상세**, 영역 제목은 **이 클래스 신청 링크**다. 클래스 기본 정보 바로 다음, 참가자 목록보다 앞에 배치한다.

```text
[클래스 목록으로]
클래스 상세
{프로그램명}
{날짜} · {시작–종료 시각} (한국 시간)
{장소}

이 클래스 신청 링크
링크 상태: 링크 활성
현재 환경: 운영
접수 조건: 접수 가능

┌ 링크 발급 카드 ─────────────────┐
│ 대상: 이 클래스 전용            │
│ 신청금액(관리자용): {지정액}원   │
│ [신청금액 설정]                 │
│ 준비: 입금 안내·동의 문구 준비됨 │
│ 발급: {시각} · {처리자}         │
│                                │
│ 발급 직후에만 아래 주소 표시    │
│ {현재 환경의 전체 신청 주소}     │
│ [복사]                         │
│ [공유]                         │
│ [보호자 화면 열어보기]          │
│                                │
│ 주소는 발급 직후에만 확인·복사할 │
│ 수 있습니다. 지금 복사해 주세요.│
└────────────────────────────────┘

[링크 재발급]
[신청 접수 중지]
[이 클래스 신청 보기]

[여러 클래스 통합 신청 링크 만들기]
이 클래스가 포함된 다른 링크
{전용 / 기존 주소 전환 / 통합 범위별 카드}
```

위 그림은 **발급 성공 직후**다. 최초 미발급이면 발급 이력·주소·주소 작업 대신 주 버튼 **[링크 발급]**을 둔다. 현재 클래스 하나의 발급에 그룹명 입력이나 클래스 재선택을 요구하지 않는다.

#### 상태별 표시·버튼

| 상태 | 표시 | 주 행동·보조 행동 |
|---|---|---|
| 미발급·준비 완료 | `미발급` | `[링크 발급]` |
| 새 방식 금액·설정 미비 | `신청금액 미설정` / `입금 안내 설정 필요` / `동의 문구 준비 필요` | `[신청금액 설정]` / `[입금 안내 설정]` 등 해결 행동. 발급 불가 이유를 바로 옆에 표시 |
| 링크 활성·발급 직후 원문 있음 | `링크 활성`과 발급 이력·전체 주소 | `[복사]` `[공유]` `[보호자 화면 열어보기]`; 재발급·중지는 보조 |
| 링크 활성·재방문으로 원문 없음 | `링크 활성`과 발급 이력. `유효한 링크가 있습니다. 주소는 발급할 때만 확인할 수 있습니다.` | 주소 작업을 제공하지 않고 `[링크 재발급]` 제공. 미발급으로 표시하지 않음 |
| ADMIN이 접수 중지 | `링크 비활성 · 접수 중지` | `[접수 재개 및 새 링크 발급]`. 이전 주소는 되살아나지 않음 |
| 클래스 취소·시작 시각 경과 | `클래스 상태로 신규 접수 불가` | 발급·재개 차단, `[이 클래스 신청 보기]` 유지 |
| 조회 실패 | `링크 정보를 불러오지 못했습니다.` | `[다시 불러오기]`. 발급 버튼으로 대체하지 않음 |
| 발급·재발급 중 / 실패 | `링크 발급 중…` / `링크를 발급하지 못했습니다.` | 중복 실행 방지. 실패한 작업만 `[다시 시도]`, 기존 상태·대상 보존 |

**해시 저장 안내:** 새 방식은 링크의 비밀값 원문을 저장하지 않고 **해시만 저장**한다. 원문 주소는 발급 응답을 받은 직후 현재 화면에서만 확인·복사·공유·열어보기가 가능하다. 재방문·새로고침·탭 종료 후에는 복원하지 못한다. 평문 주소를 브라우저 저장소·로그 등에 남겨 이 제한을 우회하지 않는다. 이미 복사해 둔 주소는 재발급·중지 전까지 유효하며, 원문을 화면에서 못 본다는 사실이 링크 비활성을 뜻하지 않는다. 기존 Phase 18 원문 보유 링크의 호환 범위는 별도 유지하며 자동 재발급하지 않는다.

`[복사]` 성공은 `신청 링크를 복사했습니다.`로 알린다. 실패하면 `복사하지 못했습니다. 주소를 길게 눌러 복사해 주세요.`와 선택 가능한 전체 주소를 유지한다. `[공유]`는 사용자가 공유 대상을 고르는 창을 열며 자동 발송하지 않는다. 공유 취소는 실패·접수 중지가 아니다. 공유 기능을 사용할 수 없으면 `공유 기능을 사용할 수 없습니다. 링크를 복사해 전달해 주세요.`와 `[복사]`를 제공한다. 어느 행동도 링크를 새로 만들거나 교체하지 않는다.

#### 운영·Preview 설명과 접수 중지 구분

환경 안내는 링크 상태 바로 아래에 항상 두고, 주소를 보여줄 때도 해당 주소의 환경을 함께 표시한다.

| 구분 | 쉬운 한국어 안내 | 행동·판정 |
|---|---|---|
| 운영(Production) | `보호자에게 안내할 실제 서비스 환경입니다. 링크와 접수 준비 상태를 확인한 뒤 전달해 주세요.` | 운영이라는 이유만으로 접수 가능을 보장하지 않음 |
| Preview | `변경한 화면을 미리 확인하는 테스트 환경입니다. 여기서는 일반 보호자 신청을 받지 않습니다. 실제 보호자에게 보낼 링크는 운영 환경에서 확인해 주세요.` | 현재 주소를 운영 주소로 바꾸거나 운영 상태를 추정하지 않음 |
| 허용된 Preview 합성 검증 | `합성 테스트 전용입니다. 허용된 테스트 범위에서만 확인할 수 있습니다.` | 기존 세션·lease 조건 유지. 실제 개인정보 입력을 유도하지 않음 |
| ADMIN 접수 중지 | `관리자가 이 링크의 신규 신청을 중지했습니다. 기존 신청과 예약은 유지됩니다.` | 실제 업무상 중지. 재개는 명시적인 새 링크 발급 |

Preview 제한은 **현재 테스트 환경의 접근 제한**, 접수 중지는 **ADMIN이 실행한 링크의 업무 상태**다. 둘은 독립적으로 표시한다. `링크 활성 + Preview 일반 신청 제한`도 가능하고 `접수 중지 + Preview 일반 신청 제한`도 가능하다. Preview라는 이유로 중지 상태를 기록하거나 접수 재개를 권하지 않는다. `[보호자 화면 열어보기]`도 일반 공개 제한을 우회하지 않는다.

#### 재발급·중지 확인창과 화면 전환

```text
링크를 재발급할까요?
기존 링크가 무효화됩니다
대상: {이 클래스 / 통합 링크에 포함된 클래스 목록}
기존 주소로는 새 신청을 받을 수 없습니다.
이미 접수된 신청은 유지됩니다.
공유한 곳에 새 주소를 다시 안내해 주세요.

[취소]
[기존 링크를 무효화하고 재발급]
```

- `[링크 발급]` → 같은 카드에 발급 결과·주소·`[복사]`·`[공유]`. 자동 복사·공유는 하지 않는다.
- `[링크 재발급]` → 위 확인창 → 실행 성공 후 같은 카드에 새 주소. `[취소]`는 기존 주소와 상태를 보존한다.
- `[신청 접수 중지]` → `이 링크의 신규 신청을 중지합니다. 이미 접수된 신청은 유지됩니다.`와 대상 범위를 표시 → `[취소]` / `[신청 접수 중지]` → 같은 카드의 중지 상태.
- `[접수 재개 및 새 링크 발급]` → `새 주소로 접수를 재개합니다. 이전 주소는 사용할 수 없습니다.` 확인 → `[취소]` / `[새 링크로 접수 재개]` → 새 주소 표시.
- `[보호자 화면 열어보기]` → 현재 주소의 공개 화면을 새 탭에서 읽기. `[이 클래스 신청 보기]` → Screen B의 클래스 필터가 적용된 목록. 뒤로 돌아오면 클래스 문맥을 유지한다.
- 여러 링크는 각각의 범위·상태·발급 이력을 보인다. 통합 링크의 재발급·중지는 포함된 모든 클래스에 영향을 준다고 확인창에 명시하고, 독립된 다른 링크는 유지한다. 기존 주소를 유지하는 명시 전환과 재발급을 같은 버튼으로 합치지 않는다.

### Screen B: Admin Application List / Detail — 가족 단위 신청 처리

#### 목록 제목·정보 순서·모바일 카드

제목은 **예약 신청**이다. 제목 → 가족/아이 건수 → 필터 → 가족 카드 → 페이지 이동 순서로 배치한다. 기본 필터는 `처리 대기`다.

```text
예약 신청
대기 {N}가족 · 아이 신청 {M}건
[필터 열기]
적용 중: 처리 대기 · {클래스 또는 전체}

┌ 가족 신청 카드 ────────────────┐
│ 보호자 {이름} · 자녀 {N}명      │
│ {접수 일시}                    │
│ {자녀 이름 요약}               │
│ {클래스·일시 요약}             │
│ 신청 당시 총 청구액 {합계}원    │
│                               │
│ 입금 알림: 〈알림 받음 · 시각〉 │
│ 실제 입금: 〈은행 확인 {D}원〉  │
│ 예약에 쓸 수 있는 금액 {A}원   │
│ 예약 확정: 〈확정 {n}/{N}명〉   │
│ 처리 대기 {m}명 · 반려/취소 {k}명│
│ 반환: {필요/일부 반환/완료 요약}│
│                               │
│ [자녀 {N}명 펼치기]            │
│ [신청 확인하기]                │
└───────────────────────────────┘
{다음 가족 카드}
[이전 페이지]
[다음 페이지]
```

카드의 자녀 펼침은 아이별 이름 → 클래스·일시 → 신청 당시 고정 금액 → 처리 상태 순서이며, 버튼은 **[자녀 접기]**로 바뀐다. 연락처·생년월일·요청사항·동의 원문은 상세에서만 보여준다. 펼침과 `[신청 확인하기]`는 독립 버튼이다. 목록에서 입금 기록·확정을 실행하지 않는다.

한 카드는 한 제출이며 같은 가족 제출의 자녀를 페이지 사이에 나누지 않는다. 연락처가 같은 별도 제출이나 친구 가족을 병합하지 않는다. 클래스 필터가 있어도 입금액은 **가족 제출 전체 기준**임을 표시하고 해당 클래스의 자녀를 구별한다. 기존 신청은 `기존 방식 · 아이 1명 신청`, 금액은 `금액 미기록`으로 표시하며 0원으로 바꾸지 않는다.

#### 독립적인 세 상태 배지

| 축 | 정확한 표시 예 | 해석 |
|---|---|---|
| 보호자 입금 알림 | `알림 없음` / `알림 받음 · {시각}` | 보호자의 진술. 없음=미입금, 있음=은행 확인으로 판단하지 않음 |
| 실제 입금 | `은행 확인 기록 없음` / `은행 확인 입금 누계 {D}원` | ADMIN이 기록한 실제 거래. 가용액·선택 부족액은 별도 표시 |
| 예약 확정 | `예약 확정 {n}/{N}명`와 `처리 대기 {m}명`·반려·취소 수 | 아이별 결과. 일부 확정인 가족을 전체 확정으로 표시하지 않음 |

`입금 완료` 하나로 세 상태를 합치지 않는다. 보호자 알림이 없어도 실제 입금 기록과 기존 조건이 충족되면 확정할 수 있다.

#### 입금·초과액·선택 일괄 확정의 상태와 전환

- **입금 저장:** 실제 거래를 확인하고 `[입금 기록 저장]` → `입금 기록 저장 중…` → `입금 기록을 저장했습니다.`. 같은 화면의 거래 카드·세 상태·원장·선택 합계·부족액을 최신 값으로 갱신한다. 확정 영역 이동에 수동 새로고침이 필요 없어야 한다. 저장만으로 예약이 생성되지 않는다.
- **입력 오류:** 실제액·입금자명·일시 각각의 바로 아래에 오류를 표시하고 입력을 유지한다. 보호자 입력 입금자명과 은행 입금자명은 별도 표시하며 다르다는 이유로 자동 확정·거절하지 않는다. 부분·추가·초과입금을 실제액 그대로 거래별 누적한다.
- **원장:** 확인 입금 누계 D = 가용액 A + 예약 배정액 P + 반환 필요 잔액 R + 반환 완료액 T. 부족액은 선택 청구액 S와 A를 비교한 `max(0, S−A)`다. 총 입금액과 원래 가족 총 청구액만 비교해 확정 가능을 판단하지 않는다.
- **초과입금:** `초과입금 반환 필요 {금액}원`을 별도 줄로 보여준다. 선택하지 않은 형제의 청구액을 곧바로 초과입금으로 간주하지 않는다. 반환 필요·일부 반환·반환 완료와 잔액은 기존 원장 값을 따르며, 이미 배정·반환한 금액은 재사용하지 않는다. 초과액을 확정 결제나 매출에 더하지 않는다.
- **반환 기록:** `[반환 내역 펼치기]`는 거래 카드를 연다. `[반환 이체 기록]`은 실제 이체한 금액·일시·사유 기록으로 이어지며 송금을 실행하지 않는다. 예약 확정 후 환불은 기존 예약·결제·환불 흐름으로 연결한다.
- **미선택·부족·검증 필요:** 아이를 자동 선택하지 않는다. `확정할 아이를 선택해 주세요.` / `예약 확정에 {부족액}원이 부족합니다.` 등 이유를 버튼 옆에 표시한다. 중복·아이 연결 미완료·비활성/파기·클래스 상태 등 기존 확정 조건도 충족해야 한다.
- **일괄 확정:** `[선택한 아이 {n}명 예약 확정]` → `선택한 아이 {n}명 예약 확정 중…` → 같은 화면에서 아이별 결과와 실제 예약·연결 결제를 표시한다. 한 번의 선택 처리는 전부 성공 또는 전부 실패하며 미선택 형제는 그대로다. 초과 예약은 기존 ADMIN 명시 확인을 거치고 대상 변경 시 다시 확인한다.
- **실패·경합:** 실패한 아이·조건과 수정할 위치를 알려주고 안전한 입력·선택을 보존한다. 최신 원장을 다시 보여주며 결과가 불명확한 금융 작업·확정을 자동 반복하지 않는다. 성공한 예약에 중복 결제 등록을 유도하지 않는다.
- **목록 복귀:** `[목록으로 돌아가기]` → 기존 필터·페이지·스크롤 위치. 클래스 상세에서 시작했다면 클래스 문맥도 유지한다. 기존 아이 상세 URL 진입은 해당 가족 상세의 대상 아이로 연결한다.

기존 Phase 18 신청은 같은 순서로 검토하되 **금액 없는 입금 확인 기록과 확정 후 별도 수동 결제**를 유지한다. 새 방식의 원장·금액을 과거 신청에 소급 적용하지 않는다.

#### 목록·상세의 빈 상태·오류

최초 0건은 `접수된 신청이 없습니다.`와 링크 관리 안내, 필터 0건은 `조건에 맞는 신청이 없습니다.`와 **[필터 초기화]**를 표시한다. 조회 실패는 `신청을 불러오지 못했습니다.`와 **[다시 불러오기]**를 둔다. 처리 중에는 해당 작업의 중복 실행을 막고 다른 상태를 완료로 표시하지 않는다.

### Screen C: Guardian 3-Step Application — 모바일 신청

#### 제목·공통 상태·진행 표시·금액 영역

제목은 **클래스 신청**이다. 세 입력 단계는 정확히 **클래스 선택 → 보호자·자녀 정보 → 동의·최종 확인**이다. 제출 완료·입금 안내는 별도 결과 화면이며 네 번째 입력 단계가 아니다.

각 단계는 제목 → `3단계 중 {현재}단계`와 단계 이름 → `신청은 예약 확정이 아닙니다.` → 현재 단계 내용 → 신청 요약 → 주/보조 버튼 순서다. 360px에서는 단계 이름을 세로 목록으로 배치해 가로 탐색을 요구하지 않는다. 완료한 단계는 **[클래스 수정]**, **[보호자·자녀 정보 수정]**으로 돌아갈 수 있다.

**금액 표시 — USER DECISION ITEM (Q-PRICE):** 입력 중 실시간 총액 표시는 현재 승인된 동작이 아니다. Phase 20·통합 SPEC의 **1~3단계 가격 비공개**를 유지한다. 각 단계 하단의 계속 갱신되는 요약에는 `선택한 클래스 {K}개 · 신청 자녀 {N}명`과 **`정확한 입금액과 계좌는 신청 완료 후 안내합니다.`**를 표시한다. 아직 아이를 입력하지 않은 1단계는 `자녀 정보는 다음 단계에서 입력합니다.`로 안내한다. 금액을 0원·추정가로 대신하거나 숨긴 금액을 공개 응답에 포함하지 않는다.

요청된 running total amount의 배치 위치는 **이 하단 신청 요약 영역**이다. 입력 단계 공개를 사용자가 별도 결정한 경우에만 이 위치의 `총 신청금액 {합계}원` 안을 검토한다. 지금의 기본 와이어프레임에는 숫자 금액이 없다. 실제 고정 금액 합계는 유효한 자기 완료 권한이 있는 제출 결과에서만 표시한다.

```text
{추가 자녀: 이름·클래스·입력 상태 요약 카드}
[내 자녀 추가]

신청 요약
선택한 클래스 {K}개 · 신청 자녀 {N}명
정확한 입금액과 계좌는 신청 완료 후 안내합니다.
[다음]
[이전]
```

- 아이와의 관계는 기존 값 `부 / 모 / 기타 법정대리인`을 유지한다. `입금할 때 사용할 이름`은 새 방식에서만 받는다. 각 자녀는 후보 중 정확히 한 클래스에 연결하며, 단일 클래스는 이미 정해진 대상을 표시한다.
- `[내 자녀 추가]` → 새 자녀 카드를 펼치고 이름 입력으로 이동한다. 보호자·다른 자녀·클래스·동의 입력은 유지한다. 새 방식은 1~10명이며 10명일 때 `자녀는 최대 10명까지 신청할 수 있습니다.`로 이유를 표시한다. 기존 금액 없는 Phase 18은 자녀 1명 흐름을 유지한다.
- `[자녀 정보 접기]` → `자녀 {번호} · {이름 또는 입력 필요} · {클래스} · {입력 완료/입력 필요}` 요약. **[아이 정보 수정]**으로 다시 펼친다. 추가 자녀의 **[이 아이를 신청에서 제외]**는 대상 이름·클래스를 확인하고 초안에서만 제외한다. 마지막 자녀는 제외할 수 없다.
- Step 1에서 후보를 제거해도 아이를 다른 클래스로 자동 변경하지 않는다. 해당 카드에 `이 아이의 클래스를 다시 선택해 주세요.`를 표시한다. 유효한 같은 기기 재신청은 기존 자기 자녀 범위만 이용하며 과거 동의를 자동 적용하지 않는다.
- 연락처는 전화 키패드를 사용하고 날짜는 카드 폭 안에 둔다. `[다음]` → 유효한 필수 입력이면 Step 3, `[이전]` → 값 유지 후 Step 1. 추가·접기·단계 이동은 제출이 아니다.

#### Step 3 — 동의·최종 확인

```text
클래스 신청
3단계 중 3단계 · 동의·최종 확인
① 클래스 선택 — 입력 완료
② 보호자·자녀 정보 — 입력 완료
③ 동의·최종 확인 — 현재

보호자 {이름} · 신청 자녀 {N}명

{아이별 입력 정보·클래스·일시·장소·요청사항}

□ (필수) 프로그램 안전 및 이용사항 확인
□ (필수) 개인정보 수집·이용 동의
□ (필수) 법정대리인 확인
□ (필수) 취소 및 환불규정 확인
{각 항목의 [내용 보기] · 문구 버전}

선택 동의
동의하지 않아도 참가에 제한이 없습니다.
{아이 1 이름} · {클래스}
□ (선택) 활동 사진·영상 촬영 및 참여 보호자 공유

{각 항목의 [내용 보기] · 문구 버전}
{다음 아이도 독립적인 선택 항목 2개}
{아이별 선택 결과: 동의 / 미동의}

선택한 클래스 {K}개 · 신청 자녀 {N}명
정확한 입금액과 계좌는 신청 완료 후 안내합니다.
신청은 예약 확정이 아닙니다.
입금과 운영자 확인 후 예약이 확정됩니다.
```

필수 4개와 선택 2개는 다른 구역이며 기본 미선택이다. `[내용 보기]` / `[내용 접기]`로 기존 원문·현재 버전을 읽는다. 필수·선택 전체 동의는 두지 않는다. 공통 필수 입력의 적용 대상과 아이별 저장은 유지하고, 새 자녀 추가 시 기존 확인을 몰래 적용하지 않는다. 선택 동의는 아이마다 다르게 선택할 수 있으며 미동의를 오류로 표시하지 않는다.

`[클래스 수정]` → Step 1, `[보호자·자녀 정보 수정]` / `[이전]` → Step 2. 수정 후 요약·적용 아이·동의 결과를 갱신하고 다른 입력은 유지한다. `[신청서 제출]`만 최종 제출이며 처리 중 **신청서 제출 중…**, 성공 후 **완료 화면으로 이동 중…**으로 바꾼다. 다자녀는 모두 접수되거나 모두 실패한다.

#### 필드 오류·입력 보존·접근 상태

| 상황 | 화면 표시·이동 | 보존 |
|---|---|---|
| 보호자 필수/형식 오류 | 필드 바로 아래 `보호자 이름을 입력해 주세요.` / `연락처를 확인해 주세요.` | 보호자·모든 자녀·클래스 선택 유지 |
| 자녀 오류 | 해당 자녀 카드를 펼쳐 이름 아래 `아이 이름을 입력해 주세요.`, 날짜 아래 `올바른 생년월일을 입력해 주세요.` 등 표시 | 다른 자녀·현재 정상 입력 유지 |
| 필수 동의 누락 | 해당 항목 아래 `필수 항목을 확인해 주세요.`와 적용 아이 표시 | 다른 필수 확인·아이별 선택 동의 유지 |
| 서버가 이전 단계 오류 반환 | 상단 `입력 내용을 확인해 주세요.`와 `[2단계 자녀 {번호}의 생년월일 수정]` 같은 오류별 이동 버튼. 해당 단계·카드를 열어 첫 오류로 이동 | 오류 요약만 보여주거나 전체 초기화하지 않음 |
| 통신 실패·결과 불명 | `처리 결과를 확인하지 못했습니다. 잠시 후 다시 확인해 주세요.`. 자동 성공·재제출 금지 | 폼을 계속 보여줄 수 있는 경우 현재 입력·동의 유지 |
| 중지·무효·허용 범위 소멸 | `현재 신청을 받지 않는 링크입니다.` | 내부 사유·클래스 존재를 노출하지 않고 더 이상 권한 없는 폼/정보를 표시하지 않음 |
| 조회 중·조회 실패 | `신청 정보를 불러오는 중입니다.` / `신청 정보를 불러오지 못했습니다.`와 `[다시 불러오기]` | 실패를 선택 가능한 클래스 0개로 표현하지 않음 |

오류는 각 입력과 연결하고 색 외 텍스트로 알린다. 단계 이동·유효한 현재 폼의 검증 실패에는 입력을 보존하지만 새로고침·탭 종료 후 복원을 약속하지 않는다. 개인정보·동의·입금자명을 URL·브라우저 저장소·로그에 저장하지 않으며, 제출 성공 후 뒤로가기·새로고침에서 이전 개인정보 폼이나 재제출을 되살리지 않는다.

#### 제출 후 결과 화면으로의 연결

```text
신청이 접수되었습니다
아직 예약이 확정된 것은 아닙니다.
안내 금액 송금 → 입금 알림 → 운영자 확인 후 예약 확정

{아이별 제출 당시 고정 신청금액}
총 입금액 {합계}원
{은행·계좌번호·예금주·입금자명}
[계좌번호 복사]
[입금액 복사]
[입금자명 복사]
[입금했어요]
```

이는 **새 방식의 유효한 자기 완료 권한**에서만 보이는 송금 안내다. 현재 클래스 가격으로 다시 계산하지 않는다. `[입금했어요]`는 `송금을 마친 뒤 눌러주세요. 실제 입금 확인이나 예약 확정을 대신하지 않습니다.`와 함께 표시한다. 누른 후 `입금 알림을 보냈습니다. 운영자 확인을 기다려 주세요.`로 알리며 실제 입금·예약·매출 상태를 바꾸지 않는다. 기존 Phase 18 완료 안내와 권한 만료 시 허용 정보 범위는 그대로 유지한다.

## Open Questions

- **Q-PRICE — USER DECISION ITEM:** 입력 중 총 신청금액을 표시하도록 Phase 20 비공개 정책을 변경할 것인가? **현재 문서의 기본값은 변경 없음**이다. 승인 전에는 모든 입력 단계의 가격을 숨기며, 공개하기로 결정할 경우 범위·표시 시점·합계 의미를 별도 확정한다.
- **Q-SEATS — 사용자 결정 항목:** 요청한 잔여석 표시를 위해 기존 공개 금지 정책을 변경할 것인가? **현재 문서의 기본값은 변경 없음**이다. 카드 안의 위치만 제시하며 숫자·만석·예약 가능 표시는 승인 전 공개하지 않는다.

두 항목은 이 문서에서 임의 확정하지 않는다. 이 보완 SPEC 작성은 완료할 수 있으나, 정책을 바꾸는 후속 구현으로 진행하는 근거가 되지 않는다. 확정 결정은 별도 공식 문서·ADR 절차로 반영한다.
