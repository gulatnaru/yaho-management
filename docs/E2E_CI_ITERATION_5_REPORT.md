### Source evidence and mechanism boundary

All three existing product paths require a client route Flight transition to commit before the relevant authoritative UI can change. The CI facts establish successful HTTP headers and correct fresh server state alongside a live route transition that does not commit. The following source dependencies are directly demonstrated; they do **not** prove the initiating cause of the interrupted Flight stream:

- Price: `ApplicationPriceForm` awaited the successful mutation, updated its own draft revision/saved notice, then called `router.refresh()` inside the same async transition. `ApplicationLinkCard` rendered its price exclusively from `view.applicationPrice`; it had no success-to-card data handoff. Thus a successful save notice could coexist indefinitely with an old card price and pending refresh. The unchanged price action already calls `revalidatePath` for the class and group layout.
- Issuance: `MultiClassLinkComposer` delivered a receipt to `GroupCreateForm`/the class card, then called `router.refresh()`. The group form required the receipt link ID in its server `activeLinkIds` prop; the card required an active scope, current-class membership and an active matching link ID. A newly issued receipt cannot satisfy those old props. This explains the demonstrated receipt-visible/address-absent combination without inventing a DB issuance failure. Removing those gates would expose stale addresses, so the fix retains them and supplies a separate authoritative projection.
- Filter clear: the clear control was a Next `Link` inside the native GET filter form. Installed Next `dist/client/app-dir/link.js` calls `preventDefault()` and dispatches client navigation. That matches the established hydrated, unobstructed real-click/defaultPrevented/one-RSC-request/noncommitted-URL evidence. A native anchor uses the same generated destination through normal browser navigation, so this control no longer depends on the failed client route transition. Merely being inside a form is **not** independently proven to cause the stream interruption.

Installed Next **15.5.23** source supports this boundary: `router-reducer/reducers/refresh-reducer.js:35–45,89–98` waits for `fetchServerResponse` and inactive-segment reads before applying its new cache; `router-reducer/fetch-server-response.js:105,139` receives headers before decoding Flight. `app-router-instance.js:131–134` discards a pending action for NAVIGATE/RESTORE, while ordinary refresh actions queue; therefore a cancellation race cannot be inferred merely from multiple refresh callers. The fetch module's explicit AbortController cancellation is on `pagehide` (`fetch-server-response.js:54`); no relevant admin-page effect establishes such an event. The original stream termination's initiator remains **unresolved** here; no browser/DB reproduction or cancellation-cause claim is made.

The new projection actions perform reads without `revalidatePath`. Installed Next `server/app-render/action-handler.js:773,857` uses `skipFlight: !workStore.pathWasRevalidated || actionWasForwarded`, so these reads return ordinary action data without requesting a refreshed route tree. The regression harness holds original server props fixed and makes `router.refresh` never resolve: it proves the repaired product handoff and gates, not the browser's original transport failure.

### Classification and unchanged verification contract

The observer now retains HTTP status **per Request**. A `requestfailed` event is classified as numeric **`abortedAfterResponse`** only when that same request already produced HTTP **200**. The original numeric **`failed`** counter still records it. Numeric **`lostResponses`** counts requests lacking observed HTTP 200, plus failures that occurred before a successful response. A later response cannot retroactively reclassify an earlier failure. A successful response for one request cannot mask another request's missing/non-200 response. ### New install sequence and failure ownership

The original install block, immediately after Prisma generate and before Verify PostgreSQL, becomes:

1. **Install browser binaries (no APT)**: `npx playwright install chromium` for desktop Chromium; `npx playwright install chromium webkit` for every WebKit project. There is no `--with-deps`. Its **10-minute** timeout/failure belongs to the clearly named browser-binary download step.
2. **Smoke check required browser engines**, ID `browser-smoke`: run `node --import tsx scripts/ci/playwright-browser-smoke.ts`, with **3 minutes** and `continue-on-error: true`. From `UX_PROJECT`, the script actually launches Chromium alone for desktop or Chromium plus WebKit otherwise. For each engine it creates a context and page, closes the page/context/browser, then prints `SMOKE_OK <engine>`. Launch or lifecycle errors print `SMOKE_FAIL <engine>` with details. A failed engine does not prevent checking the next engine; any failure makes the process exit nonzero. Each launch has a **30-second** timeout, with browser/context cleanup in `finally` blocks.
3. **Install system dependencies after failed browser smoke**: only `if: steps.browser-smoke.outcome == 'failure'`, run the official `npx playwright install --with-deps` command with the same engine split and a separate **10-minute** timeout. An APT timeout/failure fails this explicitly named system-dependency step. There are no wrapper retries or ignored dependency-install failures.
4. **Recheck required browser engines after system dependencies**: the identical smoke command, the same failure condition and **3-minute** timeout, without `continue-on-error`. After a successful fallback installation, engines that still cannot launch fail the job here with their smoke output.

**Fast path:** if the GitHub-hosted runner image already provides the required system libraries, the first smoke passes, steps 3–4 are skipped and no APT download occurs. **Fallback path:** an initial launch failure is recorded while allowing the dependency step to run; its condition uses the original smoke **outcome**, which remains `failure` despite `continue-on-error`. Dependency installation must succeed before the final smoke can validate launchability. Slow or failing APT remains a visible infrastructure failure within its original 10-minute bound; this change does not promise to accelerate APT when fallback is genuinely needed.

Only official Playwright installation and GitHub-hosted runners are used. Chromium remains required for the unchanged auth harness in every project; WebKit remains the WebKit projects' test engine.
