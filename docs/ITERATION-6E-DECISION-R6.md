## Problem

27항목의 목적 종료 방향, 기간·기산점, 공유 단위, 법정 증빙, 재시도·복구 조건이 서로 다른 수준에서 미결정이다. 운영자는 지금 선택할 수 있는 방향과 전문가·운영 사실을 먼저 확보해야 하는 결정을 구별해야 한다. 일부 방향의 승인이나 원장 보존을 필드 전체의 보관기간·파기 허가로 확대하면 안 된다.

## User Story

운영자로서 기존 승인 범위를 유지하면서 각 결정 ID의 선택·제외·보류 이유와 필요한 전문가 근거를 기록하고, 승인 뒤 어떤 후속 계획을 확정할 수 있는지 알고 싶다.

## Scope

F01–F05/F07 6항목, F33–F37 5항목, F50–F57 8항목, K01–K04 4항목, G1–G4 4항목을 **하나의 27행 승인표**로 통합한다. G4는 목적 혼합 overlay이며 별도 고객 수로 합산하지 않는다. R5의 조건부 권고 유지 19항목·보완 대상 8항목(F02/F04/F05/F07/K03/K04/G3/G4)을 그대로 추적한다. R5 M01–M06은 아직 채택되지 않은 보완안이다.

## Out of Scope

다른 파일 수정·기존 문서 덮어쓰기, REQUIREMENTS/ADR 갱신, 코드/테스트/설계 구현, stage/commit/push·CI·lint·build·앱 테스트 실행, 모든 DB 접근·실제 개인정보/백업 조회·삭제, migration·scheduler. 금액·환불 정책·수집항목·새 원문/hash/역매핑도 결정하지 않는다. 로컬 Memory는 보조 문맥으로만 읽었고, `agent-memory-repo` 스킬은 설치·프로젝트·Memory 경로에서 찾지 못했다. Memory 수정은 없다.

## Business Rules

### 분류와 집계 기준

**A/B/C는 승인 상태의 분류이고, 금융 A층/개인정보 B층과 관계없다.** 본표의 구분은 각 항목에서 **이번에 남은 결정**을 기준으로 하나만 부여한다. 승인된 일부 원칙을 가진 항목도 전체 새 종료 정책이 확정되지 않았다면 A행으로 올리지 않는다. 이미 승인된 부분은 아래 A에서 한정 확인하고 각 행에도 표시한다. C01–C08은 여러 행에 걸친 입력·검증 gate이므로 27항목에 추가 합산하지 않는다.

- **A. 기존 승인 범위 내 확정 사항:** 아래 기존 경계와 R1 여섯 방향만 재확인한다. **본표의 남은 결정 전체가 기승인인 행은 0개**다. 이는 기존 승인이 없다는 뜻이 아니다.
- **B. 이번 사용자 승인 대기 사항:** 운영자가 지금 방향을 선택할 수 있는 **9개**다. 행별 “운영자 승인 필요 사항”이 선택 문구다. 방향을 승인해도 C의 기간·법적 근거·단위·운영 gate는 해소되지 않는다.
- **C. 법률·운영 근거 부족으로 보류할 사항:** 추가로 판단할 핵심이 전문가 근거·계정 정책·사건 증명·S 통합 조건 등에 있어 **18개**를 보류한다. 아래 C01–C08과 각 행에 해소할 사람·사실을 명시한다. B행의 미확정 실행 조건도 C gate로 남는다.

상태는 구분과 별개다. **구현 가능**은 해당 새 정책의 근거·기간/적법 종료 규칙·기산·단위·예외가 확정되어 후속 설계 대상으로 삼을 수 있다는 뜻이며 실행 허가가 아니다. **전문가 검토 필요**는 검토 의뢰할 범위가 정해져 있으나 필수 판단이 없다. **보류**는 사건·계정 처리·공유 단위·S/재시도 등 계약 자체도 미정인 상태다. 전문가 검토 필요 역시 구현에 진입할 수 없다. 현재 집계는 **구현 가능 0 / 전문가 검토 필요 15 / 보류 12**다.

### A. 기존 승인 범위 내 확정 사항 — 이번에 다시 승인받지 않는 부분

- **R1 여섯 방향:** 현재 사용자 요청이 기승인으로 한정해 인계한 범위만 따른다. F01 결제 대사 완료→이름 NULL, F02 대사·해당 문의 종결→메모 NULL 방향, F03 환불 완료·실제 분쟁 종결→상세 NULL, F04 실제 입금자 대사 완료→이름 NULL, F05 반환 이행·관련 실제 분쟁 종결→사유 NULL, F07 선언명·실제 입금 대사 완료→선언명 NULL이다. 실제 법정 필요가 확인될 때만 필요한 최소 범위를 분리·제한 보관하는 **조건부 예외 원칙**도 이 한정 범위다([R1 승인 방향 목록](ITERATION-6E-DECISION-R1.md#L30)). **기간·기산점·예외 해제일·S 선후·K04 계약은 이 승인에 포함되지 않는다.** R1–R5의 “승인 대기” 원문을 소급 수정하지 않으며, 그 문서의 작성 자체를 승인 증거로 쓰지 않는다.
- **기존 C5/A1/S:** 위 Current Process의 대상·기간·기산·KST 경계·상태·수동 실행·파기 범위만 유지한다. 특히 S의 현행 제거가 필드별 별도 기간 승인이나 새로운 보존 예외의 승인은 아니다. F02의 공유 본문 단위 보완, F04/F05/F07의 S 선후, K03 부분 파기, G3/G4 새 예외는 모두 B/C로 남는다([R5 M01–M06](ITERATION-6E-DECISION-R5.md#L163)).
- **기존 금융·책임 구조:** 원장 행·금액·일시·상태·FK·처리자·배정·환불/반환 누계를 유지한다. `D = A + P + R + T`에서 D=확인 입금, A=미배정 가용액, P=Payment 배정액, R=반환 필요 잔액, T=완료 반환액이다. 이 A는 A분류나 A층이 아니다. 원장 보존은 그 원장에 연결된 실명·이메일·자유입력·토큰 전체의 기간 승인이 아니다([ADR-060:549](DECISIONS.md#L549), [SPEC BR1](ITERATION-6E-SPEC.md#br1-금융행위와-개인정보-필드는-다른-보관-층이다)).
- **기존 안전·동의·권한:** 안전정보 분리·목록 제외, 동의 append-only와 기존 C5 만료 예외, ADMIN 재무/계정 경계를 유지한다. 고객 파기로 User/ADMIN 계정 삭제나 비CONFIRMED Consent/Safety의 새 삭제 예외를 승인하지 않는다([REQUIREMENTS 19–20-1](../REQUIREMENTS.md#L801), [ADR-006/008](DECISIONS.md#L65), [ADR-050](DECISIONS.md#adr-050-phase-16은-adminmanagerteacher-3단계-역할과-manager의-재무계정-경계를-사용한다)).

### 표 공통 해석 — B/C를 A로 바꾸지 않는 조건

`P/H/E/T/C`는 [SPEC BR2](ITERATION-6E-SPEC.md#br2-근거-표기와-법률-검토)의 개인정보·아동/건강·전자상거래·세무·상업장부 **검토 후보**다. `L`은 실제 적용되는 증빙 분류의 기간·기산점으로 **ESTIMATE / 미결정**이다. 이 문서는 법령의 현재 적용·개별 적법성을 새로 검증한 법률 의견이 아니다. SPEC의 숫자 후보도 여기서 채택하지 않으며 새로운 기간 숫자를 제안하지 않는다. 기존 C5/A1을 다른 필드·집단·계정·capability에 전용하지 않는다.

모든 행은 C06의 사본·복구, C07의 당시 고지·적법 근거, C08의 기존 범위·후속 검증을 적용한다. 목적 종료 사건 후보는 법정 기산점이나 실행 가능한 만료일이 아니다. `updatedAt`, 등록일·퇴사일·거래일로 없는 종료 사실·신고기한·장부 폐쇄일을 추정하지 않는다. 예외/hold에는 실제 근거·최소 필드/사본·접근자·해제 사건·재검토일·담당자가 필요하며 포괄 무기한 보존을 채택하지 않는다. NULL/공통 표시/hash만으로 법률상 익명정보·전 사본 파기 완료라고 하지 않는다. 실제 개인 내용의 혼입·대상 수·사건 발생은 조사하지 않았다.

### 승인 기록 방법 — 응답 전에는 빈 상태

운영자는 **결정 ID별로** 선택/보류/제외, 선택한 정확한 문구와 범위, 결정자 역할·결정일, 전문가 확인 출처·결론·미확인 부분을 기록한다. 배치 선택도 구성 ID마다 남긴다. 현재는 B 9건 모두 **미응답**, C 18건 모두 **근거/결정 미완료**이며 자동 체크된 승인이나 추정 답은 없다. A의 기존 승인 확인을 새 행 승인으로 재집계하지 않는다.

기간·기산·예외가 필요한 결정에는 필드/사본별 최소 범위, 숫자 기간 또는 적법한 종료 규칙, 입증할 기산사건·timezone/만료경계, hold 발생·해제 증거/재검토일/담당자, 과거자료·고지/거부 처리, 사본 최종 잔존·복구 책임을 함께 기록해야 한다. 그 답이 없으면 방향만 선택된 것으로 남기고 실행 조건은 C에서 보류한다. 운영자 선호는 전문가의 법정 적용 확인을 대체하지 않는다.

- **C07 / X07 — 당시 고지·아동/제3자·과거자료:** 개인정보·법률/노무 전문가(E01/E04/E07/E08)와 운영자는 당시 항목·목적·기간·정보주체/대리권·동의 또는 다른 적법 근거와 새 정책의 차이를 확인해야 한다. 특히 F07/F04의 직접 열거 간극, 건강 자유입력·비상연락자·직원/강사, G1 출처 미상·G2 과거자료가 대상이다. **부족 입력:** 누구에게 어떤 문구를 언제 고지/변경 동의/별도 민감 동의할지, 거부·미응답·연락불가 처리·과거자료 정리 근거. 일반 신청 동의/“거래는 법령 보존” 문구만으로 추가 원문/목적을 정당화하지 않는다. 새 version은 미래 제시에만 쓰고 과거 consentVersion UPDATE·소급 동의 가정·민감정보 자동 이관 금지. 근거 확보 전 해당 새 적용 차단.
- **C08 / X08 — 확인된 기존 경계·scope 기록 및 후속 검증:** 운영자는 승인할 Entity/필드/집단·명시 scope와 기존 C5/A1/금융 범위 비변경을 기록해야 한다. 후속 PLAN/금융·동시성 검토는 `D=A+P+R+T`, 환불 상한·누계/status·PaymentItem 매출, 원장/actor FK·키, **Payment→PaymentItem**, **Submission→Application→Child**, **Submission→ReturnObligation** 순서와 잠금 후 재판정을 유지하는지 확인해야 한다([환불:114](../lib/payments/core.ts#L114), [파기 잠금:237](../server/reservation-applications/retention.ts#L237), [bounded scope:280](../server/reservation-applications/retention.ts#L280), [반환:421](../server/reservation-applications/finance.ts#L421)). 최초 item 탐색은 잠금 획득이 아니다. 명시 scope에서 빠진 category는 빈 목록이며 전체 sweep으로 승격하지 않는다. **필요 기록/검증:** 공유 행·형제·빈/누락 scope·기존 파기 범위와 경합의 후속 합성 회귀 범위. 기존 불변식·잠금·CTE/purge scope 변경을 원하면 이번 승인에서 제외하고 별도 요구사항/PLAN으로 돌린다. X08은 미해결 정책 충돌로 세지 않으며 정적 문서 확인을 구현 검증 PASS로 쓰지 않는다.
