## Problem

예약 신청 목록이 일상적인 접수 처리와 드물게 쓰는 관리 기능의 출발점을 겸한다. 운영자는 메뉴 이름만으로 무엇을 하는 화면인지 판단하기 어렵고, 아이별 상세와 가족별 입금 화면을 오가야 신청 내용 확인에서 예약 확정까지 진행할 수 있다.

목표는 `신청 내용 확인 → 실제 입금 확인·기록 → 예약 확정`을 가족 신청 상세 한 화면에서 끝내는 것이다. 개인정보 관리, 설정, 반환, 신청 링크 구성 기능에는 각각 명확한 관리 위치를 제공한다.

### 4. 현재 처리 동선과 상태의 혼동

1. 아이별 목록에서 신청을 연다.
2. 아이 상세에서 신청 내용·동의를 읽고, 새 방식이면 가족 입금·확정 화면으로 이동한다.
3. 가족 화면은 현재 선택 확정 영역이 실제 입금 기록 영역보다 먼저 나온다. 보호자 알림·실제 금액·아이별 영문 상태가 섞여 있고 확정 전에 확인할 정보를 되찾아야 한다.
4. 아이 반려·취소에는 다시 아이 상세, 반환 기록에는 반환 관리로 이동한다.

소스에서 목록은 `확인/미확인`, 기존 상세는 `미확인`을 사용한다. 사용자 제시 표현 `입금 미확인`까지 포함해, 알림이 없는 것인지·은행 확인 기록이 없는 것인지·금액이 부족한 것인지 구분할 수 없는 표현을 대체한다. 가족 상세의 현재 `미배정`은 `입금−모든 배정` 계산이므로 정의 자체가 반환 보류액을 다시 더하는 것은 아니다. 문제는 금액의 구성·다음 행동을 설명하지 않는 표시와 화면 분산이다.

## User Story

- ADMIN으로서 한 가족이 누구를 어느 클래스에 신청했는지 먼저 파악하고, 자녀별 내용을 펼쳐 검토하고 싶다.
- ADMIN으로서 보호자의 입금 알림과 은행에서 직접 확인한 입금을 구별해, 부분·초과입금도 실제 금액대로 기록하고 싶다.
- ADMIN으로서 같은 화면에서 확정할 아이를 선택하고, 쓸 수 있는 잔액·반환할 금액·확정 결과를 확인하고 싶다.
- ADMIN으로서 링크 준비·설정·개인정보 파기·반환 업무를 메뉴 이름만 보고 찾고 싶다.
- 보호자로서 내 자녀만 선택하고 내 정보·동의를 입력한 뒤, 접수 완료와 송금 안내를 단계별로 이해하고 싶다.

## Scope

- 전체 관리자 메뉴의 정보 구조·이름·중복 진입점 정리와 기존 경로 호환 요구.
- 가족 기본 목록, 펼칠 수 있는 아이 신청, 세 상태 축, 필터·집계·모바일 카드.
- 신청 내용·은행 입금 기록·초과입금·아이별 확정을 한 가족 상세에 통합하는 UX.
- 클래스 상세 신청 링크 발급과 통합 신청 링크 관리의 연결.
- 보호자 3단계 신청과 완료 안내, 기존·다자녀·친구 초대의 표시 호환.
- 화면별 버튼·안내·오류 문구, 기능·권한·데이터 호환과 수용 기준.

## Business Rules

### 1. 유지할 핵심 규칙

1. 가족은 **한 번 제출한 묶음**이다. 새 방식은 `ReservationApplicationSubmission` 한 건을 표시 단위로 삼고, 아이별 `ReservationApplication`·`Reservation`·출결·동의는 그대로 독립적이다.
2. 연락처·보호자 이름이 같아도 별도 제출은 합치지 않는다. 친구 동행 가족도 별도 카드·별도 입금으로 유지하고, 동행 연결을 가족·Child 관계로 바꾸지 않는다.
3. 신청은 좌석을 점유하지 않는다. 확정 전 신청·입금·반환은 기존 예약·매출 집계에 넣지 않는다.
4. 보호자 입금 알림 없이도 ADMIN이 은행 거래를 확인해 기록하고 확정할 수 있다. 알림만으로는 입금 기록·결제·확정을 만들 수 없다.
5. 실제 입금은 여러 차례 누적한다. 초과분을 실제액에서 빼서 기록하거나 임의 할인·수수료·가상 반환을 만들지 않는다.
6. 새 방식은 선택 아이의 고정 청구액을 충족하는 가용 입금과 기존 예약 검증을 통과해야 확정된다. 선택 일괄 확정은 전부 성공하거나 전부 실패한다.
7. 반려는 운영자 판단, 신청 취소는 보호자 요청이며 아이별 사유가 필수다. 확정 후에는 기존 예약 취소·Refund 흐름을 사용한다.
8. 개인정보·동의·수동 파기 범위, ADMIN 전용 신청·재무 권한은 유지한다. 공개 금액은 ADR-063의 유효 링크 내 클래스별 참가비·본인 예상 총액과 자기 완료 권한의 저장된 송금액으로 한정한다.

### 2. Before / After 메뉴 구조

**Before — 현재 전역 메뉴와 신청 하위 구조**

```text
대시보드 / 아이 관리 / 선생님 관리 / 프로그램 관리 / 클래스 일정
예약 관리 / 예약 신청(아이 대기 건수) / 결제·환불 / 매출 집계
계정 관리 / AI 상담(Mock) / 비밀번호 변경

예약 신청
├─ 아이별 신청 목록 → 아이 상세 → 가족 신청 및 입금
├─ 개인정보 보관기간 관리
├─ 신청 그룹 관리 → 그룹 상세·링크 발급
├─ 운영 설정
└─ 반환 처리
클래스 상세 → 단일 신청 링크 발급 → 그룹 신청 관리
별도: /ai-service 페이지는 전역 진입점 없음
```

**After — 제안하는 업무별 메뉴 구조**

```text
대시보드
신청·예약
├─ 예약 신청 처리 [대기 N가족]
│  └─ 가족 신청 상세: ① 신청 확인 → ② 입금 확인 → ③ 예약 확정
└─ 예약 관리
클래스 운영
├─ 클래스 일정 → 클래스 상세 → 이 클래스 신청 링크
├─ 신청 링크 관리 → 단일/여러 클래스 링크·클래스 구성 관리
├─ 프로그램 관리
└─ 선생님 관리
아이 관리 → 아이 상세·이력·안전정보·동의
결제·정산
├─ 결제·환불 → 예약 결제 상세·환불 기록
├─ 예약 전 입금 반환 → 반환 대상·부분반환·완료 내역
└─ 매출 집계
운영 관리
├─ 입금 계좌·안내 채널
├─ 개인정보 보관·파기
├─ 계정 관리
└─ AI 상담 관리
   ├─ 합성 상담 검증 (Mock)
   └─ 실연동 관리 (운영 승인 별도)
내 계정 → 비밀번호 변경
```

이는 메뉴의 논리적 계층이다. 데스크톱은 ADR-017의 상단 가로 탐색을 유지하고 업무 묶음에서 하위 메뉴를 연다. 모바일은 같은 이름·순서의 드로어를 사용하며 현재 업무 묶음을 펼친다. 메뉴 과밀을 가로 스크롤로 해결하지 않는다. 새 고정 사이드바 도입은 요구하지 않는다.

| 이동 대상 | 새 기본 위치·설명 | 신청 화면에서의 연결 | 기능 보존 조건 |
|---|---|---|---|
| 개인정보 보관기간 관리 | 운영 관리 → **개인정보 보관·파기**: 만료 대상 조회와 파기 | 가족 상세의 `보관 정보`에서 관련 상세 연결. 목록 상단 상시 버튼은 이동 | 반려·취소 신청·확정 고객·먼저 처리할 신청, 재실행·파기 범위·처리 이력 유지 |
| 운영 설정 | 운영 관리 → **입금 계좌·안내 채널**: 계좌 3개·채널 URL 3개 | 설정 미비 때 `입금 안내 설정 열기`라는 문맥 링크 | 6개 값 수정, 최초 기존 설정 가져오기, HTTPS 검증·미비 시 접수 차단 유지 |
| 반환 처리 | 결제·정산 → **예약 전 입금 반환** | 가족 상세에 같은 반환 내역·기록 기능을 문맥 내 제공하고 `전체 반환 대상 보기`로 연결 | 미처리뿐 아니라 부분·완료 이력을 찾을 수 있음. Refund와 원장·의미 구별 |
| 신청 그룹 관리 | 클래스 운영 → **신청 링크 관리**: 여러 클래스를 한 링크로 접수하도록 구성 | 처리 목록 상단에는 두지 않음. 클래스 상세에서 해당 클래스가 포함된 링크 관리로 연결 | 그룹 생성·구성 변경·중지·재개·발급·교체·기존 단일 링크·전환 모두 유지 |

#### 중복 진입점 정리와 탐색 규칙

| 현재 겹치거나 불명확한 경로 | 개선안 |
|---|---|
| 아이 상세와 가족 상세가 모두 신청 처리 화면 | 새 방식의 주 처리 화면은 가족 상세 한 곳. 아이 상세 기존 URL은 같은 가족 상세의 해당 아이 영역으로 연결하며 권한 검사를 유지 |
| 클래스 단일 링크 카드와 그룹 관리 | 단일·여러 클래스 링크의 관리 홈을 `신청 링크 관리`로 통합. 클래스 상세는 현재 클래스 범위의 같은 업무를 제공하는 바로가기. 별도 복제 데이터·별도 발급 규칙을 만들지 않음 |
| 한 클래스가 기존 단일 링크와 여러 그룹에 들어갈 수 있음 | 모두 구분해 표시. 기존 주소 전환으로 연결된 그룹과 일반 그룹을 구별하고, 단순히 클래스가 같다는 이유로 합치거나 다른 링크를 무효화하지 않음 |
| 신청 목록·상세·가족 화면의 반환 이동 | 반환 관리 홈은 한 곳이며 가족 상세는 해당 가족 범위의 문맥 진입점. 동일 입금을 두 개 원장으로 만들지 않음 |
| 예약 목록의 `예약 등록`, 아이·클래스 상세의 `예약 추가` | 같은 직접 생성 경로의 문구를 **직접 예약 등록**으로 통일. 아이/클래스 사전 선택 유지. 신청 확정 버튼과 구별 |
| 예약 상세·아이 결제 이력·결제 목록의 결제 상세 | 유용한 문맥 링크 유지. `결제 내역 보기`, `예약 내역 보기`로 목적을 표시하고 동일 결제 상세 사용 |
| 확정 신청의 `결제 등록` | 새 방식은 연결된 Payment의 `결제 내역 보기`. 기존 방식만 결제 미등록이면 `결제 등록`. 이미 존재하면 다시 등록하지 않음 |
| 대시보드 캘린더와 클래스 목록 | 캘린더는 날짜별 운영 탐색, 목록은 클래스 관리로 유지. 같은 클래스 상세로 연결하고 별도 신청 대기·매출 계산을 복제하지 않음 |
| 메뉴 `매출 집계`와 제목 `매출 현황` | 메뉴·페이지 제목을 **매출 집계**로 통일. 집계 규칙은 유지 |
| 프로그램 기본 가격과 클래스 신청금액 | `프로그램 기본 가격(참고)`와 `이 클래스 신청금액`을 명시. 기본 가격을 청구액으로 자동 사용하지 않음 |
| AI Mock 메뉴와 전역 경로가 없는 실연동 화면 | 운영 관리의 `AI 상담 관리`에서 두 목적을 구별해 찾도록 제안. 기존 ADMIN·환경·운영 승인 차단을 유지하고 신청 설정과 합치지 않음 |
| 계정 관리와 본인 비밀번호 변경 | 전자는 운영 관리, 후자는 내 계정으로 구별. 선생님에게는 `내 정보` 유지 |
| 상세의 `목록으로`, 브라우저 뒤로가기 | 신청 필터·페이지·클래스 범위와 선택 가족 위치를 복원. 다른 메뉴에서 왔다면 `가족 신청 보기`와 원래 메뉴 복귀를 제공 |

기존 관리자 URL은 북마크로 계속 도달할 수 있어야 한다. 기능별 새 메뉴를 먼저 제공하고, 기존 경로는 같은 화면 또는 해당 위치로 연결한다. 정확한 새 URL·redirect 방식은 PLAN에서 정한다. 공개 `/apply/...` 주소는 메뉴 이동 때문에 바꾸거나 재발급하지 않는다.

### 3. 관리자 신청 목록 — 가족 카드 기본

#### 표시 단위·집계·정렬

- 새 방식은 제출 ID별 한 카드다. 자녀 1명도 같은 카드이며, 여러 제출·동행 가족은 합치지 않는다.
- `submissionId`가 없는 기존 신청은 **기존 방식 · 아이 1명 신청** 카드 한 개로 표시한다. 화면상 묶음일 뿐 새 Submission을 생성하거나 다른 신청과 합치지 않는다.
- 목록과 페이지 구분은 카드 단위다. 제안 페이지 크기는 20가족이며, 아이별 페이지를 먼저 잘라 가족이 두 페이지로 나뉘면 안 된다.
- `총 N가족 · 아이 신청 M건`처럼 단위를 붙인다. 전역 메뉴는 `대기 N가족`, 화면에는 대기 아이 건수도 병기한다. 기존 아이 기준 숫자를 가족 숫자로 재명명하지 않는다.
- 기본은 `처리 대기`: 미처리 아이가 하나라도 있는 가족. 처리 대상 아이의 가장 이른 클래스 시작일 → 접수 시각 → 안정적인 식별 순으로 정렬한다. 취소·시작된 클래스의 미처리 신청도 자동 제외하지 않고 처리 필요로 표시한다. 다른 상태는 최근 접수 순이다.

#### 화면 구성

```text
예약 신청 처리
신청 내용을 확인하고 실제 입금을 기록한 뒤 예약을 확정하세요.
[신청 상태: 처리 대기 ▾] [입금 알림: 전체 ▾] [입금 기록: 전체 ▾]
[필터 적용] [필터 초기화]
대기 N가족 · 아이 신청 M건

┌ 보호자 {이름} · 자녀 2명 ({아이 1}, {아이 2})
│ {프로그램명} · {클래스 날짜/시작–종료 시간}
│ 처리 대기 1명 · 예약 확정 1/2명
│ 입금: 알림 받음 · 은행 확인 필요
│ [신청 처리하기]
│ [아이 신청 2건 펼치기]
└ 펼치면 아이별 이름·클래스·일시·고정 금액·처리 상태
```

위 예시는 형식 설명이며 이름·수량·상태는 실제 해당 제출 값으로 표시한다. **기본 노출은 보호자 이름, 자녀 수·이름 요약, 프로그램/클래스 시간, 처리 상태, 핵심 입금 상태, `[신청 처리하기]`**다. 여러 클래스면 `클래스 {K}개 · 가장 이른 수업 {일시}`로 요약하고 펼침에서 모두 확인한다. 접수 시각·세부 상태 시각·거래 금액 설명은 펼침 또는 상세로 옮긴다. 파기된 이름은 `(파기됨)`으로 표시하고 다른 기록으로 복원하지 않는다.

**기본 숨김:** 배정액 P, 가용액 A의 구성·차감 상세, 반환 의무 원장, 거래별 입금, PaymentItem/결제 항목 매핑, 동의 원문. 목록에 원장 표를 펼쳐 놓지 않는다. 필요한 경우 가족 상세의 해당 영역을 명시적으로 펼쳐 확인하며, 입금/확정 처리 영역에는 그 행동에 필요한 최신 A·선택액·부족액을 제공한다. 연락처·생년월일·요청사항도 상세에서만 확인한다.

**상태 원칙:** 지금 필요한 행동을 먼저 짧게 보여준다. `신청 확인 필요`, `은행 입금 확인 필요`, `예약 확정 검토`, `반환 내역 확인 필요`처럼 현재 단계에 맞는 안내와 핵심 배지를 사용한다. 보호자 알림·은행 확인·예약 확정을 모두 긴 문장으로 기본 카드에 나열하지 않는다. 세 축의 의미·판단 근거는 독립적으로 유지하고 상세에서 확인한다. 알림이 있다는 이유로 은행 확인·예약 확정을 표시하거나, 일부 확정을 가족 전체 확정으로 줄이지 않는다. 오류·처리 불가·반환 조치가 있으면 관련 경고·해결 위치만 드러낸다.

아이 펼침에는 각 아이의 클래스별 일시·고정 청구액·`처리 대기/예약 확정/신청 반려/신청 취소`와 중복 가능 표시를 둔다. `이 아이 신청 확인`은 가족 상세의 해당 아이로 이동한다. 펼침과 `[신청 처리하기]`는 서로 다른 버튼이며 카드 전체를 클릭 가능한 중첩 링크로 만들지 않는다. 목록에서 금전 기록·반려·확정을 실행하지 않는다.

#### 필터와 가족 요약

- 신청 상태: `처리 대기 / 예약 확정 포함 / 신청 반려 포함 / 신청 취소 포함 / 전체`. 가족 안에 해당 아이가 있으면 한 번 표시하고, 펼치면 다른 상태의 자녀도 함께 보여 `필터에 해당`을 구별한다. 기존 `status` 북마크의 의미도 유지한다.
- 보호자 입금 알림: `전체 / 알림 받음 / 알림 없음 / 기존 방식(알림 기능 없음)`.
- 입금 기록: `전체 / 은행 확인 기록 없음 / 은행 확인 기록 있음 / 기존 방식(금액 기록 없음)`. `입금 안 함`으로 추정하지 않는다.
- 반환 대기 카드의 `반환 내역 확인`은 해당 가족 상세의 반환 영역으로 이동한다. 클래스 상세에서 `이 클래스 신청 보기`로 들어오면 클래스 범위를 명시하고 해제할 수 있어야 한다.
- 여러 필터는 함께 적용한다. 아이 상태와 클래스 범위 조건은 **같은 아이 신청**이 충족해야 하며 서로 다른 형제의 값을 조합해 일치시키지 않는다. 해당 가족의 입금은 전체 가족 기준이라는 범위를 표시한다.
- 확정된 아이와 대기 아이가 섞이면 `예약 확정 1/2명 · 처리 대기 1명`, 확정·반려가 섞이면 `예약 확정 1/2명 · 신청 반려 1명`으로 표시한다. `가족 전체 확정`으로 줄이지 않는다. 모든 아이가 확정됐을 때만 `모두 예약 확정`이다.
- `중복 신청 확인 필요`는 기존의 같은 클래스·아이 이름·보호자 연락처 판정을 보존한다. 중복 확정이라는 단정이나 자동 차단·병합을 하지 않는다.

#### 반응형·기본 상태

모바일 768px 미만은 세로 카드 목록이며 표의 가로 스크롤·열 숨김에 의존하지 않는다. 현재 필요한 행동·처리 상태·핵심 입금 상태는 모바일에서도 보이며 세 축의 세부 근거는 펼침/상세에서 확인한다. 데스크톱도 같은 가족 카드를 사용하고 상태·금액을 읽기 쉬운 구역으로 배치한다. 펼쳐진 아이 목록도 카드 내부 세로 항목으로 제공한다.

처음 비어 있으면 `접수된 신청이 없습니다. 클래스 운영의 신청 링크 관리에서 링크를 준비할 수 있습니다.`와 해당 메뉴 링크를 제공한다. 필터 결과가 없으면 `조건에 맞는 가족 신청이 없습니다.`와 `필터 초기화`를 제공한다. 조회 중에는 카드 영역에 로딩 상태를, 실패에는 `신청 목록을 불러오지 못했습니다.`와 `목록 다시 불러오기`를 제공하며 실패를 0건으로 표시하지 않는다.

### 4. 서로 독립적인 상태·금액 정의

| 상태 축 | 새 방식의 표시 | 판단 근거·금지할 해석 |
|---|---|---|
| 보호자 입금 알림 | `알림 없음` / `알림 받음 · 시각` | `Submission.depositNotifiedAt`. 알림 없음은 미입금이 아니고, 알림 받음은 은행 확인이 아님 |
| 은행 확인 입금 | `은행 확인 기록 없음` / `은행 확인 입금 누계 D원`; 필요 시 `선택한 아이 확정에 B원 부족` | 실제 `ApplicationDeposit` 누적과 현재 배정·반환을 반영. 기존 `depositConfirmedAt`만으로 새 방식의 금액 충족을 판단하지 않음 |
| 예약 확정 | 아이별 처리 상태 + `확정 n/N명` | 실제 `ReservationApplication.status`. 알림·입금 기록 저장만으로 확정 배지로 바뀌지 않음 |
| 보조 반환 상태 | `반환 대기 R원` / `일부 반환 완료 · 남은 R원` / `반환 완료` | 실제 `ReturnObligation`·`ApplicationReturn`. 확정 상태를 대체하거나 전부 막는 상태가 아님 |

이 표는 상태의 의미와 상세 표시 기준이다. 기본 카드에는 현재 필요한 행동과 짧은 핵심 상태만 표시한다. 금액은 UI에서 독자적인 금융 정책을 계산하지 않고 기존 원장의 권위 있는 값으로 보여준다. 상세의 금액 설명은 다음과 같다.

| 기호 | 화면명 | 정의 |
|---|---|---|
| Q | 접수 당시 신청금액 합계 | 아이별 `quotedAmount` 합계. 반려·취소돼도 원래 신청금액을 조용히 바꾸지 않음 |
| D | 은행 확인 입금 누계 | 실제 확인 입금액 합계 |
| P | 예약 결제에 연결한 금액 | 확정한 아이 Payment 배정 합계. 이후 Refund를 이 원장에서 또 차감하지 않음 |
| R | 반환 예정으로 확보한 금액 | 반환 의무 중 아직 돌려주지 않은 잔액. 예약에 다시 사용할 수 없음 |
| T | 반환 완료액 | 실제 완료된 예약 전 반환 누계 |
| A | 예약에 쓸 수 있는 금액 | `D − P − R − T`. 원장의 미배정 가용액과 일치 |
| S | 이번에 확정할 금액 | 현재 선택한 처리 대기 아이들의 고정 청구액 합계 |
| B | 이번 확정에 부족한 금액 | `max(0, S − A)`. 부족 여부는 입금 누계 D와 원래 총액 Q의 단순 비교가 아님 |

항상 `D = A + P + R + T`를 만족해야 한다. 완료 반환이 반환 배정에 이미 포함돼 있어도 다시 차감하지 않는다. 초과입금은 남은 처리 대기 청구를 제외한 실제 미배정 초과분에 대해 기존 서버가 반환 의무로 확보한 금액으로 표시한다. `D−Q`만으로 반려·부분확정 가족의 반환액을 산출하지 않는다.

기존 방식은 `입금 알림: 제공하지 않는 신청`, `입금액: 기록 없음(기존 방식)`으로 표시하고, 시각이 있으면 `입금 확인 기록 있음 · 시각·처리자`로 구별한다. 금액 미기록을 0원·전액 입금·부족으로 추정하지 않는다.

### 5. 관리자 가족 신청 상세 — 확인 → 입금 → 확정

#### 공통 구조

```text
신청·예약 > 예약 신청 처리 > 가족 신청 상세
[신청 목록으로]  보호자 A 가족 · 아이 2명 · 접수 일시
보호자 입금 알림: 받음 | 은행 확인 입금: D원 | 예약 확정: n/N명

① 신청 확인
  보호자 정보·연락처 / 아이별 클래스·신청 내용·동의·기존 아이 연결
② 입금 확인
  안내한 입금자명 / 실제 은행 입금 기록 / 누계·가용액·초과분·반환
③ 예약 확정
  이번에 확정할 아이·금액 / 최종 검증·정원 경고 / 확정 결과

보조 정보: 처리 이력 / 보관 정보 / 관련 클래스·예약·결제
```

세 영역은 같은 페이지에 순서대로 있고 단계 표시에서 해당 영역으로 이동한다. 입금 기록 후 다른 화면을 열거나 수동 새로고침하지 않고 갱신된 잔액을 보고 확정할 수 있어야 한다. 큰 화면은 세 영역과 요약을 함께 읽기 쉽게 배치하고 모바일은 순서대로 쌓는다. 단계 표시는 업무 안내이며 새 DB 상태 `검토 완료`나 별도 승인 절차를 만들지 않는다. 화면을 열었다는 이유로 신청 상태·동의·감사 이력을 변경하지 않는다.

#### ① 신청 확인

- 보호자 이름·`tel:` 연락처·아이와의 관계·접수 시각을 공통 영역에 한 번 보여준다. 친구 동행이 있으면 다른 가족의 별도 신청으로 연결하되 금액·처리를 합치지 않는다.
- 아이별로 이름·생년월일·성별·신청 클래스·날짜/시간(KST)·장소·고정 신청금액·요청사항·상태를 제공한다. 목록의 특정 아이에서 왔으면 그 아이를 펼쳐 시작한다.
- 해당 아이의 필수 확인 4개, 선택 동의 2개, 제출 시각·문구 버전을 펼쳐 확인할 수 있다. 선택 미동의를 누락·오류로 표시하거나 확정을 막지 않는다.
- 중복 가능, 클래스 취소·시작/종료, 아이 비활성·파기 등 확인할 사유는 해당 아이 옆에 표시한다. 확정 가능 여부는 기존 서버 규칙으로 최종 판정한다.
- `기존 아이 연결`과 `신청 정보로 새 아이 등록`을 명확히 구별한다. 후보 일치는 참고이며 ADMIN이 선택한다. 기존 아이의 정보를 신청 값으로 덮어쓰지 않는다. 같은 기기에서 선택한 기존 아이는 기존 동일성·소유 범위 검증을 유지한다.
- 예약 메모는 아이별로 보호자 요청사항을 검토·정리할 수 있어야 한다. `건강·알레르기 정보가 포함돼 있으면 예약 메모에서 제외하고 아이의 안전정보에서 관리해주세요.`를 표시한다. 동의·신청 원문을 임의로 수정하는 기능은 만들지 않는다.
- 미처리 아이의 보조 작업은 `신청 반려`와 `보호자 요청으로 신청 취소`다. 대상 아이 이름·클래스·사유 입력과 결과를 같은 화면에서 확인한다. 다른 형제는 바꾸지 않는다. 실제 입금이 있으면 기존 서버의 반환 의무 결과를 함께 표시한다.
- 확정한 아이는 `예약 내역 보기`, 연결 결제가 있으면 `결제 내역 보기`를 제공한다. 예약 취소는 확정 후 기존 예약 화면에서 처리한다. 신청 반려·취소와 같은 동작으로 보이지 않게 한다.

#### ② 입금 확인·초과입금·반환

- 맨 위에 `보호자 입금 알림`과 알림 시각을 별도 표시한다. 그 아래 `알림은 보호자가 보낸 안내입니다. 실제 은행 입금은 따로 확인해주세요.`를 둔다. 알림 유무로 금액 입력을 막지 않는다.
- `보호자가 안내한 입금자명`과 `은행에서 확인한 입금자명`을 구별한다. 다른 이름이어도 자동 불일치 거절·자동 일치 확정을 하지 않고 ADMIN이 확인한다.
- 입금 입력 필드는 `실제 입금액(원)`, `은행 입금자명`, `입금 일시(KST)`다. 저장 버튼은 **은행 확인 입금 기록** 하나다. 확인 ADMIN·기록 시각은 시스템 기록이며 보호자가 입력하지 않는다.
- 입금 기록 목록에는 건별 금액·입금자명·실제 입금 일시·확인 ADMIN·확인 시각을 보여준다. 이후 입금은 `추가 입금 기록`으로 새 입력을 열어 누적한다. 총액을 덮어쓰거나 초과분을 숨기지 않는다.
- 저장 성공 시 같은 페이지의 원장 요약 D/P/R/T/A, 이번 선택 금액 S와 부족액 B, 아이 상태를 서버 최신값으로 함께 갱신한다. `입금을 기록했습니다. 예약에 쓸 수 있는 금액은 {A}원입니다.`와 다음 영역 이동을 안내한다. 저장만으로 확정하지 않는다.
- 부족하면 `선택한 아이의 예약을 확정하려면 {B}원이 더 필요합니다.`를 보여준다. 가용액으로 일부 아이를 선택 확정하는 기존 기능은 유지한다. 시스템이 자동으로 특정 아이를 골라 확정하지 않는다.
- 초과분에는 `초과입금 {금액}원 · 반환 대기`와 `예약 결제에 포함되지 않습니다.`를 표시한다. 원래 신청금액·확정할 금액과 나란히 비교하고, 반환 대기 때문에 잔액을 충족한 다른 아이의 확정을 일률 차단하지 않는다.
- `반환 내역`은 같은 페이지에서 펼친다. 반환 사유 구분, 필요액·완료액·잔액·실제 반환일·처리일·ADMIN·사유 이력을 보여준다. `EXCESS/REJECTED/CANCELLED`는 각각 `초과입금/신청 반려/신청 취소`로 표시한다.
- 실제 은행 반환을 한 뒤에만 `실제 반환액(원)`, `반환 일시(KST)`, `반환 사유`를 입력해 **반환 이체 기록**한다. 이 버튼은 돈을 송금하지 않는다. 부분반환 후 남은 금액을 갱신하며 잔액 0일 때만 완료 표시한다.
- 가족 상세와 `결제·정산 → 예약 전 입금 반환`은 같은 대상·같은 기록 동작을 제공한다. 전자는 현재 가족 범위, 후자는 전체 미처리·부분반환·완료 내역의 작업함이다. 처리 위치가 다르다고 중복 완료할 수 없어야 한다.
- 반려·취소 후 뒤늦게 실제 입금이 들어온 경우도 기존 원장 처리 범위에서 기록하고 반환 결과를 확인할 수 있어야 한다. 확정 가능한 아이가 없다는 이유로 금융 이력을 숨기지 않는다.

#### ③ 예약 확정

- 미처리 아이 중 이번 대상을 명시적으로 선택하고, 아이별 연결 방식·클래스·고정 금액과 `선택 {n}명 · 이번 확정 {S}원 · 예약에 쓸 수 있는 금액 {A}원`을 보여준다. 처음부터 모든 아이를 확정 대상으로 간주해 제출하지 않는다.
- 미선택, 아이 연결 미정, 부족액, 이미 처리된 아이, 클래스·아이 상태 등의 차단 이유를 행동 옆에 구체적으로 표시한다. disabled 버튼만 보여주지 않는다. 금액 충족은 확정의 필요 조건이며 `모든 검증 통과`를 미리 보장하지 않는다.
- 주 버튼은 **선택한 아이 {n}명 예약 확정** 하나다. 입금 저장과 확정을 합친 버튼, 같은 의미의 `확정/일괄 확정/처리` 버튼을 병렬 배치하지 않는다.
- 정원 초과 때는 대상 클래스·현재 예약 수·정원·확정 후 초과 인원을 ADMIN에게 보여준다. 기존 명시 확인 절차 안에서 **정원 초과 확인 후 예약 확정**으로 주 버튼을 바꾼다. 이때 일반 확정 버튼을 동시에 남기지 않는다. 선택 아이·연결·클래스 조건이 바뀌면 초과 확인을 다시 받으며 최종 서버 검증을 유지한다.
- 성공하면 `선택한 아이 {n}명의 예약을 확정했습니다.`와 각 예약·결제 연결을 같은 화면에서 보여준다. 새 방식은 아이별 고정 금액만 PaymentItem에 연결하고 합계 Payment를 한 번 생성하는 기존 흐름이다. 별도 `결제 등록`을 유도하지 않는다.
- 일부만 선택 확정했으면 나머지는 미처리 상태와 잔액을 그대로 보여준다. 이미 확정한 아이를 재시도 대상으로 남기지 않는다. 한 번의 일괄 처리에서 일부만 성공한 것처럼 표시하지 않는다.
- 다른 ADMIN의 처리·반환·파기 등으로 서버 재검증이 실패하면 쓰기 결과를 추정하지 않고 최신 상태를 표시한다. 안전하게 유효한 입력·선택은 보존하고 변경된 대상만 다시 확인하게 한다.

#### 기존 방식·완료 상태의 예외

기존 단일 신청도 같은 `① 신청 확인 → ② 입금 확인 → ③ 예약 확정` 구조를 사용하되, 금액 입력 원장이 아닌 **기존 방식 입금 확인 기록**을 제공한다. `이 신청은 입금액을 저장하지 않는 기존 방식입니다. 은행 입금을 확인한 뒤 기록해주세요.`를 표시하고 기존 확인 시각·처리자로 확정을 허용한다. 확정은 기존대로 Payment를 만들지 않으므로 미등록이면 `결제 등록`을 제공한다.

가족 전체가 처리된 뒤에도 신청·입금·반환·동의·처리 이력을 읽을 수 있다. 파기된 정보는 `(파기됨)`과 파기 시각으로 대체하며, 남아 있는 금융 원장을 개인정보 복원 수단으로 사용하지 않는다. 수동 파기는 이 상세에서 즉시 실행하지 않고 `운영 관리 → 개인정보 보관·파기`에서 수행한다.

### 6. 클래스 상세 — 신청 링크 발급 화면

클래스 상세의 ADMIN 전용 영역 이름을 **이 클래스 신청 링크**로 정한다. 기본 노출은 클래스 이름·시간·참가비·링크 상태와 `[링크 발급] [링크 복사] [공유하기] [신청 화면 확인]`이며 상태·원문 보유 여부에 맞는 행동을 제공한다. 이력·교체/중지·여러 클래스·진단·호환 설명은 기본 접힌 고급 영역에 둔다. 오류·설정 미비·Preview 제한 때만 관련 이유·해결 행동을 드러낸다. 상세 기준은 통합 SPEC BR 2를 따른다.

```text
이 클래스 신청 링크
클래스: 프로그램 · 날짜/시간
참가비: 설정값 또는 미설정
링크 상태: 미발급 / 접수 중 / 접수 중지 / 접수 불가
[링크 발급] [링크 복사] [공유하기]
[신청 화면 확인]
{오류·설정 미비·Preview 제한일 때 관련 안내·해결 행동}
[이 클래스 신청 보기]
[고급 설정 펼치기] (기본 접힘)
  발급 이력 / 링크 교체·중지 / 여러 클래스 / 진단·호환 설명
```

| 상황 | 주 행동·안내 | 보존할 동작 |
|---|---|---|
| 새 링크, 신청금액 미설정 | `신청금액 설정`; `관리자가 실제 신청금액을 먼저 지정해주세요.` | ADMIN이 실제 금액을 입력·저장. 기본 가격을 자동 대입하지 않음 |
| 새 링크, 준비 완료 | `신청 링크 발급` | 새 방식의 단일 클래스 범위로 발급. 여러 클래스를 묶으려면 같은 관리 홈의 `여러 클래스 신청 링크 만들기` 사용 |
| 발급 직후 주소를 가진 상태 | `링크 복사`·`공유하기`·`신청 화면 확인`, 고급 영역의 교체·중지 | 복사·공유·신청 화면 확인은 쓰기 없이 수행. 주소는 발급 직후, 최근 발급 시각·ADMIN은 고급 영역에 표시 |
| 기존 새 방식 링크, 화면 재방문으로 원문 없음 | `신청 링크 교체`; `기존 주소는 복원할 수 없습니다. 새로 발급하면 이전 주소로 접수할 수 없습니다.` | 해시 저장 토큰을 복원·영속 평문 저장하지 않음. 자동 재발급 금지 |
| 접수 중지 | `접수 재개 및 새 링크 발급` | 이전 주소를 되살린다고 안내하지 않음 |
| 클래스 취소·시작 시각 경과 | `클래스 상태로 접수할 수 없습니다.` | 발급·재개를 막고 기존 신청은 관리 가능. 공개 화면에는 내부 사유 비노출 |
| 설정·동의 문구 준비 안 됨 | `입금 안내 설정 열기` 또는 해당 준비 사유 | 설정값·필수 문구 미비 시 공개 접수 차단 유지. 유효한 주소가 있다는 사실과 실제 접수 가능을 구별 |
| 기존 방식 링크, 금액 없음 | `기존 방식(금액 안내 없음)`과 기존 주소 복사·중지·재발급 | 자동 폐쇄·가격 추론·강제 전환 금지 |
| 기존 방식 링크를 명시 전환 | `다자녀·입금 관리 방식으로 전환` | 실제 금액 지정 후 ADMIN 명시 실행. 기존 공개 주소 유지, 이후 접수에 적용. 이전 신청을 새 원장 방식으로 소급 전환하지 않음 |

링크 교체·중지 전에는 영향 범위와 취소 버튼을 보여준다. 교체 문구는 `새 링크를 발급하면 이전 링크로는 신청할 수 없습니다. 이미 접수된 신청은 유지됩니다.`이며, 중지 문구는 `이 링크의 신규 접수를 중지합니다. 이미 접수된 신청은 유지됩니다.`다. 여러 클래스 링크에서는 영향을 받는 클래스 목록도 함께 표시한다.

`신청금액 설정`은 이 영역에서 ADMIN 입력을 열고 `신청금액 저장`으로 기존 클래스 최종 신청금액을 저장한다. 이후 준비 상태를 다시 보여 발급으로 이어간다. 기본 가격·임의 추천 가격을 입력값으로 확정하지 않으며 이미 접수된 신청의 금액을 바꾸지 않는다.

`신청 링크 관리`는 기존 단일 링크와 여러 클래스 링크를 모두 찾는 관리 홈이다. 기본 목록은 클래스 이름·일시·포함 클래스 수·실제 접수 상태·발급 시각으로 식별한다. 현재 Group에는 제목 필드가 없으므로 사용자 지정 그룹명·이름 검색을 전제하지 않고, 클래스 요약으로 구별한다. 같은 클래스의 여러 그룹은 개별 항목으로 보존한다.

여러 클래스 링크 생성 화면은 기존 예정 클래스를 선택하고 각 최종 신청금액·설정 준비를 확인한 뒤 `선택한 클래스로 신청 링크 구성`으로 묶음을 만든다. 이어 같은 작업 흐름 안에서 `신청 링크 발급`과 `신청 링크 복사`를 제공한다. 그룹 생성과 링크 발급의 저장 결과를 구별해, 발급 실패 때 묶음을 중복 생성하지 않고 다시 발급할 수 있어야 한다.

기존 구성 수정은 `접수 클래스 구성 저장`, 중지는 `신청 접수 중지`, 재개는 `접수 재개 및 새 링크 발급`이다. 저장 전 `변경은 이후 신청에 적용됩니다. 이미 접수된 아이의 클래스와 신청금액은 유지됩니다.`를 표시한다. 기존 과거·취소 클래스 구성이 조회에서 사라지지 않게 하고, 새로 추가할 클래스의 적격성은 기존 서버 규칙으로 검증한다.

### 7. 보호자 3단계 신청 화면

[통합 SPEC BR 3·INT-08~17](UX-REDESIGN-INTEGRATED-SPEC.md)과 동일하게 **① 클래스 선택 → ② 보호자·자녀 정보 → ③ 동의·최종 확인**의 세 입력 단계와 **제출 후 결과·입금 안내**로 구성한다. 결과 화면은 입력 단계로 세지 않는다. `[다음]`·`[이전]`·카드 편집은 접수하지 않으며 ③의 `[신청서 제출]`만 원자 제출한다. 참가비 표시는 **Policy A — decided (2026-10-20, ADR-063)**를 따른다.

#### ① 클래스 선택

- 제목 `클래스 신청`, 현재 단계 이름, `신청은 예약 확정이 아닙니다.`를 보여준다.
- 유효 신청·동행 초대 링크 범위의 접수 가능 클래스에 대해 프로그램명·설명·대상 연령·날짜/시작·종료 시각(KST)·장소와 **클래스별 `ClassSchedule.applicationPrice` 참가비**를 표시한다. 단일 클래스는 정해진 대상을 확인만 하며 통합 링크는 이번 가족의 후보를 고른다.
- 후보 선택은 좌석 확보가 아니며, ②에서 아이마다 후보 중 정확히 1개 클래스에 연결한다. 후보 전체 가격을 가족 총액으로 합산하지 않는다. 아이 입력 전에는 `자녀 정보는 다음 단계에서 입력합니다.`를 표시한다.
- 정원·예약 수·잔여석·만석/예약 가능 여부·다른 그룹 가격·카탈로그·내부 운영정보·다른 가족 PII·입금/결제/반환/환불 원장은 제공하지 않는다. `[다음]`은 ②로만 이동한다.

#### ② 보호자·자녀 정보

- 보호자 이름·연락처·아이와의 관계를 한 번 입력한다. 새 방식에서만 `입금할 때 사용할 이름`을 받으며 실제 은행 확인 값과 구별한다.
- 아이 카드에는 이름·생년월일·성별(선택 안 함 포함)·클래스·선택 요청사항과 **본인 자녀별 선택 클래스의 참가비·예상 합계**를 표시한다. 자녀 추가·제외·클래스 변경마다 아이별 금액과 합계를 갱신한다. 미배정 자녀가 있으면 `클래스 선택 필요 · 예상 합계 확인 전`으로 안내한다.
- 새 방식 자녀 1~10명, 기존 금액 없는 Phase 18 자녀 1명을 유지한다. `내 자녀 추가`, `이 아이를 신청에서 제외`는 초안만 바꾸며 마지막 아이는 유지한다. 후보를 제거해도 다른 클래스로 조용히 재배정하지 않는다.
- 유효한 같은 기기의 이전 자기 자녀만 선택할 수 있다. 연락처로 다른 아이를 조회하거나 친구 가족의 자녀를 가져오지 않는다. 기존 아이 동일성·비활성/파기 제한을 유지하며 폼 편집으로 기존 Child를 갱신하지 않는다.
- 요청사항 안내는 `건강·알레르기 정보는 적지 말아 주세요. 필요한 안전 정보는 예약 확정 후 따로 여쭙니다.`다. 오류는 해당 아이·필드에 연결하고 다른 정상 입력을 보존한다.
- `[다음]`은 필수 정보와 아이별 클래스 배정을 검증한 뒤 ③, `[이전]`은 값을 보존하고 ①로 이동한다. 아직 접수하지 않는다.

#### ③ 동의·최종 확인

- 자녀 이름·클래스·일시·장소·입력 정보, **선택 클래스별 참가비와 총액**, 아이별 선택 동의 결과와 `아직 예약이 확정되지 않았습니다. 입금과 운영자 확인 후 예약이 확정됩니다.`를 표시한다. `[클래스 수정]`은 ①, `[보호자·자녀 정보 수정]`·`[이전]`은 ②로 이동한다.
- 공통 필수 확인은 적용할 아이 이름·클래스를 명시하고 한 번 입력하되 기존처럼 각 아이 신청에 현재 결과·버전을 저장한다. 필수 4개는 프로그램 안전 및 이용사항, 개인정보 수집·이용, 법정대리인, 취소 및 환불규정 확인이다. 서로 다른 이용사항 원문도 각각 읽을 수 있다.
- 선택 2개는 활동 사진·영상 촬영 및 참여 보호자 공유, YAHO 홍보 활용이다. 아이별 독립 값과 `동의하지 않아도 참가에 제한이 없습니다.` 안내를 유지한다. 다른 아이에게 자동 복사하지 않는다.
- 필수·선택 모두 기본 미선택, 과거 동의 자동 적용·필수/선택 `전체 동의`는 없다. 자녀·클래스 변경 시 적용 대상과 요약·금액을 갱신하고 새 자녀에 확인을 묵시 적용하지 않는다. 원문·버전·보관/환불 정책은 바꾸지 않는다.
- **신청서 제출**만 저장하며 처리 중·완료 이동 중 중복 클릭/Enter 제출을 막는다. 서버가 링크 유효성, 클래스 접수 상태/링크 소속, 확인 가격과 현재 가격 일치, 현재 버전 필수 확인·동의, 보호자/자녀 접근 범위를 재검증한다. 모두 접수되거나 모두 실패한다.

#### 가격 변경·제출 불일치·공개 범위

- 입력 중 가격 변경은 `참가비가 변경되었습니다. 변경된 금액과 총액을 다시 확인해 주세요.`와 허용 클래스별 이전→현재 가격·아이별 금액·새 총액을 보여주고 재확인받는다. 현재 유효한 입력·독립 선택 동의는 보존하며 확인하지 않은 새 가격으로 제출하지 않는다.
- 제출 시 확인 가격과 서버 현재 가격이 다르면 **어느 아이도 저장하지 않고** 같은 가격 재확인 상태로 돌아간다. 재확인 후 보호자가 명시적으로 다시 제출하며 그 사이 또 바뀌면 다시 거부한다. 가격 재확인은 필수 동의를 대신하지 않고 자동 재제출하지 않는다.
- 무효·중지·접근 불가 링크는 가격도 제공하지 않으며 기존 공통 문구 **현재 신청을 받지 않는 링크입니다.**를 사용한다. 가격 오류를 통해 내부 사유·클래스 존재·다른 그룹 가격을 누설하지 않는다.
- 공개 HTML·RSC·서버 응답에는 유효 링크 범위의 클래스별 참가비와 본인 자녀 예상금액만 허용한다. 다른 그룹 가격/카탈로그·좌석/가용성·다른 가족 PII·내부 메모/운영정보·금융 원장은 HTML·RSC·응답·오류·로그·캐시에서 제외한다. 다른 링크/기기와 캐시를 공유해 가격·개인정보를 노출하지 않는다. Preview guard와 허용 합성 범위는 그대로다.
- 가격 없는 기존 Phase 18 링크는 임의 가격·자동 폐쇄 없이 금액 미표시를 유지한다. null `applicationPrice`/`quotedAmount`를 0원이나 `Program.defaultPrice`로 채우지 않고 ADMIN 명시 업그레이드 뒤에만 새 금액 흐름을 적용한다.

#### 제출 후 결과·입금 안내 (입력 단계 밖)

- 제목은 **신청이 접수되었습니다**, 설명은 `아직 예약이 확정된 것은 아닙니다. 입금과 운영자 확인 후 예약이 확정됩니다.`다.
- 새 방식의 유효한 자기 완료 권한에서만 **서버가 검증·저장한 아이별 `quotedAmount`와 합계**, 은행·계좌·예금주·보호자가 제시한 입금자명을 보여준다. 클라이언트 예상액·현재 클래스 가격으로 재계산하지 않으며 이후 가격 변경은 이미 제출·확정한 금액을 바꾸지 않는다. `계좌번호 복사 / 입금액 복사 / 입금자명 복사`는 대상을 구별한다.
- **입금했어요**는 송금 후 최초 알림 시각만 멱등 기록하며 실제 은행 확인·예약 확정·매출을 바꾸지 않는다. 알림 후 `입금 알림을 보냈습니다. 운영자 확인을 기다려 주세요.`를 표시한다.
- **친구 보호자 초대**는 보조 영역에서 생성·복사·취소하며 친구가 자신의 정보·자녀·동의를 같은 세 입력 단계로 별도 제출한다. 다른 가족 정보·금액·입금 결과를 보여주지 않는다.
- 기존 Phase 18은 금액·입금자명·알림·초대를 추정하지 않고 기존 일반 완료 안내의 계좌·예금주·채널 범위를 유지한다. 완료 권한 무효/만료는 저장된 자기 신청·금액을 재노출하지 않는다. 새 고객 신청 관리·취소 기능, 입금 기한·환불 안내는 추가하지 않는다.
- 초안은 유효한 현재 폼 메모리에만 두며 개인정보·동의·입금자명을 URL·localStorage·sessionStorage·로그에 저장하지 않는다. 성공 후 전체 문서 이동·기존 캐시/완료·기기 권한을 유지하고 뒤로가기·새로고침에서 이전 PII·재제출 폼을 복원하지 않는다.

처리 중 문구는 `입금 기록 중… / 반환 기록 중… / 예약 확정 중… / 링크 발급 중… / 설정 저장 중… / 신청서 제출 중…`처럼 대상을 붙인다. 같은 요청의 연속 클릭은 막고 서버의 중복 방지도 유지한다. 성공 메시지는 스크린리더에 알리고 해당 부분의 갱신 결과를 화면에 남긴다.

운영 관리로 이동했다고 MANAGER에게 개인정보 파기·계좌 설정을 허용하지 않는다. MANAGER가 접근하는 클래스 상세에는 신청금액·입금 상태·대기 가족 수·관리 링크를 조회·직렬화하지 않는다. 메뉴 숨김뿐 아니라 직접 URL·서버 조회·액션·응답에서 최신 계정 상태·권한을 검증한다. 새 가족·입금 요약을 공용 카드에 넣어 재무정보를 누출하지 않는다.

#### 데이터 매핑·기존 데이터 호환

| UX 개념 | 현재 근거 데이터 | 호환 요구 |
|---|---|---|
| 가족 카드 | `ReservationApplicationSubmission.id`, 공통 보호자 정보 | 가족 master 신설 불필요. 보호자 연락처로 병합하지 않음 |
| 기존 방식 카드 | `ReservationApplication.submissionId = null` | 한 기존 신청의 표시용 묶음. Submission·금액·알림을 생성하지 않음 |
| 펼쳐지는 아이 | `ReservationApplication`, `classScheduleId`, `status` | 확정·반려·취소와 선택 동의는 독립. 영문 enum은 한국어 표시만 변경 |
| 가족 요약 상태 | 아이별 상태·개수 | 파생 표시. `PARTIALLY_CONFIRMED` 같은 새 영속 상태를 전제하지 않음 |
| 신청금액 | `ClassSchedule.applicationPrice` → 제출 시 `quotedAmount` | 입력은 유효 링크의 ADMIN 지정 가격·본인 예상 합계, 제출은 확인 가격=현재값 재검증 후 고정, 완료는 저장된 스냅샷. null을 0 또는 `Program.defaultPrice`로 채우지 않음 |
| 알림 | `Submission.depositNotifiedAt` | 최초 시각·멱등성 유지. 실제 입금 확인 상태로 변환하지 않음 |
| 실제 입금 | `ApplicationDeposit` | 원금·입금자·실제 일시·확인 시각·ADMIN 보존. 요약 때문에 행을 합치거나 덮지 않음 |
| 결제 배정 | `FundAllocation`, `ReservationApplicationPaymentMapping`, `Payment/PaymentItem` | 새 방식 확정 성공 시 한 번만 연결. 새 직접 결제 등록이나 중복 Revenue 없음 |
| 반환 | `ReturnObligation`, `ApplicationReturn`, 배정 | 반환 예정과 완료를 구별. 이미 반환 확보한 금액을 확정에 쓰지 않음 |
| 기존 확인 | 아이별 `depositConfirmedAt/By` | 기존 방식은 시각 확인으로 기존 확정. 금액 기반 새 원장과 혼동 금지 |
| 신청 링크 | `ReservationApplicationLink`, `ReservationApplicationGroup/Class` | 공개 주소 유지·명시 교체만 무효화. 그룹 원문 토큰은 발급 직후만 복사 가능 |
| 기기·친구 | 기존 Device/Submission 관계·Companion 모델 | 가족·친구 관계 자동 생성/병합 금지, 타 가족 입금 공유 금지 |
| 동의·보관 | 아이별 확인/동의·버전·파기 시각, `ChildConsent` | 공통 입력 UI여도 아이별 데이터·신청 시각·버전·미동의/철회 의미 유지 |

필요한 정보는 현재 모델에 있다. UX를 위해 새 가족 Entity·검토 완료 플래그·금융 상태 enum·개인정보 필드를 반드시 추가할 이유는 발견하지 못했다. 다만 현재 가족 페이지/목록 조회에는 통합 상세·한국어 상태·정확한 가족 집계에 필요한 선택 필드가 부족하므로, **쿼리와 화면 계약 변경은 필요**하다. migration 불필요를 확정하는 구현 설계는 아니며 PLAN에서 기존 모델로 충족되는지 확인한다.

이미 접수된 금액 없는 기존 신청은 미래 링크를 전환해도 기존 확정·수동 결제 방식을 유지한다. 새 방식의 기존 접수분은 링크 교체·그룹 구성·금액 설정을 변경해도 제출 당시 클래스·고정 청구액·동의 버전과 원장 연결을 유지한다. 기존 신청 내역·토큰을 삭제하거나 자동 재발급하는 데이터 정리를 요구하지 않는다.

#### 모바일·접근성·오류 및 동시 처리

- 360px·390px·768px·데스크톱에서 가로 스크롤 없이 핵심 상태·행동을 읽고 수행할 수 있어야 한다. 모바일은 가족·아이·링크·반환 목록을 카드로 쌓는다. 다른 도메인의 기존 표 전체를 이번에 전환하지는 않는다.
- 버튼은 터치하기 충분한 영역(최소 44px 높이)을 확보하고 좁은 화면에서 여러 버튼은 세로 배치한다. 긴 이름·클래스·금액·계좌·주소는 넘치지 않게 줄바꿈한다. 주요 안내·오류를 가로 스크롤이나 hover에만 두지 않는다.
- 카드 제목·입력 라벨·단계 제목·선택 영역의 의미를 구별한다. 펼침 상태를 보조기기에 알리고 키보드로 열고 닫으며 포커스를 잃지 않는다. 색상과 아이콘만으로 입금·확정 상태를 전달하지 않는다.
- 단계 이동·입력 오류는 해당 제목/필드로 포커스를 안내한다. 모달·패널을 쓰는 경우 닫힌 내부 컨트롤에 포커스가 가지 않으며 닫은 뒤 실행 위치로 돌아간다. 모바일 키보드나 하단 버튼이 오류·금액을 가리지 않아야 한다.
- 입금·반환·확정 처리 중에는 같은 동작의 재클릭을 막고 성공·오류를 알린다. 저장 실패·서버 재확인 실패에서 입력을 보존한다. 응답을 잃으면 이미 저장됐는지 확인할 수 있게 하고 새 거래를 자동 생성하지 않는다.
- 두 ADMIN의 확정·입금·반환, 파기·아이 변경, 정원·클래스 상태 변경의 기존 원자성·중복 방지를 유지한다. UI에서 한 번 disabled한 것을 서버 검증의 대체로 보지 않는다.
- 개인정보·동의·토큰 원문·입금자명·요청사항은 로그·분석 이벤트·새 URL 파라미터에 넣지 않는다. 운영 값·실제 고객 데이터 없이 문서를 검토하고, 후속 검증은 기존 환경·데이터 안전 규칙을 따른다.

## Acceptance Criteria

아래는 후속 PLAN·QA에서 추적할 요구 기준이다. 이 SPEC 작성 단계에서 테스트를 구현하거나 실행했다는 뜻이 아니다.

| ID | 시나리오·수용 기준 |
|---|---|
| UX-01 | 현재 전역 메뉴 전체와 신청 관련 하위 진입점이 위 목록으로 추적되며, 이동한 네 기능을 새 관리 메뉴에서 각각 찾을 수 있다. 기존 URL도 접근 가능하다. |
| UX-02 | ADMIN이 `예약 신청 처리`에 들어오면 처리 대기 가족 카드가 기본이다. 기본 노출은 보호자 이름·자녀 수/이름 요약·프로그램/클래스 시간·처리 상태·핵심 입금 상태·`[신청 처리하기]`다. 필요한 행동을 먼저 짧게 보여주며 세 상태를 장문 나열하지 않는다. 같은 제출의 자녀는 한 카드·한 페이지이며 별도 제출·친구 가족은 합치지 않는다. |
| UX-03 | 카드·전역 대기 표시의 가족 수와 아이 신청 건수를 구별하고, 혼합 상태 가족의 확정/반려/취소/대기 수를 실제 아이 상태와 일치시킨다. |
| UX-04 | 상태·클래스 범위·입금 조건을 함께 적용할 때 같은 아이가 상태·클래스 조건을 충족한다. 가족 전체 입금임을 표시하고 다른 상태 형제도 펼쳐 확인할 수 있다. |
| UX-05 | 카드 펼침으로 자녀별 클래스·일시·고정 금액·처리 상태·중복 가능성을 확인하고, 해당 아이 선택 상태의 가족 상세로 이동한다. 생년월일·요청사항·배정 P·가용 A 상세·반환 의무 원장·거래별 입금·결제 항목 매핑·동의 원문은 기본 목록에 노출하지 않고 상세의 해당 영역에서 확인한다. |
| UX-06 | 보호자 알림이 있어도 실제 입금 기록이 없으면 목록은 `알림 받음 · 은행 확인 필요`처럼 필요한 행동을 짧게 표시하고 상세는 세 축의 근거를 구별하며 확정하지 않는다. 알림이 없어도 은행 입금 기록으로 잔액을 충족하면 기존 검증 후 확정할 수 있다. |
| UX-07 | 가족 상세 한 화면에서 아이·동의·연결·메모 확인 → 실제 입금 저장 → 갱신된 잔액 확인 → 선택 확정을 끝낸다. 아이 상세·결제 등록으로 이동할 필요가 없다. |
| UX-08 | 여러 차례 부분입금이 누적되고, 현재 선택 청구액 S보다 A가 적으면 부족액을 표시해 확정을 막는다. 같은 입금액을 다른 형제·반환에 이중 사용하지 않는다. |
| UX-09 | 초과입금은 실제액 전체로 기록하고 초과분의 반환 상태를 표시한다. 잔액을 충족한 아이의 확정은 허용하며 초과분을 Payment·Revenue에 포함하지 않는다. |
| UX-10 | 아이 한 명만 선택 확정해도 다른 아이의 신청·동의·반려·취소 상태는 바뀌지 않는다. 선택한 여러 명의 일괄 확정은 전부 성공하거나 전부 실패한다. |
| UX-11 | 아이 연결·정원·중복·비활성·파기·클래스 상태를 최종 서버 검증한다. 정원 초과 경고 때 일반/초과 확정 버튼을 중복 노출하지 않고 선택 변경 시 다시 확인한다. |
| UX-12 | 아이 반려/보호자 요청 취소는 이름·클래스·필수 사유를 확인해 같은 가족 화면에서 처리하고, 실제 입금 범위의 반환 필요액·남은 형제 가용액을 갱신한다. |
| UX-13 | 같은 가족 화면과 전체 반환 관리에서 동일 반환 의무의 부분반환·완료 이력을 확인한다. 일부 반환 후 잔액을 보이고 과다/중복 반환은 거부한다. 버튼이 송금을 실행한다고 안내하지 않는다. |
| UX-14 | 새 방식 확정 후 실제 예약·Payment 연결을 보여주고 중복 `결제 등록`을 유도하지 않는다. 기존 방식의 금액 미기록·시각 확인·확정 후 수동 결제는 유지한다. |
| UX-15 | 클래스에서 신청금액과 접수 준비 상태를 확인하고 링크 구성·발급·복사로 이어진다. 복사는 주소를 교체하지 않으며 원문 없는 재방문에 복사를 약속하지 않는다. |
| UX-16 | 링크 교체·중지·재개 시 영향 범위를 구별하고, 이미 접수된 기록과 기존 공개 주소는 명시한 작업 외에는 변경되지 않는다. 여러 클래스 그룹의 구성 변경도 기존 접수에 소급하지 않는다. |
| UX-17 | 같은 클래스가 여러 그룹에 속하거나 기존 링크가 있어도 모두 찾을 수 있다. 금액 없는 기존 링크를 자동 폐쇄하거나 새 방식으로 강제 전환하지 않는다. |

| UX-19 | 보호자 정보·공통 확인은 반복 입력하지 않아도 각 아이 신청에 동일 버전·결과가 남는다. 선택 사진 동의는 아이별로 다를 수 있고 미동의로도 제출되며 과거 동의는 자동 적용되지 않는다. |
| UX-20 | 새 방식 제출 후 유효한 자기 완료 권한에서만 서버 검증·저장 `quotedAmount` 스냅샷·합계·송금 안내와 세 복사 기능을 제공한다. 이후 클래스/기본 가격 변경도 제출·확정된 금액을 바꾸지 않는다. 보호자 `입금했어요`는 알림만 기록하고 상태·매출을 변경하지 않는다. |

금액 시나리오는 실제 정책값을 정하는 대신 아래 **합성 검증 예시**로 보존식을 확인한다. 단위는 임의의 원 단위 예시이며 운영 가격·환불 정책이 아니다.

| 합성 시나리오 | 기대 표시·처리 |
|---|---|
| 아이 A 청구 40, 아이 B 청구 60, 입금 30+70 | D=100, A=100. A만 확정하면 P=40, A=60, B는 대기. 이후 B 확정 시 P=100, A=0 |
| 같은 청구 합계 100, 입금 110 | R=10, A=100. 두 아이 확정 후 P=100, R=10. 초과 10은 Revenue 아님 |
| 청구 40+60, 입금 100 후 B 신청 취소 | 기존 원장이 B 반환 의무 60을 확보하면 A=40, R=60. A 확정 후 P=40; 반환 20 기록 시 T=20, R=40. D=100 보존 |
| 알림 있음·은행 기록 없음 | 알림만 표시. 은행 확인 누계 0원·확정 부족을 구별하며 실제 미입금이라고 단정하지 않음 |
| 기존 신청의 quotedAmount 없음·확인 시각 있음 | `입금액 기록 없음(기존 방식)`·기존 확인 이력 표시. 금액 0원으로 새 방식 검증하지 않음 |

| REQUIREMENTS Phase 20; ADR-060 | **유지**: 해시 토큰은 원문 복원 불가, 기존 단일 주소 명시 전환, 친구 별도 가족·기기 소유 범위·실패 차단. 메뉴 통합을 주소 자동 교체로 구현하지 않는다. |

이 문서의 메뉴명·배치·카드·버튼은 검토용 UX 제안이다. 가격 표시와 재검증은 REQUIREMENTS Phase 20·ADR-063의 확정 결정을 반영하며 추가 사업정책은 제안하지 않는다. 이번 작업에서는 기존 REQUIREMENTS·Accepted ADR을 수정하거나 새 Accepted ADR을 만들지 않는다. 승인된 UX의 공식 문서 반영과 기술 설계는 후속 작업에서 추적한다.

## Open Questions

없음 — Q-PRICE는 decided (Policy A, 2026-10-20)이며 참가비 표시·가격 재확인은 ADR-063을 따른다. Q-SEATS는 범위 밖으로 좌석 비공개를 유지한다. 반환·개인정보·권한은 기존 확정 정책을 유지한다. 메뉴 배치·레이아웃·문구·3단계 구성은 이 문서의 구체적인 검토 제안이다. 기존 24장의 무료/현장 결제 예외, 거래기록 정리, 기존 고객 전체 보관기간 등은 그대로 범위 밖이며 새 규칙으로 채우지 않는다.

기술적 선택인 정확한 관리자 URL·이전 방식, 가족 단위 조회 계약·집계, UI 구성·갱신, 접근성 검증 방법은 PLAN에서 다룬다. 이 SPEC 작성 완료를 PLAN 승인이나 구현 착수로 간주하지 않는다.

## Priority
