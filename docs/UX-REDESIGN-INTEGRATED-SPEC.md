## Problem

신청 업무는 클래스 상세에서 링크를 준비하고, 보호자가 모바일로 신청한 뒤, ADMIN이 내용을 확인하고 입금·예약을 처리하는 하나의 여정이다. 현재는 단일 링크와 그룹 관리, 긴 보호자 폼, 아이별 상세와 가족 입금 화면으로 나뉘어 사용자가 다음 행동과 처리 결과를 판단하기 어렵다.

목표는 ADMIN이 클래스 상세에서 바로 링크를 발급·복사·열어보고, 보호자가 세 입력 단계로 자기 가족의 신청을 제출하며, ADMIN이 가족 상세 한 화면에서 신청 검토·실제 입금 기록·선택 일괄 확정을 끝내는 것이다. 단일 클래스는 기본 흐름으로, 여러 클래스 통합 신청은 운영자가 선택하는 확장 기능으로 제공한다.

### Area 1 — 현재 클래스 상세와 발급

- 클래스 기본 정보 다음에 ADMIN 전용 `예약 신청 링크` 카드가 있다. 기존 단일 링크는 `링크 만들기 → 링크 복사`가 가능하며 재발급·중지는 확인창을 거친다. 보호자 화면을 직접 열어 확인하는 행동은 없다.
- 클래스 최종 신청금액은 카드 입력이 아니라 클래스 등록·수정에서 지정한다. 기존 링크에 금액이 있으면 `그룹 신청으로 전환`을 제공하고, 전환 후 관리는 그룹 상세로 이동한다. 새 방식은 그룹 구성과 발급이 별도 흐름이어서 단일 클래스 운영에도 그룹 개념을 이해해야 한다.
- `getApplicationLinkForClass`는 직접 연결 링크와 그 클래스가 포함된 그룹 링크를 `findFirst`로 함께 찾는다. 전용 단일 링크·기존 주소 전환·여러 클래스 통합 링크 중 어떤 것인지 식별해 모두 보여주는 조회가 아니다.
- 새 방식은 토큰 해시만 저장한다. 클래스 페이지는 원문 `token`이 있을 때만 카드의 `link`를 넘기므로, 새 방식 링크가 있어도 주소·발급 이력이 없는 것처럼 보일 수 있다. 그룹 화면의 원문 주소도 발급 직후 클라이언트 상태에만 남는다.
- 현재 카드의 `RUNTIME_NOT_READY`는 Preview 접근 제한과 설정·동의 준비 미비를 같은 상태로 설명한다. 클래스 페이지의 환경 설정 기반 준비 판정과 공개 화면의 DB 설정 우선 판정도 다를 수 있다. 화면만 보고 실제 운영 접수 중지인지, 현재 배포에서만 접근이 제한되는지 판단하기 어렵다.

### Area 2 — 현재 보호자 신청

- `/apply/[token]`의 기존 방식은 클래스 설명 아래 아이 정보·보호자 정보·요청사항·동의가 이어지는 한 폼이다. 필드별 오류·값 복원·필수/선택 표시·성공 뒤 재제출 방지가 이미 있으므로 보존한다.
- `/apply/group/[token]`은 보호자·입금자 정보 다음에 자녀마다 클래스·정보·동의 6개를 반복한다. `아이 추가/이 아이 삭제`는 있으나 단계 진행·자녀 요약·최종 검토가 없어 여러 자녀를 입력할수록 길어진다.
- 새 방식은 controlled state로 입력을 유지하고 필수 동의 오류는 아이별로 표시하지만, 일반 필드의 서버 오류는 대부분 `입력 내용을 다시 확인해주세요.`로 합쳐진다. 연락처 입력도 별도 모바일 전화 키패드 안내가 없다. 기존 방식의 필드별 피드백 수준을 새 방식에도 맞출 필요가 있다.
- 그룹 화면의 클래스는 프로그램명·시간·장소를 합친 선택 항목이다. 기존 단일 화면의 프로그램 설명·대상 연령까지 일관되게 읽을 수 있는 카드가 없다.
- 완료 화면은 새 방식에서 아이별 금액·총액·계좌·입금자명 복사, `입금했어요`, 친구 초대를 제공한다. 접수와 확정의 차이는 이미 안내하지만, 신청 진행 상태와 송금 후 다음 행동을 연결해 보여줄 필요가 있다.
- 같은 기기 재신청과 친구 초대는 이미 별도 capability 범위를 갖는다. 명시 전환한 기존 `/apply/[token]`도 새 방식 폼으로 이어진다. 주소 모양만으로 입력·금액 기능을 결정할 수 없다.

### Area 3 — 현재 관리자 신청과 선행 분석

선행 SPEC의 Current Process 및 Business Rules 3~5절을 기준으로 한다. 현재 목록은 아이별 표·아이 단위 페이지 구분이며 입금 열이 모바일에서 숨겨진다. 가족 상세는 보조 진입점이고, 가족 화면에서 선택 확정이 실제 입금 기록보다 먼저 나온다. 아이 상세의 신청·동의·반려·취소와 가족 화면의 입금·확정이 나뉜다.

선행 SPEC의 핵심은 **가족 제출 카드 기본 목록 → 가족 상세에서 신청 확인 → 은행 입금 기록 → 선택한 아이 예약 확정**이다. 개인정보 파기·계좌 설정·예약 전 반환·신청 링크 관리는 목적이 드러나는 관리 위치를 갖되, 기존 URL과 문맥 이동은 유지한다.

## User Story

- ADMIN으로서 클래스 상세에서 대상·신청금액·접수 조건을 확인하고 그룹 관리 화면을 거치지 않고 이 클래스의 링크를 보내고 싶다.
- ADMIN으로서 링크를 열어 보호자 화면을 확인하고, 접수 중지·주소 교체·Preview 접근 제한의 차이를 알고 싶다.
- 보호자로서 휴대폰에서 클래스를 먼저 확인하고, 보호자 정보를 한 번 입력하며 여러 자녀를 쉽게 추가·수정하고 싶다.
- 보호자로서 필수 확인과 선택 동의를 구별하고, 잘못 입력한 항목만 고친 뒤 신청 내용과 송금 안내를 이해하고 싶다.
- ADMIN으로서 한 가족의 신청 내용·알림·실제 입금·확정 상태를 같은 화면에서 확인하고 필요한 아이만 안전하게 확정하고 싶다.

## Scope

- Area 1: 클래스 상세의 단일 클래스 바로 발급·복사·열어보기, 금액·접수 준비·환경 제한 표시, 교체·중지 경고, 선택적인 여러 클래스 링크 관리.
- Area 2: 모바일 우선 3단계 입력, 자녀 추가·수정·클래스 배정, 동의 구분, 입력 보존·필드별 오류, 제출 완료·자기 송금 안내.
- Area 3: 선행 SPEC의 가족 단위 목록·처리 화면, 세 상태 축, 입금 후 같은 화면의 선택 일괄 확정, 모바일 카드.
- 통합: 페르소나별 여정, 재사용 UI 목록, UI만의 변경과 조회·액션 구조 변경 구분, 예상 파일·위험·수용 기준·호환 제약.

## Out of Scope

- 코드·컴포넌트·API·query·schema·migration 구현, 구체적 함수 계약·잠금 순서·라우트 이전 설계, 런타임 테스트 실행, PR·배포.
- ADR-063으로 확정된 가격 표시 외의 가격·할인·무료/현장 결제 예외·환불·보관기간 정책 변경, 개인정보 수집 확대, 새 법률 적합성 판단.
- 고객 계정·신청 조회/수정/취소 서비스, 온라인 결제, 자동 은행 조회·입금 매칭·송금·확정·외부 알림.
- 공개 가격표·전체 클래스 카탈로그·캘린더·정원·예약 수·잔여석·만석/예약 가능 여부 공개.
- 새 가족 master, 연락처 기반 가족 병합, 친구 정보 대리 입력, Child 관계 자동 생성, 새 영속 검토 상태.
- 기존 거래 수정·삭제·확인 취소 또는 반려·취소 신청 재개 정책 신설. 앱 전체 메뉴·AI 상담·다른 관리자 도메인 재설계는 이번 세 영역의 구현 범위로 확장하지 않는다.

## Business Rules

### 1. 공통 용어와 유지할 정책

| 용어 | 이 SPEC에서의 의미 |
|---|---|
| 단일 클래스 신청 링크 | 신청 대상 ClassSchedule이 1개인 링크. 새 방식에서는 여러 자녀가 그 클래스에 각자 신청할 수 있음 |
| 여러 클래스 통합 신청 링크 | ADMIN이 선택한 여러 ClassSchedule 중 자녀마다 1개를 고르는 링크. 한 아이가 여러 회차를 한 번에 예약하는 상품이 아님 |
| 가족 신청 | 한 번 제출한 `ReservationApplicationSubmission`. 이름·전화번호가 같은 다른 제출과 합치지 않음 |
| 기존 방식 | Phase 18의 단일 클래스·아이 1명·금액 없는 신청. 주소가 `/apply/[token]`이라는 이유만으로 기존 방식으로 단정하지 않음 |
| 새 방식 | Phase 20의 제출 묶음·아이별 고정 금액·실제 입금 원장을 사용하는 신청. 단일/여러 클래스 모두 포함 |
| 입금 알림 / 은행 확인 입금 / 예약 확정 | 보호자의 진술 / ADMIN이 확인한 실제 거래 / 서버 검증 뒤 Reservation 생성. 서로 별개 |
| 링크 열어보기 | 현재 공유 주소로 보호자 화면을 여는 읽기 행동. 접수 성공·좌석·운영 환경 전체 정상의 보증이 아님 |

1. `ReservationApplication`·`Reservation`·출결·동의·확정·반려·취소는 아이 1명 단위를 유지한다. 가족 화면은 표시·공통 입력·입금 처리의 묶음이다.
2. 신청 제출과 보호자 입금 알림은 Child·Reservation·Payment·ChildConsent를 생성·변경하지 않으며 좌석을 점유하지 않는다. 확정 전 신청·입금·예약 전 반환은 기존 매출 집계에 포함하지 않는다.
3. 금액은 ADMIN이 지정한 `ClassSchedule.applicationPrice`를 제출 시 각 신청의 `quotedAmount`로 고정한다. `Program.defaultPrice`·null·이전 결제에서 추론하거나 소급 갱신하지 않는다.
4. **Policy A — 결정됨(2026-10-20, ADR-063):** 유효한 신청·동행 초대 링크의 보호자에게 해당 링크 범위의 접수 가능 클래스별 `ClassSchedule.applicationPrice`와 본인 자녀의 예상금액·총액을 입력 1~3단계에서 표시한다. 제출 중 가격 변경은 클래스별 변경액·총액을 알리고 다시 확인받으며, 서버는 확인한 가격과 현재 가격이 다르면 저장하지 않는다. 제출 후 송금 안내는 유효한 자기 완료 권한에서 저장된 아이별 `quotedAmount`와 합계를 사용한다. 가격 없는 기존 Phase 18 흐름은 금액 미표시를 유지한다.
5. 기존 동의 원문·버전, 필수 확인 4개·선택 2개, 아이별 동의 이력, 미동의/철회 규칙, 개인정보 보관·수동 파기·거래 기록 보존은 유지한다.
6. 신청·발급·입금·확정·설정·파기는 ADMIN 전용이다. MANAGER·TEACHER에게 카드·건수·금액·토큰·관리 URL을 서버 조회·HTML·RSC·액션으로 제공하지 않는다.

### 2. Area 1 — Admin Class Detail: 바로 발급·복사·확인

#### 기본 구성과 단일 클래스 흐름

클래스 기본 정보 다음의 ADMIN 전용 영역을 **이 클래스 신청 링크**로 부른다. 모바일에서도 참가자 목록 아래까지 내려갈 필요 없이 찾을 수 있어야 한다.

```text
이 클래스 신청 링크
클래스: 프로그램 · 날짜/시작·종료 시간(KST)
참가비: 지정 금액 / 미설정
링크 상태: 미발급 / 유효한 링크 있음 / 접수 중지
[링크 발급] [링크 복사] [공유하기]
[신청 화면 확인]
{오류·설정 미비·Preview 제한이 있을 때만 이유·해결 행동}
[이 클래스 신청 보기]
[고급 설정 펼치기] (기본 접힘)
  발급 이력 / 링크 교체·중지 / 여러 클래스 링크
  진단 / 기존 방식 호환 설명 / 관련 링크 범위
```

- **정보 밀도:** 기본은 클래스 이름·시간, 참가비, 링크 상태와 `[링크 발급] [링크 복사] [공유하기] [신청 화면 확인]`이다. 상태와 원문 보유 여부에 맞는 행동만 활성화하고 주 행동 하나를 강조한다. 발급 이력, 교체·중지, 여러 클래스, 진단, 호환 설명은 기본 접힌 고급 영역에서 찾는다. 정상 상태에 준비·진단 장문을 나열하지 않는다. 오류·금액/설정 미비·Preview 제한 때만 관련 이유와 해결 행동을 기본 영역에 드러내며 전체 고급 내용을 자동 펼치지 않는다. 원문 일회 제공 경고와 주소는 발급 직후 행동에 필요한 안내로 표시한다.
- 새 단일 클래스 링크의 대상은 현재 클래스다. 별도 그룹 생성 화면·그룹명·클래스 재선택을 요구하지 않는다. 내부에서 기존 Group 구조를 재사용할 수 있으나 운영자가 그룹을 먼저 만들어야 한다는 절차는 없앤다. 새 Entity나 DB 변경을 이 요구의 전제로 삼지 않는다.
- ADMIN이 실제 신청금액을 지정하지 않았다면 `신청금액 설정`을 제공하고 같은 영역에서 기존 금액을 저장할 수 있게 한다. 저장 후 준비 상태를 갱신한다. 프로그램 기본 가격을 자동 입력·확정하지 않는다. 기존 금액 없는 링크에는 아래 호환 예외를 적용한다.
- 준비가 끝나면 **신청 링크 발급** 한 번으로 새 방식의 이 클래스 신청 주소를 얻는다. 발급 직후 같은 페이지에 주소·복사·공유·신청 화면 확인을 보여주고 발급 시각·ADMIN은 고급 영역에서 확인한다. 발급이 자동 복사·공유·테스트 제출까지 했다고 안내하지 않는다.
- 복사는 현재 주소만 복사한다. 복사할 때 링크 생성·토큰 교체·그룹 생성·기존 링크 중지가 일어나면 안 된다. 성공 문구는 `신청 링크를 복사했습니다.`이며 실패하면 주소 선택·수동 복사를 제공한다.
- `신청 화면 확인`은 주소가 있을 때 같은 환경의 실제 공개 주소를 새 탭에서 연다. 관리자 권한이나 특별 파라미터로 공개 guard를 우회하지 않고, 신청·입금 알림·테스트 데이터를 자동 생성하지 않는다.
- 현재 배포 환경을 주소 옆에 표시한다. Preview 주소를 운영용으로 검증됐다고 안내하거나 현재 origin에서 운영 도메인을 추정하지 않는다. 다른 환경의 주소·상태는 해당 환경에서 확인한다.
- 발급 실패 시 원인을 설명하고 기존 작업 맥락을 유지한다. 내부 범위 생성과 발급이 나뉘어도 재시도마다 그룹·링크를 중복 생성하거나 기존 유효 주소를 의도치 않게 무효화하지 않아야 한다. 구체적인 원자성·재시도 설계는 PLAN에서 정한다.

#### 상태·토큰·준비 상태를 분리한다

| 상황 | 관리자 표시·행동 | 지켜야 할 구분 |
|---|---|---|
| 링크가 없음 | `미발급` → 준비 후 `신청 링크 발급` | 해시 링크의 원문이 없다는 이유로 미발급으로 판정하지 않음 |
| 유효 링크·현재 주소 보유 | 주소·복사·공유·신청 화면 확인, 교체·중지는 고급 영역 | 유효 토큰이라는 사실만으로 실제 공개 접수를 보장하지 않음 |
| 유효한 새 방식 링크·원문 없음 | `유효한 링크가 있습니다. 주소는 발급할 때만 확인할 수 있습니다.`와 고급 영역의 발급 이력·`신청 링크 교체` | 기존 주소를 자동 복원·재발급하지 않음. 복사·실제 주소 열기는 제공하지 않음 |
| ADMIN이 접수 중지 | `접수 중지` → `접수 재개 및 새 링크 발급` | 예전 주소를 다시 살리는 행동으로 설명하지 않음 |
| 클래스 취소·시작 시각 경과 | `클래스 상태로 신규 접수 불가` | 발급·재개를 막지만 기존 신청 조회·처리는 유지 |
| 설정 또는 동의 준비 미비 | `입금 안내 설정 필요` / `동의 문구 준비 필요`와 해결 위치 | DB 운영 설정 우선 등 실제 공개 판정과 일치. 접수 중지·Preview 제한으로 오표시하지 않음 |
| Preview 일반 공개 접근 | `Preview 환경에서는 일반 공개 신청이 제한됩니다.` | 링크 중지 상태를 기록하지 않으며, 이 결과로 Production의 접수 상태를 추정하지 않음 |
| 허용된 Preview 합성 검증 | `합성 테스트 전용`과 기존 세션/lease 조건 안내 | 현재 검증 범위만 열림. 일반 공개나 실제 개인정보 접수의 허용이 아님 |

링크 유효성·업무상 접수 조건·현재 환경 접근 제한은 함께 성립할 수 있다. 예를 들어 중지된 링크를 Preview에서 보면 두 사실을 함께 표시한다. 새 DB 상태값 하나로 합치지 않고 서버가 판단한 사실을 구별해 보여준다. 공개 보호자 화면의 닫힘 사유는 기존 공통 일반 문구를 유지한다.

새 방식 토큰은 해시 저장·발급 응답에서의 일회 원문 제공을 유지한다. 미복사 후 재방문·탭 닫힘에는 주소를 다시 보여줄 수 있다고 약속하지 않는다. 평문 영속 저장·localStorage·로그·분석 이벤트로 이 제약을 우회하지 않는다. 기존 방식 원문 주소와 새 방식의 표시 가능 범위는 구분한다.

#### 여러 클래스 통합 신청은 opt-in

- **여러 클래스 통합 신청 링크 만들기**는 보조 기능이다. 선택하면 현재 클래스를 초기 포함 대상으로 보여주고, 기존 예정 클래스 중 추가할 클래스를 고른다. 월·연속 주차 조건을 신설하지 않는다.
- 포함 클래스·각 최종 신청금액·준비 상태를 확인한 뒤 구성·발급·복사로 이어진다. 구성 저장과 주소 발급의 성공 여부는 구별하되, 사용자가 서로 다른 관리 화면을 찾아야 완료되는 흐름은 피한다.
- 단일 링크가 있다고 여러 클래스 기능을 강요하지 않는다. 통합 링크 생성·구성 수정이 다른 단일 링크나 이미 배포한 다른 그룹 주소를 자동 교체하지 않는다.
- 같은 클래스가 여러 그룹에 포함될 수 있다. `이 클래스 전용`, `기존 주소를 전환한 링크`, `여러 클래스 통합`을 범위·포함 클래스·발급 이력으로 구별해 모두 찾을 수 있어야 한다. 클래스가 같다는 이유로 하나를 임의 선택·병합하지 않는다.
- 여러 클래스 링크를 교체·중지하면 해당 링크/그룹의 모든 포함 클래스에 영향이 있음을 표시한다. 클래스 상세에서 시작했어도 현재 클래스만 중지하는 것으로 안내하지 않는다.
- 구성 변경은 이후 제출에만 적용한다. 기존 신청의 클래스·고정 청구액·입금·확정은 유지한다. 사용자가 이미 선택한 클래스가 제거되면 공개 제출 시 서버가 다시 거부한다.

#### 교체·중지 경고와 기존 주소 전환

| 작업 | 확인 내용·버튼 | 결과 |
|---|---|---|
| 신청 링크 교체 | `새 링크를 발급하면 이전 링크로는 신청할 수 없습니다. 이미 접수된 신청은 유지됩니다. 공유한 곳에 새 주소를 다시 안내해주세요.` 대상 범위와 `교체하지 않고 닫기 / 이전 링크를 무효화하고 새 링크 발급` | 기존 토큰 즉시 무효, 새 주소 제공. 확인 취소 시 변경 없음 |
| 신청 접수 중지 | `이 링크의 신규 접수를 중지합니다. 이미 접수된 신청은 유지됩니다.` 대상 범위와 `중지하지 않고 닫기 / 신청 접수 중지` | 해당 범위의 신규 접수 차단. 예약 취소·신청 반려·환불을 실행하지 않음 |
| 접수 재개 | `새 주소로 접수를 재개합니다. 이전 주소는 사용할 수 없습니다.` | 같은 페이지에서 새 주소 제공. 클래스·설정·권한 재검증 |
| 기존 방식의 명시 전환 | `기존 주소를 유지하고 이후 신청부터 다자녀·입금 관리 방식을 적용합니다. 이미 접수된 신청은 기존 방식으로 유지됩니다.` | ADMIN 지정 금액·설정 확인 후만 전환. 자동 전환 없음 |

기존 주소를 유지하는 전환과 주소를 무효화하는 교체는 다른 작업이다. 전환된 주소도 이후 운영자가 명시적으로 해당 그룹 링크를 교체·중지하면 그 영향을 받는다. 여러 클래스 링크에는 확인창 안에서 영향받는 클래스 목록을 보여준다.

### 3. Area 2 — Guardian Application: 모바일 우선 3단계

#### 단계 정의와 공통 화면

```text
① 클래스 선택  →  ② 보호자·자녀 정보  →  ③ 동의·최종 확인
                                             [신청서 제출]
                                                 ↓
                                  신청 접수 완료·입금 안내 (결과 화면)
```

상단에 현재 단계의 번호·이름과 `신청은 예약 확정이 아닙니다.`를 표시한다. 완료한 입력 단계로 돌아가 수정할 수 있으며, `다음`·`이전`은 저장·접수가 아니다. 단계 이동 중 입력을 유지하고 최종 **신청서 제출**에서만 서버에 한 번의 제출을 요청한다. 화면 진행 단계는 새 영속 신청 상태가 아니다.

| 입력 단계 | 핵심 정보·행동 | 다음으로 가는 기준 |
|---|---|---|
| 1. 클래스 선택 | 유효 링크 범위의 클래스 카드, 프로그램명·설명·대상 연령·일시(KST)·장소·클래스별 참가비(`applicationPrice`). 단일 클래스는 대상 확인만 수행 | 단일 대상 확인 또는 통합 링크에서 이번 가족이 신청할 클래스 후보 1개 이상 선택 |
| 2. 보호자·자녀 정보 | 보호자 공통 정보, 새 방식 입금자명, 자녀 카드 추가·수정, 아이별 클래스 1개·금액, 본인 자녀의 예상 합계, 선택 요청사항 | 필수 정보와 각 아이의 클래스 배정 유효. 자녀 추가·제외·클래스 변경마다 금액·합계 갱신. 다음은 접수 아님 |
| 3. 동의·최종 확인 | 자녀 이름·클래스·일시·클래스별 참가비·총액, 정보 수정, 공통 필수 확인과 아이별 선택 동의, `아직 예약이 확정되지 않았습니다.` | 현재 문구·가격과 적용 대상을 확인한 뒤 제출. 서버가 링크·클래스·가격·동의·접근 범위를 최종 재검증 |

여러 클래스 링크의 1단계 선택은 **이번 폼의 후보 선택**이며 예약·좌석 확보·그룹 구성 변경이 아니다. 2단계에서 각 아이는 그 후보 중 정확히 1개 클래스에 연결된다. 선택한 후보 모두에 아이를 배정할 의무는 없고, 실제 신청 대상은 최종 아이별 연결이다. 같은 아이의 여러 클래스 동시 신청 기능을 만들지 않는다.

#### 참가비·예상 합계와 가격 변경

- 1단계는 링크 범위의 접수 가능 클래스별 참가비, 2단계는 본인 자녀별 선택 클래스·참가비와 계속 갱신되는 예상 합계, 3단계는 자녀 이름·클래스별 참가비·총액을 보여준다. 후보 클래스 가격을 모두 더하지 않고 실제 아이별 배정만 합산한다. 미배정 아이가 있으면 `클래스 선택 필요 · 예상 합계 확인 전`으로 표시하고 완성된 가족 총액처럼 안내하지 않는다.
- 입력 중 금액은 예상금액이다. 계좌 등 송금 안내는 제출 후 자기 완료 화면에서 제공한다. `applicationPrice`·`quotedAmount`의 null은 0원이나 `Program.defaultPrice`로 대체하지 않는다. 금액 없는 기존 Phase 18 링크는 자동 폐쇄·backfill 없이 1명·금액 미표시를 유지한다.
- 입력 중 가격 변경을 확인하면 `참가비가 변경되었습니다. 변경된 금액과 총액을 다시 확인해 주세요.`와 허용된 클래스별 이전→현재 금액, 자녀별 금액·새 총액을 표시한다. 현재 유효한 폼 입력·아이별 선택 동의는 보존하고 가격을 다시 확인받기 전 제출을 막는다. 가격 재확인은 필수 확인·동의를 대신하지 않는다.
- 제출 시 가격 불일치는 가족 전체를 저장하지 않고 같은 재확인 상태로 돌아간다. 보호자가 새 금액을 확인해 명시적으로 다시 제출하면 서버가 링크 유효성·클래스 접수 상태/소속·확인 가격과 현재 가격의 일치·현재 버전 필수 확인/동의·보호자/자녀 접근 범위를 다시 검증하고 `quotedAmount`로 고정한다. 재확인 뒤 다시 바뀌어도 동일하게 차단하며 조용한 새 가격 저장·자동 재제출을 하지 않는다.
- 무효·중지·접근 불가 링크에는 변경 가격도 제공하지 않고 일반 접수 불가 안내를 사용한다. 제출 뒤 클래스 가격이 바뀌어도 이미 제출·확정한 신청과 완료 화면은 저장된 스냅샷·합계를 유지한다.

#### 자녀 추가·수정과 재방문

- 새 방식은 자녀 1명으로 시작하고 `내 자녀 추가`로 늘린다. 현재 서버 범위인 최소 1명·최대 10명을 유지하고 상한에서 추가 불가 사유를 표시한다. 금액 없는 기존 방식은 아이 1명 흐름을 유지한다. 여러 자녀는 명시 전환 또는 새 방식 링크에서만 제공한다.
- 아이 카드에는 이름 또는 `아이 1`, 연결 클래스·일시, 입력 완료/입력 필요 표시와 `아이 정보 수정`을 둔다. 진행 상태는 현재 폼의 완성도를 뜻하며 예약 가능·서버 검증 완료를 뜻하지 않는다.
- 한 아이를 입력한 뒤 접고 다른 아이를 편집할 수 있다. 오류가 있는 카드는 자동으로 펼치고 해당 필드로 안내한다. 추가한 아이·다른 아이의 입력·선택 동의를 보존한다.
- 단일 링크의 새 아이는 같은 클래스를 표시한다. 여러 후보가 있으면 각 아이의 클래스를 명시적으로 고르게 한다. 앞 단계에서 후보를 제거했을 때 해당 아이를 다른 클래스로 조용히 바꾸지 않고 재선택을 요구한다.
- `이 아이를 신청에서 제외`는 초안에서만 제거한다. 대상 이름·클래스를 확인할 수 있게 하고 기존 Child 삭제·접수 취소로 표현하지 않는다. 마지막 1명은 유지하며 최종 제출 데이터에 제외한 아이가 남지 않는다.
- 자녀 추가·제외·클래스 변경 뒤 3단계의 적용 대상·요약을 갱신한다. 이미 확인한 공통 항목을 새 자녀에게 몰래 적용하지 않고 변경된 대상을 명확히 확인하게 한다. 각 아이의 선택 동의는 다른 아이에게 자동 복사하지 않는다.
- 같은 기기의 기존 자기 자녀는 현재 유효한 기기 capability로 허용된 범위만 선택한다. 권한 만료·회전·철회·브라우저 데이터 삭제 시 새 입력으로 진행하며 연락처만으로 조회하지 않는다.
- 기존 아이 선택은 현재 동일성 검증을 유지한다. 기존 정보가 읽기 전용인 경우 수정 가능한 프로필처럼 보이지 않게 안내하고, 다른 아이 입력으로 전환할 수 있게 한다. 신청 폼의 편집이 기존 Child 정보를 갱신한다고 약속하지 않는다. 비활성·파기 아이는 재선택하지 않는다.
- 친구 초대 보호자도 같은 세 단계를 사용하되 자기 가족만 입력한다. 초대한 가족의 자녀·동의·입금은 표시하거나 복사하지 않는다.

#### 정보 입력 범위와 모바일 피드백

보호자 이름·연락처·아이와의 관계는 한 번 입력하고, 새 방식에만 `입금할 때 사용할 이름`을 받는다. 아이별 이름·생년월일·성별은 기존 필수 규칙을 유지하며 성별의 `선택 안 함`도 유효하다. 요청사항은 선택이고 `건강·알레르기 정보는 적지 말아 주세요. 필요한 안전 정보는 예약 확정 후 따로 여쭙니다.`를 표시한다. 새 개인정보 항목을 추가하지 않는다.

| 상황 | 요구 피드백·보존 |
|---|---|
| 필수 누락·형식 오류 | 해당 보호자/아이 필드 옆에 `아이 이름을 입력해주세요.` 등 구체적 안내. 연락처는 숫자·하이픈, 생년월일은 유효 날짜·미래 금지 등 기존 규칙 사용 |
| 서버 일반 필드 오류 | 새 방식도 보호자 필드와 아이별 이름·생년월일·성별·클래스·요청사항에 안전한 오류를 연결. 원본 Zod 오류·제출 값·DB 오류를 그대로 노출하지 않음 |
| 다른 단계의 오류 | 상단에 수정할 단계·아이를 요약하고 해당 단계·펼친 카드의 첫 오류로 이동. 현재 단계 오류만 보여 이전 단계의 문제를 숨기지 않음 |
| 필수 동의 누락 | 대상 아이와 확인할 항목 바로 옆에 표시. 선택 미동의는 오류로 만들지 않음 |
| 입력 중 가격 변경 / 제출 시 가격 불일치 | 변경된 클래스별 금액·자녀별 금액·총액으로 이동해 재확인. 불일치 제출은 전부 미저장, 유효한 현재 입력 보존. 닫힌 링크는 가격 없이 일반 안내 |
| 링크 철회·중지·접수 범위 무효 | 기존 일반 접수 불가 안내. 클래스 존재·취소 등 내부 사유를 필드 오류로 누설하지 않음. 공개 표시 권한이 사라지면 입력 폼을 계속 노출하지 않음 |
| 통신 실패·처리 결과 불명 | 폼을 계속 보여줄 수 있는 경우 안전한 입력·클래스 선택·동의를 유지. 자동 재제출·성공 추정·전부 초기화 없이 재시도 안내. 이미 성공한 제출은 다시 보내지 않음 |
| 기존 자녀 조회 실패 | 이전 자녀가 없다고 단정하지 않고 새 정보 입력으로 진행할 수 있게 안내. 기존 입력을 지우거나 타 가족 조회로 대체하지 않음 |

필드 안내와 오류는 보조기기에서 입력에 연결한다. 상단 오류 요약만으로 대체하지 않는다. 연락처는 전화 입력·키패드, 생년월일은 모바일 너비에 맞는 날짜 입력을 사용하고 기존 허용 값·서버 Zod 검증을 완화하지 않는다.

단계 초안은 현재 처리 중인 폼 메모리 범위에서 보존한다. 새로고침·탭 종료 후 복원을 약속하지 않으며 평문 PII·동의·입금자명을 URL·localStorage·sessionStorage·로그에 저장하지 않는다. 제출 실패의 입력 보존은 유효한 현재 사용자 폼에 한정하며, 무효 capability로 서버의 개인정보를 다시 가져오는 근거가 아니다.

#### 필수 확인·선택 동의와 최종 검토

| 구분 | 항목 | 표시·저장 제약 |
|---|---|---|
| 필수 | 프로그램 안전 및 이용사항 확인, 개인정보 수집·이용 동의, 법정대리인 확인, 취소 및 환불규정 확인 | 네 항목을 각각 구별. 공통 확인은 적용할 아이·클래스를 보여 한 번 입력할 수 있으나 각 아이 신청에 해당 결과·버전을 저장 |
| 선택 | 활동 사진·영상 촬영 및 참여 보호자 공유, 사진·영상 YAHO 홍보 활용 | 별도 `선택 동의` 구역, `동의하지 않아도 참가에 제한이 없습니다.` 표시. 아이별로 다른 두 값을 유지하고 최종 요약에서도 확인 가능 |

- 원문과 현재 버전을 읽을 수 있게 한다. 화면상 재배치로 원문·보유기간·사진 공유 대상·환불 기준을 요약 변경하지 않는다. 이용사항·법정대리인·환불 확인과 ChildConsent로 옮기는 동의를 같은 종류의 이력으로 바꾸지 않는다.
- 체크박스는 기본 미선택이며 이전 신청의 동의를 자동 체크하지 않는다. 필수·선택을 함께 체크하는 `전체 동의`를 두지 않는다. 선택 동의를 필수처럼 강조하거나 미동의 자녀를 미완료로 표시하지 않는다.
- 3단계 요약에는 자녀 수·이름, 아이별 클래스·일시·장소·참가비와 총액, 입력 정보와 선택 동의 결과, `클래스 수정 / 보호자·아이 정보 수정`을 제공한다. 수정 후 금액·합계를 갱신하며 다른 입력을 유지한다.
- 제출 전 `아직 예약이 확정되지 않았습니다. 입금과 운영자 확인 후 예약이 확정됩니다.`와 예상 총액을 보여준다. 가격 변경은 다시 확인받으며 정확한 송금액·계좌는 저장된 스냅샷을 사용하는 완료 화면에서 안내한다.
- 최종 버튼은 **신청서 제출** 하나다. 진행 중 `신청서 제출 중…`, 성공 뒤 `완료 화면으로 이동 중…`으로 바꾸고 연타·Enter 재제출을 막는다. 클라이언트 검사와 별개로 서버가 링크·클래스·금액·동의·기기 소유 범위를 다시 검증한다. 다자녀는 모두 접수되거나 모두 실패해야 한다.

#### 제출 결과·금액·다음 행동

완료 화면은 세 입력 단계가 끝난 결과이며 제목은 **신청이 접수되었습니다**다. `예약 확정 완료`나 `입금 확인 완료`로 표현하지 않는다.

- 새 방식은 유효한 자기 완료 capability 범위에서만 아이별 고정 신청금액·합계·은행·계좌번호·예금주·보호자가 제시한 입금자명을 보여준다. 현재 가격을 다시 곱하거나 다른 신청 금액을 포함하지 않는다.
- `계좌번호 복사 / 입금액 복사 / 입금자명 복사`를 구분하고 복사 성공 대상을 알린다. 복사 실패 시 읽기 가능한 값을 선택·수동 복사할 수 있어야 한다.
- 다음 행동을 `안내 금액 송금 → 입금했어요로 알림 → 운영자가 실제 입금·신청 확인 후 예약 확정`으로 설명한다. 이 표시는 처리 안내이며 실시간 은행 조회나 보호자의 예약 상태 조회 기능이 아니다.
- **입금했어요**에는 `송금을 마친 뒤 눌러주세요. 운영자에게 알림을 남기며 실제 입금 확인이나 예약 확정을 대신하지 않습니다.`를 표시한다. 알림 후에는 `입금 알림을 보냈습니다. 운영자 확인을 기다려주세요.`로 바꾼다. 최초 시각 기록·멱등성과 내부 상태 비노출을 유지한다.
- 친구 초대는 보조 영역 `친구 보호자 초대`에 두고 친구 보호자가 자기 정보·동의를 직접 제출한다는 안내와 기존 초대 생성·복사·취소 기능을 유지한다. 계좌 안내·입금 알림보다 먼저 강조하지 않는다.
- 기존 방식은 일반 완료 안내의 계좌·예금주·채널 범위를 유지하며 없는 금액·입금자명·알림·초대 기능을 추정해 만들지 않는다. 기존 채널 링크의 이용 경로도 보존한다.
- 완료 권한 만료·무효 시 자기 자녀·금액·입금자명을 재노출하지 않고 기존 일반 안내 허용 범위만 제공한다. 새 입금 기한·입금자명 규칙·완료 화면의 취소/환불 안내·확정 통지 발송 약속을 추가하지 않는다.
- 성공 시 기존 전체 문서 이동·이전 폼 복귀 방지·캐시 정책을 유지한다. 뒤로가기·새로고침에서 제출 전 PII나 재제출 가능한 폼을 되살리지 않는다.

### 4. Area 3 — Admin Applications: 가족 단위 처리

이 영역의 상세 요구는 [선행 SPEC](UX-REDESIGN-ADMIN-APPLICATIONS-SPEC.md)의 Business Rules 2~5·9절과 UX-02~14·23~28을 참조한다. 아래는 세 영역 연결에 필요한 핵심이다. 선행 문서의 전체 메뉴·AI 화면 정리까지 이번 범위에 포함하는 것은 아니다.

#### 가족 카드와 세 상태 축

- 목록 기본 단위는 제출 1건이다. 가족별로 페이지를 구분해 같은 제출의 자녀가 두 페이지에 나뉘지 않아야 한다. `submissionId` 없는 기존 신청은 `기존 방식 · 아이 1명 신청` 카드로 표시하고 Submission을 소급 생성하지 않는다.
- 기본 필터는 처리 대기다. `대기 N가족 · 아이 신청 M건`처럼 단위를 붙이고 전역 배지도 실제 가족 수로 집계한다. 아이 건수를 가족 수로 재명명하지 않는다.
- 가족 카드의 기본은 보호자 이름·자녀 수/이름 요약·프로그램/클래스 시간·처리 상태·핵심 입금 상태와 `[신청 처리하기]`다. 현재 필요한 행동을 먼저 짧게 표시하며 아래 세 상태를 모두 장문으로 나열하지 않는다. 아이 펼침에서 각 클래스·고정 금액·처리 상태를 확인한다. 배정 P·가용 A 상세·반환 의무 원장·거래별 입금·PaymentItem 매핑·동의 원문은 기본 숨김이며 상세의 해당 영역에서 펼친다. 연락처·생년월일·요청사항·동의 원문은 상세에서만 노출한다.
- 모바일은 세로 카드이며 핵심 입금 상태·필요한 행동을 바로 보여준다. 카드 펼침·상세 이동은 별도 버튼이고 중첩 링크를 만들지 않는다. 목록에서 입금 기록·확정을 바로 실행하지 않는다.

| 독립 상태 | 예시 문구 | 근거·판단 금지 |
|---|---|---|
| 보호자 입금 알림 | `알림 없음` / `알림 받음 · 시각` | `depositNotifiedAt`. 알림 없음은 미입금이 아니고 알림 있음은 은행 확인이 아님 |
| 은행 확인 입금 | `은행 확인 필요` / `은행 확인 D원` (가용액 A 상세는 펼침/처리 영역) | 실제 원장. 선택 대상 부족액은 별도 표시. 단순 `미확인`으로 합치지 않음 |
| 예약 확정 | `예약 확정 n/N명 · 처리 대기 m명` 및 아이별 반려·취소 | 실제 아이별 신청 상태. 혼합 상태 가족을 전체 확정으로 표시하지 않음 |

반환 필요 등 현재 조치가 있는 경우 짧은 경고·상세 진입을 표시한다. 세 독립 상태의 세부 시각·금액·반환 이력은 상세에서 확인한다. 가족 단위 입금과 클래스 필터의 아이 범위가 다름을 설명하고, 신청 상태와 클래스 조건은 같은 아이 신청이 만족해야 한다. 연락처가 같은 다른 제출·친구 가족을 합치거나 자동 확정하지 않는다.

#### 같은 화면의 신청 확인 → 입금 → 선택 일괄 확정

```text
가족 신청 상세 — 보호자 · 자녀 수 · 접수 일시
입금 알림 | 은행 확인 입금 | 예약 확정 요약
① 신청 확인: 아이별 정보·클래스·동의·기존 아이 연결·요청사항 검토
② 입금 확인: 실제 거래 입력·누적 원장·가용액·반환 내역
③ 예약 확정: 이번 아이 선택·금액·최종 검증·결과
관련 예약·결제 / 처리·보관 이력 / 목록으로 복귀
```

- 기존 아이 선택·신청 정보로 새 아이 등록을 구별한다. 후보는 참고이며 자동 연결·기존 정보 덮어쓰기를 하지 않는다. 선택 사진 미동의도 정상 신청이다.
- ADMIN이 은행을 확인한 뒤 실제 입금액·은행 입금자명·실제 입금일시(KST)를 기록한다. 보호자 알림이 없어도 입력할 수 있고, 여러 번의 부분·초과입금을 실제액 그대로 누적한다.
- 입금 저장 후 같은 화면에서 원장·가용액·선택 청구액·부족액을 최신 서버 값으로 갱신한다. 수동 새로고침이나 다른 화면 이동 없이 확정으로 이어진다. 저장만으로 Reservation을 만들지 않는다.
- 주 버튼은 **선택한 아이 {n}명 예약 확정**이다. 명시적으로 고른 아이만 대상으로 하며 아이 연결·입금액·중복·비활성/파기·클래스 상태·정원 초과 확인을 기존 서버 규칙으로 검증한다. 한 번의 일괄 처리는 전부 성공하거나 전부 실패한다.
- 초과 예약은 기존 ADMIN 명시 확인을 유지하고, 대상·선택이 바뀌면 확인을 다시 받는다. 공개 보호자 화면에는 이 정보가 전달되지 않는다.
- 반려는 운영자 판단, 신청 취소는 보호자 요청으로 구별하고 아이별 사유를 받는다. 같은 가족 화면에서 처리 결과·반환 필요액을 보여준다. 확정 후에는 기존 Reservation 취소·Payment/Refund 화면으로 연결한다.
- 새 방식 확정 후 실제 예약·연결 결제를 보여주고 중복 결제 등록을 유도하지 않는다. 기존 방식은 금액 기록 없는 입금 확인·확정 뒤 별도 수동 결제 흐름을 유지한다.
- 반환 내역·부분반환 기록은 같은 가족 문맥에서 제공하고 전체 반환 관리와 같은 원장을 사용한다. 버튼은 **반환 이체 기록**이며 실제 송금 실행을 뜻하지 않는다.
- 기존 아이 상세 URL·가족 상세·클래스의 `이 클래스 신청 보기`와 신청 목록의 필터·페이지·복귀 위치를 연결한다. 경로 이전의 세부 방식은 PLAN에서 정한다.

#### 보호자: 모바일 링크 열기부터 송금 알림까지

| 단계·진입 | 사용자 목적·행동 | 현재 마찰 → 목표 경험 | 완료 근거·인계 |

| 1. 클래스 선택 | 이번 가족의 클래스 후보 선택 | 입력 전에 대상 파악 어려움 → 단일 대상 명시·여러 클래스 선택 | 다음은 정보 입력이며 아직 접수되지 않음 |
| 2. 보호자·자녀 정보 | 보호자 한 번 입력·자녀 추가·수정 | 반복·긴 폼 → 아이 카드·요약·필드별 안내 | 자녀마다 1개 클래스·참가비·예상 합계 갱신, 오류 시 다른 입력 유지 |
| 3. 동의·최종 확인 | 필수/선택을 이해하고 신청 검토 | 동의 반복·버튼 의미 혼동 → 적용 대상·아이별 선택값·수정 진입 | 자녀별 참가비·총액 재확인, `신청서 제출`만 원자 접수·서버 최종 검증 |
| 접수 완료 결과 | 내 가족 입금액·계좌 확인·복사 | 완료=확정 오인 → 접수 상태와 다음 행동 설명 | 새 방식만 자기 고정 금액·합계·입금자명 제공 |

| 선택적 친구 초대·재방문 | 친구가 자기 신청, 다음 신청 간편 입력 | 다른 가족 정보 대리 위험 → 별도 자기 입력·현재 동의 | 기존 초대·기기 capability 범위 유지 |

두 여정의 연결점은 동일한 링크 범위, 제출 당시 고정 금액, 가족 제출 ID와 아이별 신청이다. 관리자 단계와 보호자 입력 단계를 같은 상태 기계로 합치거나 보호자에게 관리자 내부 검토 상태를 공개하지 않는다.

| 자녀 입력·요약 카드 | 보호자 2·3단계, ADMIN 아이 검토의 표시 요소 | 추가·편집·제외·클래스 연결·오류. ADMIN 처리 액션과 공개 입력 기능을 혼합하지 않음 |
| 확인·동의 원문과 결과 | 보호자 3단계, ADMIN 가족 상세 | 기존 원문·버전·필수/선택·아이 적용 대상. 입력 컨트롤과 읽기 결과를 구별 |
| 필드 오류·폼 오류 요약 | 보호자 폼, 금액·입금·반환·확정 입력 | 필드 연결·첫 오류 이동·안전한 오류·입력 보존. PII를 로그·분석으로 보내지 않음 |
| 가족 신청 카드·상태 요약 | 관리자 목록·상세 | 가족/아이 수, 세 상태 축·혼합 상태. 공개 완료 UI와 재무 데이터를 공유하지 않음 |
| 금액 내역·가용액 요약 | ADMIN 가족 상세, 보호자 입력 예상금액, 자기 완료 화면의 별도 표시 | 입력은 링크 범위의 `applicationPrice`·본인 예상 합계, 완료는 저장된 `quotedAmount`, ADMIN은 원장 권위값 사용. 사용처별 권한·데이터 계약 분리 |
| 복사 행동·결과 알림 | 링크·계좌·입금액·입금자명 | 복사만 수행, 대상별 성공 문구·수동 복사. 자동 재발급 없음 |
| 영향 확인창 | 링크 교체·중지·전환, 아이 반려·취소 | 대상·영향·실행/닫기 구분, 키보드·포커스 복귀. 확인창 자체가 서버 검증을 대체하지 않음 |
| 로딩·빈 상태·오류 안내 | 세 영역의 조회·제출·처리 | 로딩·0건·필터 0건·실패·저장 중·완료를 구별하고 해당 맥락 재시도 |

현재 기본 요소는 `components/ui/{button,card,input,label,select,textarea,checkbox,disclosure,badge,warning-banner}.tsx`다. 진행 표시·도메인 조합·확인 UI의 정확한 분리 위치는 PLAN에서 정하며 전역 UI 라이브러리를 교체하지 않는다.

### 7. 모바일·접근성·기본 상태

- `md`(768px) 미만을 모바일 기준으로 삼고 360px·390px·데스크톱에서 확인한다. 관리자 신청은 카드, 보호자 폼은 한 열로 구성하며 가로 스크롤이나 핵심 열 숨김으로 해결하지 않는다.
- 영역의 주 행동은 하나만 강조한다. 모바일 버튼은 전체 폭·세로 배치, 누를 영역은 최소 44px을 목표로 한다. 긴 주소·프로그램명·날짜 입력이 화면을 밀어내지 않아야 한다.
- 단계 이동 시 제목, 오류 시 첫 오류, 추가·제외 시 해당 아이나 다음 유효 위치로 포커스를 안내한다. 단계는 `현재 단계`를 텍스트·보조기기에 전달하고 색만으로 상태를 구별하지 않는다.
- 필드 라벨·오류 연결, 펼침 상태, 키보드 조작, 닫힌 확인창의 비활성 포커스, 성공 알림을 검증한다. 고정 하단 행동을 사용한다면 모바일 키보드·안전 영역·본문/동의 내용을 가리지 않아야 한다.
- 로딩은 진행 중임을 알리고 동일 작업의 중복 클릭을 막는다. 실패를 0건·미발급·저장 성공으로 표시하지 않는다. 신청 0건과 필터 결과 0건은 구별해 링크 준비 또는 필터 초기화를 안내한다.
- 복사 실패·조회 실패·쓰기 실패는 각각 해당 행동의 복구 수단을 제공한다. 세부 운영 오류·토큰·PII·DB 메시지를 공개 문구에 넣지 않는다.

### 8. 데이터·입금·결제·반환·예약 정합성 제약

| 대상 | 반드시 유지할 불변 조건 |
|---|---|
| 신청 단위 | 한 제출의 자녀별 독립 신청. 별도 제출·친구 가족·Child 관계를 병합하지 않음. 기존 금액 없는 신청에 Submission·금액을 생성하지 않음 |
| 금액 고정 | 제출 시 보호자가 확인한 가격과 현재 ADMIN 지정 클래스 금액의 일치를 재검증한 뒤 고정. 불일치는 가족 전체 미저장·가격 재확인. 이후 클래스·프로그램·그룹 변경은 기존 `quotedAmount`를 바꾸지 않음. null은 0원·무료·기본 가격이 아님 |
| 입금 알림 | 최초 알림 시각만 멱등 기록. Payment·Reservation·Revenue·ADMIN 확인을 생성하지 않음 |
| 실제 입금 | ADMIN의 실제 은행 확인 후 `ApplicationDeposit`에 여러 거래를 실제 금액대로 보존. 보호자 입금자명과 실제 입금자명 불일치는 ADMIN 검토이며 자동 일치·거절·확정하지 않음 |
| 가용액 | 확인 입금 누계 D = 미배정 가용액 A + Payment 배정액 P + 반환 필요 잔액 R + 완료 반환액 T. `A = D − P − R − T`를 유지하며 반환액을 중복 차감하지 않음 |
| 선택 확정 | 선택 아이 고정 청구액 합계 S와 A 비교. 부족액은 `max(0, S − A)`. 입금 누계와 원래 가족 총액의 단순 비교로 확정 가능 여부를 대신하지 않음 |
| 새 방식 Payment | 확정 성공 시 선택 아이 청구액만 기존 Payment/PaymentItem에 정확히 한 번 연결. 초과입금·예약 전 반환은 Payment·Refund·Revenue에 넣지 않음. 이미 배정/반환한 돈을 형제에게 재사용하지 않음 |
| 기존 방식 Payment | 금액 없는 기존 입금 확인 기록으로 기존 확정 규칙 적용. 확정만으로 Payment 생성 안 함. 후속 수동 결제 유지 |
| 반환과 환불 | 확정 전 `ReturnObligation`·`ApplicationReturn`의 여러 부분반환과 확정 후 기존 Refund를 분리. 기존 수동 환불액·상한·사유·예외 권한 유지, 새 자동 계산·수수료 없음 |
| 예약 검증 | 기존 예약 코어의 중복·클래스 상태·아이 비활성/파기·정원·명시 초과 확인 유지. 신청은 만석이어도 접수하며 실제 좌석 판단은 ADMIN 확정 시 수행 |
| 원자성·경합 | 다자녀 접수·선택 일괄 확정은 각각 전체 성공/실패. 두 ADMIN·입금/반환/확정·파기·구성 변경·토큰 철회 경합에서 기존 잠금·트랜잭션·제약을 유지. UI disabled는 대체 수단 아님 |
| 중복 처리 | 동일 금융 작업의 멱등 키·기존 중복 방지·감사 기록을 유지. 결과 불명 시 새 금융 작업을 자동 생성하지 않음. 같은 이름/전화번호의 별도 신청은 기존 중복 가능 표시 대상으로 두고 자동 병합·차단하지 않음 |
| 동의·개인정보 | 확인/동의 구분과 아이별 append-only·신청 시각·버전·미동의/철회 기록 유지. 안전정보 별도 관리. 1년/5년 보관·기존 대상 제한·수동 파기·상한·거래 기록 보존을 변경하지 않음 |

가족 요약·단계 완료·부분 확정 등은 기존 데이터의 표시이며 새 사업 상태를 추가하지 않는다. 원장 계산은 기존 서버의 권위 있는 값으로 제공하고 화면마다 별도 계산 규칙을 만들지 않는다. 요청사항을 예약 메모로 옮기기 전에 ADMIN이 건강정보 포함 여부를 검토할 수 있어야 하며 신청·동의 원문을 수정하는 기능과 구별한다.

### 9. 기존 링크·권한·환경 호환

| 현재 주소·데이터 | 재설계 후 보장 |
|---|---|
| 기존 `/apply/[token]`, 금액 없는 Phase 18 신청 | 주소·클래스 1개·아이 1명·금액 미표시·기존 입금 확인/수동 결제 유지. 화면만 세 입력 단계로 정리 가능. 가격 미설정을 이유로 자동 폐쇄하지 않음 |
| 명시 전환된 `/apply/[token]` | 같은 주소에서 이후 새 방식 접수. 과거 신청은 기존 방식, 이후는 고정 금액·다자녀·원장 방식. UI가 URL 모양으로 모드를 추정하지 않음 |
| `/apply/group/[token]` | 동일 유효 토큰·그룹 범위 유지. 화면 개편만으로 교체하지 않으며 새 단일 클래스 범위도 별도 그룹 생성 절차 없이 같은 새 방식 사용 가능 |
| `/apply/companion/[token]` | 기존 만료·취소·범위·자기 가족 동의 유지. 다른 가족 정보·기기 권한·관리 기능을 주지 않음 |
| `/apply/complete`, 완료/기기 capability | 기존 유효 범위·만료·Secure/HttpOnly·캐시/전체 문서 이동 유지. 만료된 완료 권한을 기기 권한으로 대체해 금액을 복원하지 않음 |
| 여러 개 링크·중지/과거 링크 | 클래스가 같아도 독립 항목으로 보존. 자동 최신 선택·병합·전환·재발급 없음. 명시한 해당 범위의 교체/중지만 신규 접수에 영향 |
| 관리자 목록·아이 상세·가족 상세 URL | 기존 북마크·권한·필터 의미 보존. 새 가족 중심 화면 또는 해당 아이 영역으로 도달. PII를 새 query parameter에 넣지 않음 |

공개 HTML·RSC·서버 응답에는 유효 링크 범위의 접수 가능 클래스별 `applicationPrice`와 본인 자녀 예상금액만 허용한다. 다른 그룹 가격·전체 카탈로그·정원·예약/잔여/만석 수·예약 가능 여부·내부 메모/운영정보·다른 가족 PII·입금/결제/반환/환불 원장은 HTML·RSC·서버 응답·오류·로그·캐시에 없어야 한다. 가격·PII를 다른 링크/기기의 캐시로 재사용하지 않으며 무효·중지·접근 불가 링크에는 가격을 제공하지 않는다. 허용된 설명·연령 정보를 보강할 때 ADMIN 클래스 전체 데이터를 공개 컴포넌트로 넘기지 않는다. 유효하지 않거나 닫힌 링크는 기존 `현재 신청을 받지 않는 링크입니다.`라는 일반 안내를 유지한다.

Preview의 일반 공개 차단·Production의 합성 그룹 거부·제한된 합성 lease/수동 테스트 세션을 유지한다. 수동 세션과 자동 lease, 친구 초대는 허용 범위가 같다고 간주하지 않는다. `열어보기` UX가 접수 guard·역할·허용 합성 데이터·운영 승인 조건을 바꾸는 근거가 되어서는 안 된다.

### 10. UI-only vs 구조 변경 분리

| 분류 | 요구 | 후속 영향·검증 범위 |

| 구조 변경: 목록 조회 | 가족 단위 페이지·필터·가족/아이 별도 집계·기존 신청 어댑터 | 아이 페이지를 가져와 화면에서만 묶는 방식으로 충족 불가. 읽기 모델 변경이며 가족 Entity 신설 아님 |

구조 변경은 기존 모델을 쓰는 조회·액션 연결 변경도 포함한다. 현재 요구만으로 schema·migration이 필요하다고 단정하지 않는다. 정확한 API·컴포넌트·transaction·파일 분할은 PLAN의 책임이다.

### Screen design deliverable — 화면 설계 산출물

[docs/UX-SCREEN-LAYOUTS.md](UX-SCREEN-LAYOUTS.md)를 세 화면의 배치·문구·상태·전환 산출물로 참조한다. Screen A는 관리자 클래스 상세 링크 발급, Screen B는 가족 목록·신청 확인→입금→확정, Screen C는 보호자 세 입력 단계와 별도 결과다. 이 SPEC은 정책·권한·수용 기준을, 화면 설계는 그 범위 안의 시각적 배치를 정의한다. 입력 참가비·예상 합계는 Policy A를 따르며 잔여석 정보는 표시하지 않는다.

후속 PLAN과 QA는 해당 문서의 LAYOUT-A1/A2 ↔ INT-01~07·27, LAYOUT-B1/B2 ↔ INT-18~24·28, LAYOUT-C1/C2 ↔ INT-08~17·26, LAYOUT-X1 ↔ INT-25·28~30을 추적한다. 이번 4개 문서 정리에서 INT-14 ↔ UX-21 ↔ LAYOUT-C2의 금액·재확인·공개 범위를 맞추고 구현 인계 시 함께 검토한다.

### Link hash limitation — 링크 원문 일회 제공과 전달 흐름

새 방식 링크는 **원문 토큰을 해시로만 저장**한다. 서버는 저장된 해시에서 원문을 복원할 수 없으며, 원문 주소는 최초 발급 성공 응답에서만 제공된다. **새로고침·탭 닫힘·재방문 또는 발급 응답 유실 후에는 기존 원문 주소를 다시 표시·복사·공유·열어보기 할 수 없다.** 이미 외부에 복사한 주소는 기존 유효 조건에 따르며, 관리 화면에 원문이 없다는 이유로 무효가 되지 않는다. 기존 방식의 평문 주소 호환은 그대로 유지한다.

1. 발급 직후 같은 카드 상단에 `링크를 발급했습니다. 이 화면을 떠나면 주소를 다시 확인할 수 없습니다. 지금 복사하거나 공유해 주세요.`와 대상·환경·주소를 표시한다. 발급 이력은 기본 접힌 고급 영역에 둔다. 현재 페이지 메모리에서만 원문을 유지하며 서버 갱신 후에도 현재 Link ID·유효 범위를 확인한다.
2. **[링크 복사] [공유하기] [신청 화면 확인]**를 바로 제공한다. 자동 복사·외부 발송은 하지 않는다. 공유는 ADMIN이 눌러 기기의 공유 창과 대상을 선택하는 행동이며 지원하지 않으면 복사로 안내한다. 취소를 실패·공유 완료로 표시하지 않는다.
3. 복사 성공은 `신청 링크를 복사했습니다.`로 알린다. 거부·실패 시 `복사하지 못했습니다. 아래 주소를 길게 눌러 직접 복사해 주세요.`와 선택 가능한 원문을 현재 화면에서 제공한다. 복사·공유·열기는 발급·교체·신청 생성 작업을 실행하지 않는다.
4. 원문 없는 재방문에는 `링크는 유지되고 있습니다. 주소는 발급 직후에만 확인할 수 있어 다시 복사할 수 없습니다. 이전에 복사한 주소를 확인해 주세요.`를 표시하고 이력은 고급 영역에서 확인한다. 복사·공유·열기 대신 제한 이유를 보여주며 `미발급`으로 바꾸지 않는다.
5. 주소를 잃었다면 명시적인 **신청 링크 교체**만 새 주소를 만든다. 이전 링크 무효·이미 접수된 신청 유지·영향받는 클래스·재공유 필요를 확인한 후 실행한다. 응답 유실·재시도·재방문을 자동 교체로 해결하거나 평문 DB·브라우저 저장소·로그·분석 이벤트에 원문을 보관하지 않는다.

이 보완은 BR 2, INT-02~07·25·29를 구체화한다. 즉시 전달 성공·수동 복사·공유 취소·재방문·응답 유실·교체 취소와 실행을 각각 검증한다.

### Preview test links vs production links — ADMIN용 쉬운 한국어 안내

환경 배지는 ADMIN 카드의 주소·행동 버튼 옆에 작게 두고, 오류·설정 미비·Preview 제한 때만 해당 상세 설명을 기본 영역에 표시한다. 정상 상태의 진단·호환 설명은 고급 영역에서 확인한다. 일반 보호자 화면에는 내부 진단 문구 대신 기존 공통 접수 불가 안내를 유지한다.

| ADMIN이 보는 상황 | 표시 제목 | 쉬운 한국어 설명·행동 |
|---|---|---|
| Preview의 일반 링크 | **테스트용 주소 · 실제 신청에 보내지 마세요** | `개발 중인 화면을 확인하는 주소입니다. 이 환경에서는 일반 보호자 신청을 받지 않습니다. 실제 신청 주소는 운영 화면에서 확인해 주세요.` 일반 주소 열기는 기존 공개 차단 결과를 따른다. |
| 기존 조건으로 허용된 Preview 테스트 | **허용된 테스트만 가능** | `미리 허용된 테스트 주소와 테스트 시간 안에서만 확인할 수 있습니다. 가상의 이름과 연락처를 사용해 주세요. 실제 보호자에게 보내지 마세요.` 현재 허용 범위·만료만 표시하며 권한을 새로 부여하지 않는다. |
| 실제 Production 배포에서 확인한 운영 링크 | **운영용 신청 주소** | `보호자에게 안내할 주소입니다. 링크의 접수 상태와 클래스·입금 안내·동의 문구 준비 상태를 함께 확인해 주세요.` 원문이 있을 때 복사·공유하며 환경 배지만으로 접수 가능을 보증하지 않는다. |
| Preview 제한과 ADMIN 접수 중지가 동시 발생 | **테스트 환경 제한 / 접수 중지** 각각 표시 | `이 테스트 환경에서는 일반 신청이 제한됩니다. 이 링크의 접수도 관리자가 중지한 상태입니다.` 테스트 제한을 풀기 위한 접수 재개를 유도하지 않는다. |

사용자 안내에는 `lease`, `guard`, `capability`, `RUNTIME_NOT_READY`를 설명 없이 노출하지 않는다. 기술 검증에서는 BR 9·INT-05·26·27을 그대로 적용한다: 일반 Preview 공개 차단, 승인된 합성 범위·세션·lease·만료, 수동 세션과 친구 초대의 서로 다른 조건, Production 합성 그룹 거부, ADMIN 조회·액션 권한을 보존한다. 열어보기·복사·공유는 우회 파라미터를 붙이지 않고 현재 환경 주소만 이용하며 Preview에서 운영 도메인이나 운영 접수 상태를 추정하지 않는다.
